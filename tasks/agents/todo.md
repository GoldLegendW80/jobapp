# Tasks: agents

Spec: [SPEC-agents.md](../../SPEC-agents.md). Depends on jobs (J5 worker and arq queue, SSE helper `app/sse.py`).

## Architecture decisions
- The agents queue is a second arq `QueueSpec` in the existing `worker` process (J5 design), not a new container.
- Credentials encrypted with `CREDENTIALS_KEY` (AES-GCM or Fernet via `cryptography`), decrypted only in the worker for the duration of a run.
- Every SDK fact (options, auth env vars, streaming message types, usage and cost fields, session persistence, file reading) is verified against the official Agent SDK docs before use and recorded here.
- CI never calls a model: a fake backend replays recorded SDK message streams.
- **Chat continuity (decided 2026-10-10, review of PR #12):** every chat message starts a fresh SDK session whose prompt is rebuilt from `agent_messages` stored in Postgres; there is no `sdk_session_id` and nothing about a conversation stays on disk. This matches the scratch directory being deleted after each run (A2) and SPEC-ingestion's persistence-off rule. SPEC-agents' `agent_threads.sdk_session_id` is dropped by A4.
- **Cost on a subscription (decided 2026-10-10, issue #33):** the SDK's `total_cost_usd` is filled on every run, on a Claude subscription too, where it is an estimate at API prices and not a bill: what the user pays is set by the plan. A run did not record which kind of credential it used, so migration 0010 adds `agent_runs.credential_kind` (the enum of `model_credentials`, nullable), written by the worker in the transaction that reads the credential at the start of the run: the kind only, never the secret, and not a reference to the credential row, so a run keeps what it used when the user replaces the credential later. No backfill: guessing from today's credential would be wrong whenever it changed, so runs from before the column (the three A5 runs on the Jetson among them) and runs that failed before reading a credential have no kind. The web words the amount by kind: an API key, "Cost"; a subscription, "Estimate at API prices" with "This run used your Claude subscription and counts toward your plan's usage limits. What you pay is set by your plan, not by this amount: the estimate is what the same tokens cost at API prices."; no kind, "Amount at API prices" with a sentence saying it is not known whether it was billed. `cost_usd` itself is stored as before. **Issue #80 (review of PR #71):** the sentence now says that a subscription run counts toward the plan's usage limits, and no wording says "not billed" any more, in the note or in the short forms ("Estimate, not a bill", "estimated at API prices, not a bill"; the `/runs` page says the same): the app knows the kind of credential, not the plan, and a plan with paid extra usage turned on may charge for a run, so the only thing said about money is that what the user pays is set by the plan. The `usage` event carries `credential_kind` next to the amount (the kind, never the secret; `null` when the run read no credential), so the step is worded right the moment it arrives: the run's detail, read while the run was queued, knows no kind yet, and the line said "at API prices" until the detail was read again. A step stored before this has no such field and falls back to the run's own kind. The note is tied to the amount for assistive technology (`aria-describedby` on the amount's `dd`).
- **Triage note voice (decided 2026-10-10, issue #33):** the real runs wrote the note about the user in the third person ("he needs no permit") while the summary said "you". `TRIAGE_PROMPT` now has a Voice rule: everything the user reads (the note, the status reason, the final summary) is written to the user in the second person, the third person forms are ruled out by name, and steps 5 to 7 each say their text is addressed to the user. The tools did not change. A test holds the prompt text, and the recorded triage streams were put in the same voice. **Issue #80 (review of PR #71):** "they" is ruled out for the user only ("They" is fine for the company, the team, the people who wrote the posting: the unscoped ban read as a ban on the word). The chat agent's prompt has one more rule: "you" and "your" in a note stored on the job mean the user, since an accepted triage note is written to the user and the chat agent reads it with `get_job`. The test of the recorded streams finds the three texts the prompt names where they are written (the `propose_note` text, the `propose_status` reason, the result's summary: one summary per run, a note in every recorded triage) and judges them together with the text the agent says between its tool calls, which the user reads live and in the timeline. The words are those of the Voice rule, the other forms of its pronouns and the name of the tests' user, the name matched with its capitals. As before it does not judge "they", which a text cannot be asked about.
- **Tool allow-list:** no shell, no web, no built-in file tools, except `Read` scoped to the run's scratch directory and only for ingestion runs. All other tools are in-process app tools enforcing user scoping server side. The ingestion plan (2026-10-10, tasks/ingestion/todo.md) does not use that exception: images reach the agent through an app tool that returns one image block per call, a path verified through the real CLI on 2026-10-10 (`tasks/evidence/ingestion-g0/`: the SDK's reader fails on a tool result echoed over 1 MiB, so an image is at most 300,000 bytes), and no scoped `Read` is kept as a fallback.
- **Logging:** never log a credential, a token or a full prompt containing personal data; tests assert run logs contain no prompt text.
- **Concurrency:** the agents queue runs with `max_jobs=2`; A2 measures the worker's peak memory with two Claude Code CLI processes plus a sweep against the 1536m limit.
- **Image:** Node and the Claude Code CLI go into a separate `worker` build stage so the api image stays small; the worker service builds that target.
- **Live answer text (decided 2026-10-10, issue #33):** the answer appears while it is written, without a database row per token. Shape: (1) the worker turns on `include_partial_messages`, reads only the `text_delta`s of the text block being written (`app/agents/live.py` `LiveText`) and appends them, coalesced every 100 ms (`FLUSH_S`), to a per-block buffer in Redis: a JSON `meta` key `{block, after}` and one string key the text is APPENDed to, both with a 20 minute expiry and deleted when the block's complete message arrives and when the run ends; (2) the api's run stream polls that buffer every 150 ms (`POLL_S`, `LiveFeed`, one per connection, under `app/sse.py` `replay`'s new transient source; since issue #80 only while the run is running: Idle polling, below) and sends what the connection has not had yet as a `partial` event **without an SSE id**: `{block, after, offset, text}`; (3) the durable `text` event is written exactly as before and replaces the live text in the browser (`web/src/features/agents/live-text.ts`). **Why this and not rows or pub/sub.** Rows in `agent_events` (about ten commits a second per answer, each an fsync on the Jetson's disk, then a compaction that leaves gaps in `seq`, which is documented gapless and is the SSE id) buy nothing: the complete `text` row already is the record. Redis pub/sub writes nothing but has no memory: a tab that connects or reconnects in the middle of an answer would need a second mechanism to get the beginning, and a slow client needs a queue per connection. A buffer that only grows needs neither: a reader keeps one number (how far it has read), a new reader starts at 0, a slow reader gets everything it missed in one piece. APPEND keeps the Redis append-only file linear in the length of the answer (rewriting a snapshot on every flush would be quadratic). Redis persists that file (`compose.yml`: `--appendonly yes`, fsync every second, one writer), so the pieces of an answer are written to the Redis volume on the Jetson's disk, and they stay there after the buffer is deleted: a delete appends one more command to the file, it erases nothing that was appended before. They leave the disk only when Redis rewrites the file, which it does by itself once the file has doubled since its last rewrite and is larger than 64 MB (Redis defaults `auto-aof-rewrite-percentage 100` and `auto-aof-rewrite-min-size 64mb`; the compose command sets neither). With the traffic of this box that can be weeks or months, so the text of an answer, also of one that was cancelled and is stored nowhere else, can rest in that file for a long time (corrected in issue #80: the earlier wording, "go at its next rewrite", was true and misleading). For the agents of today the same text is in Postgres anyway, under the same access rules (the stream checks the run belongs to the session's user before any read of the buffer, which is keyed by the run's id), and the volume is readable by the same people. An agent whose text must not rest on disk outside Postgres turns its live text off (Per agent switch, below). **Resume guarantee.** A `partial` has no id, so `Last-Event-ID` is always the seq of the last stored step, and the log resumes exactly as before. For the block being written, `offset` (UTF-16 code units, what a JavaScript string counts) makes applying a partial idempotent, `text = text.slice(0, offset) + chunk`, and every new connection starts the block at offset 0 with everything written so far: whatever the moment of the cut, the browser holds a beginning of the block's text, no fragment twice and none missing, until the stored `text` step replaces it. `after` is the seq of the last step stored before the block began: the feed sends a partial only once every step up to `after` went out on that connection (no live text ahead of the steps before it), and both the feed and the browser drop a partial once a `text` step with a greater seq is there (a delta arriving after the complete message). Proved by `api/tests/agents/test_live_text.py` (`test_reconnect_at_every_event_ends_with_the_full_text_once`: a cut at every event of the stream, the buffer cleared before or after the step becomes visible, the run moving on by 0, 2 or 50 changes while the client is away; `test_reconnecting_many_times_at_random_moments`), over HTTP with real Postgres, Redis and worker by `test_live_stream.py`, for the browser's reducer by `web/src/features/agents/live-text.test.ts` (same property, in TypeScript) and end to end by `web/e2e/agents-streaming.spec.ts` (network loss in the middle of an answer). **Never live:** thinking (its deltas are not read), tool input, the credential (scrubbed like every stored event, and a tail that could be the beginning of the credential is held back until the next characters decide), and nothing of it is logged (counts and error types only). **Bounds:** the live text of a block is capped at `TEXT_MAX` (20,000 characters, where the stored event is clipped too), so a very long answer costs the worker one bounded string; a slow client costs nothing (no queue). **Cancel or failure in the middle of an answer:** a run that does not end `done` stores no answer (unchanged), so the chat shows the unfinished text until the run ends, then drops it, and the user's message says why there is no answer; the live buffer is deleted on every path. The run log may keep the cut block: on an interrupt with partial messages on, the pinned CLI prints an assistant message with the text so far before its error result (recorded, see SDK facts), and the runner stores the text of any assistant message as a `text` step. What the pinned CLI prints on an interrupt without partial messages was never recorded, so nothing is claimed about the log of an interrupted run being the same with and without live text (corrected in issue #80; the earlier wording said "exactly as it did before this change"). What is proven: for the same messages the runner stores the same events, output and chat answer with and without partial messages (`test_live_runner.py`, `test_events_and_output_are_identical_with_and_without_partial_messages` and `test_the_chat_answer_is_stored_byte_for_byte_as_without_streaming`, on the fake backend), and a run that does not end `done` stores no answer either way. **Worker killed in the middle of an answer:** its buffer stays in Redis until it expires; the next worker start fails the run (orphan recovery), the final status drops the live text in every open tab, and the stream never polls the buffer of a run that has ended. **Redis down:** the block's live text is given up (a buffer that may miss a piece is never continued), the feed backs off for 5 s, and the run and its stored steps are unaffected. **Redis hung (issue #80):** the runner waits for Redis in one place, after each complete text block (`LiveText.close_block`). One attempt takes at most 1 s (`STORE_TIMEOUT_S`); after a failed attempt the worker leaves Redis alone for 5 s, doubling at each failure in a row up to 60 s (`WRITE_BACKOFF_S`, `WRITE_BACKOFF_MAX_S`), and starts over after a success. A run therefore waits at most 1 s per attempt: about thirteen attempts in a run of ten minutes on a Redis that never answers, about 2 percent of its time, where it was up to 2 s per text block before. At the end of the run the buffer is cleared whatever the back off, with one retry (at most 2.2 s, after the final status is stored), and what still fails expires after 20 minutes. `test_live_hardening.py` holds the bound with a store that never answers. **Kill switch:** `AGENTS_LIVE_TEXT=false` (api and worker, in `.env.example` since issue #80) turns all of it off: no partial messages asked of Claude Code, nothing published, nothing relayed. **Per agent switch (issue #80):** `AgentDefinition.live_text` (default `True`). With `False` the runner asks Claude Code for no partial messages and creates no `LiveText`, and the run stream creates no `LiveFeed`: no key of such a run is ever written to Redis (checked against a real Redis with MONITOR, which reports every command it receives: `test_live_stream.py`) and its stream never reads Redis. Made for the ingestion module, whose runs read private documents. **Sub agents (issue #80):** a stream event that names a `parent_tool_use_id` is never published. The SDK documents the field as always `None` and no agent here can start a sub agent; the guard holds if either changes. **Idle polling (issue #80):** a feed reads Redis only while its run is running (the stream tells it at each read of the log, every 500 ms): never for a queued run or one that has ended (counted by Redis itself, `test_live_stream.py`). While the run is running it reads every 150 ms as before, block or no block. A slower cadence until a block appears (500 ms) was built and given up: the first characters of every block would show up to half a second late, to save about four GETs a second per open stream on a Redis that serves one box. The status is learned at each read of the log, every 500 ms, so a block that opened in the first half second of a run would arrive in one piece; Claude Code needs longer than that to start. The resume guarantee is unchanged: the property tests pass as they are, and again with a feed that is told the run's status at each read of the log (`test_live_text.py`). **What the scrub guarantees (issue #80):** the credential is replaced wherever it stands whole inside one stored value, and a value is always scrubbed whole before it is shortened (before issue #80 the `text` event, tool results, tool arguments and the final answer were cut first, so a credential lying across the cut was stored as an unredacted beginning). Not guaranteed: a credential the model cuts in two across two stored values (two text blocks, two arguments) or rewrites; nothing joins stored values to look again. In the live text a credential is caught however the deltas of one block cut it. `test_scrub_before_clip.py` holds both the guarantee and the limit.

## SDK facts (verified 2026-10-10)
Sources read: code.claude.com/docs/en/agent-sdk (overview, python reference, sessions, permissions), code.claude.com/docs/en/env-vars, github.com/anthropics/claude-agent-sdk-python (README), the PyPI release list and the source of the pinned release (sdist and wheel). Every point below was also exercised against the bundled CLI in the worker image (a scratch stack pointed at `tests/anthropic_stub.py`, no model) unless it says otherwise.
- **Package and version:** `claude-agent-sdk==0.2.163` (PyPI, released 2026-09-30; latest 0.2.165 on 2026-10-08), Python >= 3.10, in the `agents` dependency group of `api/pyproject.toml` (installed by the `worker` and `dev` image targets and locally, never by the api's `runtime` target). Depends on `anyio`, `jsonschema`, `mcp` (2.3.0 resolved). **Whenever this pin changes, run the opt-in real CLI tests** (`cd api && JOBAPP_REAL_CLI_STUB=1 uv run pytest tests/agents/test_g6_real_cli.py -s`, never run by CI, no model): the interrupt of a turn before the client is closed (`13e2a66`, `app/agents/backend.py`) and the token budget of a run (ingestion G6) are held against the real CLI by them alone, CI only holds them on test backends.
- **Claude Code CLI:** bundled in the platform wheel (`claude_agent_sdk/_bundled/claude`, a native binary, 215 MB unpacked; `manylinux_2_17_aarch64` wheel for the Jetson). 0.2.163 bundles CLI **2.1.286** (`_cli_version.py`). README: "The Claude Code CLI is automatically bundled with the package, no separate installation required"; `cli_path` points at another one. So **no Node runtime and no npm package**: the task's "Node + pinned CLI" is satisfied by the pinned SDK wheel. The SDK runs `claude -v` before each connect unless `CLAUDE_AGENT_SDK_SKIP_VERSION_CHECK` is set in the worker's own environment, and it starts that probe **without env=** (`SubprocessCLITransport._check_claude_version`), so the probe would inherit the worker's whole environment (DATABASE_URL, CREDENTIALS_KEY, SECRET_KEY...). **Turned off in the worker** (review of PR #21): the variable is set in the `worker` and `dev` image stages and by `app/worker.py`, which also drops every secret from its own environment once its settings are read. The CLI is pinned by the wheel, so the probe only compared it with itself. `tests/agents/test_sdk_spawn.py` records what the real transport spawns.
- **Calling it:** `query(prompt=..., options=ClaudeAgentOptions(...))` for one shot, or `ClaudeSDKClient(options)` with `connect()`, `query(prompt)`, `receive_response()` (ends after the ResultMessage; do not `break` out of it), `interrupt()` (streaming mode only; the messages of the interrupted turn still arrive and must be drained), `disconnect()` (terminates the CLI process). The runner uses the client, for `interrupt()`.
- **Options used** (`ClaudeAgentOptions`): `system_prompt` (str), `tools=[]` (no built-in tool at all: `--tools ""`), `allowed_tools` (auto-approved names; does NOT restrict on its own), `disallowed_tools` (bare names are removed from the model's context, even in bypassPermissions), `permission_mode="dontAsk"` (anything not pre-approved is denied, `can_use_tool` never called), `mcp_servers={"app": server}`, `strict_mcp_config=True` (no other MCP config loaded), `setting_sources=[]` (no user, project or local settings: `--setting-sources=`; the default `None` loads user and project), `model`, `max_turns` (ends with ResultMessage subtype `error_max_turns`), `effort` (low..max), `thinking={"type": "adaptive"}`, `cwd`, `env`, `hooks={"PreToolUse": [HookMatcher(matcher=None, hooks=[gate])]}` (a hook deny holds in every mode and runs before the other checks), `stderr` (callback per line). Also available, unused: `max_budget_usd` (no spending cap, SPEC decision), `resume`/`continue_conversation`/`fork_session`, `agents`, `plugins`, `skills`, `sandbox`, `session_store`. `include_partial_messages` is used since issue #33 (Partial messages, below).
- **Environment and authentication:** `options.env` is merged OVER the worker's own environment (`{**os.environ, **options.env}`, `CLAUDECODE` dropped), so the runner overrides every inherited variable outside a short allow list with "". API key: `ANTHROPIC_API_KEY` ("used instead of your subscription even if you are logged in"). Subscription: `CLAUDE_CODE_OAUTH_TOKEN` ("OAuth access token for claude.ai authentication. Alternative to /login for SDK and automated environments", produced by `claude setup-token`). `ANTHROPIC_BASE_URL` points the CLI at another API host (used only with MODEL_API_BASE_URL on test stacks). Terms, quoted from the overview: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK." This matches the A1 decision (subscription token labelled for the owner's personal use, friends use API keys).
- **In-process tools:** `@tool(name, description, input_schema)` on an `async def handler(args) -> {"content": [{"type": "text", "text": ...}], "is_error"?: bool}`; `create_sdk_mcp_server(name, version, tools)` returns an `McpSdkServerConfig` for `mcp_servers`. Arguments are validated against the JSON schema before the handler; unknown tools, invalid input and raising handlers come back to the model as error results. Claude Code names them `mcp__<server>__<tool>` (here `mcp__app__get_job`). Verified through the real CLI: the stub asked for `mcp__app__get_job`, the handler ran in the worker and its JSON came back as the tool result.
- **Forbidden tools:** with `tools=[]` a model call to Bash is answered by the CLI itself: `<tool_use_error>Error: No such tool available: Bash. Bash is disabled for this session, in subagents as well as here.</tool_use_error>` (seen live); a tool that does exist but is not allowed would reach the PreToolUse gate (the fake backend replays this case in CI).
- **Messages streamed:** `SystemMessage` (subtype `init` first, `data` holds model, tools, mcp_servers), `AssistantMessage` (`content`: TextBlock, ThinkingBlock, ToolUseBlock{id, name, input}; `model`, `usage`, `error`), `UserMessage` (ToolResultBlock{tool_use_id, content, is_error}), `ResultMessage` (last: `subtype` success | error_max_turns | error_during_execution | error_max_budget_usd | ..., `is_error`, `num_turns`, `duration_ms`, `total_cost_usd`, `usage` {input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens}, `model_usage` per model with costUSD, `result` text, `api_error_status`, `terminal_reason`, `permission_denials`), plus `StreamEvent` (partial messages, opt-in), `RateLimitEvent`, task messages. Errors: `CLINotFoundError`, `CLIConnectionError`, `ProcessError(exit_code, stderr)`, `CLIJSONDecodeError`, all `ClaudeSDKError`.
- **Partial messages (verified 2026-10-10 for issue #33).** Sources: code.claude.com/docs/en/agent-sdk/streaming-output ("Stream responses in real-time"), code.claude.com/docs/en/agent-sdk/python (`ClaudeAgentOptions.include_partial_messages`, `StreamEvent`, `AssistantMessage`), platform.claude.com/docs/en/build-with-claude/streaming (the raw events), the source of the pinned wheel (`types.py`, `_internal/message_parser.py`, `_internal/transport/subprocess_cli.py`), and a recording of the pinned SDK 0.2.163 and its bundled CLI 2.1.286 run on the Mac against a local stub of the Messages API (no model; adapted into `api/app/agents/fake_streams/partial_recorded.json`).
  - **Turning it on:** `ClaudeAgentOptions(include_partial_messages=True)` (default `False`), which adds `--include-partial-messages` to the CLI command (`subprocess_cli.py`). Docs: "This causes the SDK to yield `StreamEvent` messages containing raw API events as they arrive, in addition to the usual `AssistantMessage` and `ResultMessage`."
  - **`StreamEvent` shape** (`types.py`, python reference): `uuid: str`, `session_id: str`, `event: dict[str, Any]` ("The raw Claude API stream event"), `parent_tool_use_id: str | None` ("Always `None`. Stream events are emitted for the main session only"). The parser requires `uuid`, `session_id` and `event`. The CLI's line also carries `ttft_ms` on `message_start`, which the Python type drops. "Both contain raw Claude API events, not accumulated text. You need to extract and accumulate text deltas yourself."
  - **Events** (`event["type"]`): `message_start`, then per content block `content_block_start` (`index`, `content_block` of type `text`, `thinking` or `tool_use`), `content_block_delta` (`index`, `delta`) and `content_block_stop`, then `message_delta` (stop reason, cumulative usage) and `message_stop`. Delta types: `text_delta` {`text`}, `input_json_delta` {`partial_json`: "partial JSON strings"}, `thinking_delta` {`thinking`} and, just before the block's stop, `signature_delta` {`signature`}. The API also sends `ping` events (the recording shows the CLI does not forward them) and "new event types may be added, and your code should handle unknown event types gracefully".
  - **Thinking deltas are forwarded with their text** (recorded: `thinking_delta` events carrying the stub's thinking text, and the complete thinking block in its `AssistantMessage`). The runner therefore reads `text_delta` only, and only for the index of an open `text` block; nothing else of a `StreamEvent` is looked at. The CLI also prints `system` messages of subtype `status` and `thinking_tokens` between events (parsed as `SystemMessage`, ignored by the runner).
  - **Order relative to the complete message** (docs, "Message flow", and identical in the recording): "Claude Code emits an `AssistantMessage` as each non-empty content block completes, so a response with a text block and a tool call yields two `AssistantMessage` objects. Each one carries only its own content block, and both share the same message ID" and "each `AssistantMessage` arrives before that block's `content_block_stop` event". Recorded order: `message_start`; thinking block start, deltas, signature, **AssistantMessage(thinking)**, stop; text block start, deltas, **AssistantMessage(text)**, stop; tool_use block start, input deltas, **AssistantMessage(tool_use)**, stop; the **UserMessage** with the tool result; only then `message_delta` and `message_stop`; then the next message. So one `AssistantMessage` per content block was already true without partial messages (the recorded streams of A2 to A4 put several blocks in one message; the runner iterates blocks, so both shapes store the same events).
  - **A cut stream** (docs, "Handle a stream that's cut off"): "Before Claude Code v2.1.290, a cut stream could end the turn without `message_stop`", fixed in "the Python Agent SDK from v0.2.164". The pin is 0.2.163 (CLI 2.1.286), so nothing here waits for `message_stop` or `content_block_stop`. Recorded on the pin, `interrupt()` during a text block: the CLI prints an **AssistantMessage with the text so far**, no stop events, a user message, then `ResultMessage(subtype="error_during_execution", is_error=True, terminal_reason="aborted_streaming")`.
  - **Text deltas and unicode:** deltas are JSON strings, so the SDK hands over `str`; a delta boundary can fall anywhere between code points (recorded: an accent and an emoji ZWJ sequence cut between deltas arrive whole in the block). Offsets sent to the browser are counted in UTF-16 code units on whole code points, so a surrogate pair is never split.
  - **Known limitation in the docs:** structured output streams as unvalidated `input_json_delta` chunks (not used here).
- **Session persistence:** sessions are written under `$CLAUDE_CONFIG_DIR/projects/<encoded-cwd>/*.jsonl` (default `~/.claude`). The Python SDK has no `persistSession` option (TypeScript only); the sessions guide names `CLAUDE_CODE_SKIP_PROMPT_HISTORY=1` instead ("skip writing prompt history and session transcripts to disk"). The runner sets it and points `HOME`, `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_TMPDIR` and `TMPDIR` into the run's scratch directory, deleted at the end. Also set: `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_AUTOUPDATER`, `DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY`, `CLAUDE_CODE_DISABLE_CLAUDE_MDS`.

Far inside the 1536m limit, sweeps included. Not measured on the Jetson (no deploy before merge).
