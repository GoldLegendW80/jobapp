## Decisions of the owner (Harald, up to 2026-10-13)
1. **Gmail only, per user, through Google OAuth.** Project `jobapp-gmail-hth`, scopes `gmail.readonly` and `gmail.send` (plus `openid` and `userinfo.email` to know which address was connected). Today in Testing mode with the owner as the only test user. Published to Production, unverified, once `/privacy` and `/terms` are served (M2, issue #63).
2. **Mails are linked to postings, with a history.** A mail can propose a status change of a posting, always undoable. The agent drafts replies.
3. **One send gate.** By default the user clicks Send (Review first). A later mode, Full auto (product intent of 2026-10-10), makes a Like on an opportunity the click for forms and for emails. So every send passes one function, `mail.gate.send`, which takes an authorisation. Today the only authorisation it accepts is an explicit click by the signed in owner on that exact draft. Later it can accept a recorded Full auto authorisation without any route changing. No route, worker or tool checks a button by itself.
4. **Guardrails inside the gate, after the authorisation, so no mode can skip them:** the roles the user's never apply rules exclude (cybersecurity, for the owner), the fact check of claims against the profile, and the place where a sending limit is checked. Decisions 11 and 12 say how far each one goes.
5. **Everything free.** No paid mail service, no Pub/Sub. Polling inside Gmail's free quota.
6. **Model by credential.** `claude-opus-5-5` on a subscription credential, `claude-sonnet-5-5` on an API key (`model_by_credential`). A run carries an estimate and stops at twice that estimate (`token_budget`). The estimate and the prices come from `app/ingestion/estimate.py` and `app/ingestion/pricing.py`.
7. **Privacy.** A mail holds personal data of third parties. Stored text is kept until the user disconnects or deletes it: no expiry by age, and a storage ceiling (decision 14). Nothing of a mail's content goes into logs, errors, job arguments or arq results. Backups keep 7 nights. Isolation between users is proven by a test in every task. The refresh token is encrypted with the existing credentials key and revoked at Google on disconnect.
8. **No CI.** Each task's own tests are its evidence (commands and output under `tasks/evidence/mail-m<n>/`). One full local check gates a deploy (`ops/local-check.sh`, PR #121).
9. **Never a real Gmail account in a test.** Tests use `e2e-*@example.org` accounts and a fake Google at the HTTP boundary (M1). The owner does one manual check with his own account per checkpoint stage, listed as a human step.

**The owner's answers to the five questions of the first version, 2026-10-13** (issue #62). They replace the planner's recommendations.

10. **A change concluded by the model may apply by itself**, above a confidence threshold, as a rule verdict does, always undoable. Below the threshold it is a proposal. The owner accepts that a crafted mail could flip a status: the undo, the job's history and the proposal row are the safety net. This plan adds the condition the review asked for (B2), stated once under "The binding rule": no verdict, of a rule or of the model, applies by itself unless the mail is bound to the posting. A status change never triggers a send by itself.
11. **No sending limit.** No daily limit and no cap per company as product rules. The gate and its audit stay, and the gate keeps the place where a limit is checked: two settings whose default is none. Gmail's own quota is the only ceiling, and the gate handles its refusal cleanly.
12. **The cybersecurity rule stops only what the AI drafts or sends by itself**, and any future Full auto send. A reply the user wrote or edited, and clicked Send on, goes out.
13. **Consent first.** One recorded consent before the assistant reads any mail. Without it the app syncs and links by plain rules: no model, no draft.
14. **A storage ceiling** (the planner's figure, which stands until the owner says otherwise): 20,000 stored messages or 300 MB of mail text per user, and a way to delete a thread from the app. At the ceiling, unlinked threads stop being stored and the Gmail card says so.

**Defaults decided by the planner (2026-10-13)**, which the owner may change.
- A message is fetched from Gmail as `format=full` (Google has already split the MIME tree), never `format=raw`: attachment bytes are then never downloaded during a sync.
- The time of a message is Gmail's `internalDate` (when Gmail received it), never the `Date` header, which the sender writes.
- A message labelled `SPAM` or `TRASH` is never stored, and a stored one that gains such a label or is deleted in Gmail is deleted from the app at the next sync.
- A sender is authenticated only by Gmail's own result, never by what the mail says of itself. "The binding rule" names the header that is read and what a pass is.
- Every setting of the module is added to `config.py` and `.env.example` by M1, so no later task edits those files: `MAIL_AUTO_APPLY_CONFIDENCE` (0.90), `MAIL_SEND_DAILY_LIMIT` and `MAIL_SEND_COMPANY_DAILY_LIMIT` (none), `MAIL_AUTO_RUNS_PER_DAY` (100, the spec's figure), `MAIL_STORAGE_MAX_MESSAGES` (20,000), `MAIL_STORAGE_MAX_BYTES` (300 MB), `MAIL_SENDS_KEEP_DAYS` (365), beside the three Google addresses.
- `gmail.readonly` is required to connect. `gmail.send` is optional: a user who unticks it at Google gets everything but Send, and the gate answers `no_send_scope`.
- The drafting conversation is the list of instructions the user typed, kept in `mail_draft_instructions`. It is not an agents chat thread: a run that reads mail is `private_io`, so its answer is never stored or shown, and the result the user sees is the draft itself.
- The message frame is `sandbox="allow-popups allow-popups-to-escape-sandbox"` (no script, no form, no same origin, no top navigation), not `sandbox=""`: with an empty sandbox a link in a mail cannot open at all.
- The undo route keeps the spec's path. Job events keep the keys the jobs module really writes: `{from, to, via}`, with `via: "mail"` and `via: "mail_undo"`.

## Open questions for the owner
Five questions are still open. The work starts on the recommended default of each. None blocks a task that can start today.
1. **A mail of an applicant tracking system on an application made through a web form.** Under the binding rule such a mail, in a thread the user never wrote in, is a suggestion he accepts in one click, for the link and for the status: the system's domain is shared by all its customers and binds nothing alone. This is the price of closing B2, and it touches the most common confirmation and rejection mails. **Recommended default: keep the rule as written.** Checkpoint stage B counts, on the owner's mailbox, how many real status mails stay suggestions. The owner then says whether a link he accepted by hand should bind the later mail of that same thread from that same authenticated address.
2. **The daily cap of automatic model runs.** The spec says 100 per user per day, and the owner's answer on limits spoke of sends only. **Recommended default:** keep 100, as the setting `MAIL_AUTO_RUNS_PER_DAY`.
3. **How long the send log lives.** `mail_sends` holds no address and no text and survives a disconnect. **Recommended default:** 365 days, then deleted by the daily tick (`MAIL_SENDS_KEEP_DAYS`). `/privacy` states the figure.
4. **A disabled app account.** **Recommended default:** the sync stops, nothing is purged, and the stored mail stays until the account is enabled again or deleted. `/privacy` says so.
5. **Deleting an account.** The app has no deletion route. **Recommended default:** the administrator deletes an account on request with the command of M22, and `/privacy` says to write to him. A button for the user himself is a later task of the identity module.

## Architecture decisions

### Google at the HTTP boundary
- **One client, `api/app/mail/google.py`** (M1): the token exchange, the refresh, the revocation, `userinfo`, and the Gmail read calls (`getProfile`, `messages.list`, `messages.get`, `history.list`, `attachments.get`). It has no send function. The only code that builds a `messages.send` request is one private function of `gate.py` (M12).
- **Three settings**, refused when `APP_ENV` is production, as `MODEL_API_BASE_URL` is: `GOOGLE_AUTH_URL` (where the browser is sent), `GOOGLE_TOKEN_BASE_URL` and `GOOGLE_API_BASE_URL` (what the server calls). Unset, the real Google addresses apply.
- **The fake, `api/tests/mail/fake_gmail.py`** (M1): one implementation, run in process by pytest and as the service `gmailstub` by `tests/gmail-stub.compose.yml`, the way `fake_ats.py` and `tests/anthropic_stub.py` are. It serves a consent page (an account field, one checkbox per scope, Allow, Deny), the token, revoke and userinfo endpoints, and the Gmail calls above plus `messages.send`. A control API (`/__control/...`) seeds mailboxes from JSON fixtures, makes the next calls of an endpoint fail (429 with `Retry-After`, 500, 401, `invalid_grant`, an expired history id), revokes a grant, and returns what was sent and every call received. Fixtures are written by hand to look like real ATS mail; no real mail is ever copied in.
- **Access tokens live in memory only**, per process, until they expire. A 401 refreshes once. `invalid_grant` sets `needs_reconnect`.
- **Backoff.** 429, 403 with a rate limit reason, and 5xx: up to three tries inside a job (1 s, 2 s, 4 s with jitter, `Retry-After` honoured), then `mail_accounts.backoff_until` doubles from 5 minutes up to 6 hours and resets on the first success. Errors are stored as a code of a fixed list (`quota`, `google_down`, `revoked`, `scope_missing`, `history_expired`, `too_large`), never as Google's message.
- **Sizes, for a Jetson whose api has 512 MB.** A cap per call, not one figure. A `messages.get` answer is refused over 8 MB, and such a message is then stored from `format=metadata` with its snippet, `truncated` set and the code `too_large`: never dropped. Every other JSON answer is refused over 2 MB. `attachments.get` may answer up to 36 MB, because a 25 MB file comes back as base64url inside JSON (M1 verifies the figure against Google's documentation), and that answer is read as a stream and decoded in chunks of 64 KB, never held whole. Downloads are limited for the whole process (two at once) as well as per user (one).

### A mail into stored text
- **The worker walks the tree Google returns, with the standard library only**: at most 20 levels and 200 parts, the first `text/plain` and the first `text/html` that are not attachments, each decoded from base64url and from its declared charset (a fixed list; anything else is read as UTF-8 with replacement), each capped at 500 KB with `truncated` set. Every other part with a file name is listed as an attachment (`part_id`, name, type, size): its bytes are not fetched.
- **HTML goes through the parser service: yes.** One new kind, `mail_html`, handled by `api/app/ingestion/sandbox/mail_html.py`: `nh3` sanitises against an allow list and a small standard library walker extracts the text. The reason is the rule of the house: content written by a stranger is parsed by a library only in the process that holds no key, no token, no database and no network, and the syncing worker holds a Gmail access token. `nh3` joins the worker image; the parser runs the same image. One message per parser job. M3 measures the time per message on the Jetson and, above 300 ms, lets one job carry up to 10 messages.
- **The allow list:** `p br div span a b strong i em u ul ol li blockquote pre code table thead tbody tr td th h1 h2 h3 h4 hr img`. `a` keeps `href` with the schemes `http`, `https` and `mailto`. `img` keeps `alt`, `width`, `height`, and its `http` or `https` source moved to `data-src`, so no remote image loads until "Show images". No `style`, `class`, `id`, `form`, `svg`, `math`, `base`, `meta`, `link`, `cid:` or `data:` address.
- **Headers are parsed in the worker by pure functions** (`mail/parse.py`, with `mail/auth.py` for A of the binding rule): addresses with `email.headerregistry` and a strict check, `Reply-To`, `Message-ID`, `References`. Two `From` headers, a `From` with several addresses, or a display name that contains an address of another domain set `suspicious`, and a suspicious message is never trusted.
- **Display:** the page builds the frame's `srcdoc` from the stored HTML with a CSP `<meta>` (`default-src 'none'; img-src 'none'`, or `img-src https:` after "Show images" for that message), links with `rel="noopener noreferrer nofollow"` and `target="_blank"`. Plain text is the fallback and what every agent reads.

### Sync
- **A queue of its own**, `jobapp:mail`, concurrency 1, in the existing worker (no new service in production). A job's only argument is a user id. The job id is `mail_sync:<user_id>`, so one sync runs per user, and the function sets `keep_result=0` as the ingestion functions do: arq refuses a job id whose result is still stored, and the next tick would be dropped. The counts of a run are written to `mail_accounts.sync_counts`, never to Redis. A second function, `mail_pipeline(user_id)`, reruns the steps below without a sync; a step may queue it with a delay through the helper M7 adds to `api/app/queue.py`. The tick skips an account that is disabled, disconnecting or in backoff.
- **First sync:** the job related query of the spec, built from the user's postings (hosts of posting addresses that are not an ATS or a job board, the ATS domains, the keywords in French and English), split into queries under 1,500 characters, `newer_than:180d`, at most 5,000 message ids. It runs as a chain of bounded jobs (100 messages each, the page token in `mail_accounts.sync_cursor`), so progress shows and a restart resumes. It links threads and creates pending suggestions; it never applies a status change.
- **Incremental sync:** a cron every minute queues the connected users whose last sync is older than 5 minutes and whose backoff has passed. A run reads `history.list` from the stored history id, at most 200 new messages and 60 s. A new message is first fetched as `format=metadata`. It is stored in full only when its thread is already stored, or when it passes the local filter. That filter is narrower than Gmail's search, on purpose: it reads `From`, `To`, `Cc`, `Subject` and Gmail's snippet, never the body, so a mail whose only sign of a job lies deep in its body is not stored. A thread already stored always gets its new messages. An expired history id starts a bounded resync: the first sync's query since the last sync minus one day.
- **`before_connection` has one definition, in `store.py`:** `received_at <= connected_at`. No sync sets it by any other rule, so a mail that arrives while the first sync runs gets the same value whichever job stores it.
- **After storing**, `mail/pipeline.py` (M7) runs the steps that exist, in this fixed order: `linking`, `classifying`, `needs_reply`, `reconciling`, `assisting`, `drafting`. A step is a module of that list, skipped while its file is not there yet. "Who owns which shared file" names the task behind each line.

### Locks
- **Two transaction advisory locks per user, defined in `mail/locks.py` (M4)** the way `ingestion.documents.lock_user` is: `pg_advisory_xact_lock(hashtextextended(key, 0))`. `locks.lock_sync(db, user_id)`, key `mail-sync:<user_id>`: taken by the sync for each batch it stores, by Disconnect, by the deletion of one thread and by the account deletion of M22. `locks.lock_send(db, user_id)`, key `mail-send:<user_id>`: taken by the gate for its decision and by Disconnect. Both are released at the commit; there is no session lock in this module.
- **No lock is held across a call to Gmail, to the parser or to a model.** A sync of up to 60 s is a series of short transactions: it reads a page from Gmail with no transaction open, then opens one, takes `lock_sync`, reads the account row again, stores the batch (100 messages at most) and commits. M7 measures the longest hold on the Jetson; it must stay under 2 s.
- **Disconnect never waits for a whole sync.** It is three steps. (1) One short transaction under `lock_sync` then `lock_send` sets `mail_accounts.disconnecting_at` and commits: it waits for one batch at most. (2) The revocation at Google, with no transaction open. (3) One transaction under both locks purges the mail and deletes the account row. A sync checks under `lock_sync`, at every batch, that the account row exists, that `disconnecting_at` is empty and that `connected_at` is the one it started with; otherwise it stores nothing and ends. The gate makes the same check under `lock_send` and refuses with `not_connected`. A reconnect is refused while the flag is set. If the process dies between (1) and (3), the tick finishes the disconnect of any account whose flag is older than 60 s.
- **Waits are bounded.** Every transaction of this module that takes a lock sets `lock_timeout` to 5 s (`SET LOCAL`), well under the 15 s `statement_timeout` of `api/app/db.py`. A wait that runs out answers 409 "Busy, try again." in a route and ends the batch in a job. Never a hung request.
- **Lock order, for every path of this module, consistent with the jobs, agents and ingestion modules:** (1) `lock_sync`; (2) `lock_send`; (3) the `mail_accounts` row; (4) the job row, through `jobs.service.lock_job`, or `lock_jobs` in id order; (5) `mail_threads` rows in id order; (6) the `mail_drafts` row; (7) the user's advisory run lock of `runs.create_run`; (8) the `agent_runs` row; (9) `proposals` rows in id order, last as everywhere ("the job first, then the proposal", issue #25). A path takes a subset, in this order. Mail never takes the chat thread row, the `profiles` row or an ingestion row. A registered proposal kind names the rows to lock before the proposal row (the `lock` argument of M11a), so an accept from the proposals page keeps the order. M4, M7, M11b, M12 and M13 each carry a test of the order on the paths they add.

### Automatic runs
- **They share the user's four slots, with no priority.** An automatic mail run is created through `runs.create_run` like any run, so it counts toward `runs.ACTIVE_PER_USER = 4`. The runner, the queue and the worker have no priority, and this plan invents none. The whole rule: the mail module keeps at most one automatic run queued or running per user, counted on `agent_runs` for the mail agents, so three slots always remain for the user. With no free slot (`ActiveRunsError`) the thread waits and is tried at the next pass of the pipeline. Nothing is queued on the side, so nothing piles up.
- **A run the user asks for** (an instruction in the draft chat, "Check against my profile") is an ordinary run: it takes a slot, or answers the existing 429 sentence.
- **The batch after the first sync** has a table, `mail_assist_batches` (0013, M4): one open batch per user (a partial unique index), its estimate, the tokens spent, the count of threads done, and the status `running`, `paused`, `done` or `cancelled`. The step `assisting` (M17) advances it one run at a time and pauses it at twice its estimate.
- **The daily cap** `MAIL_AUTO_RUNS_PER_DAY` counts the automatic runs of the mail agents on `agent_runs` (open question 2).
- **What starts them.** The pipeline runs after every sync, and `mail_pipeline(user_id)` reruns it without a sync. A step that has more to do queues that function again with a delay of 15 s, so a batch advances as its runs end, with no watcher.

### The binding rule: when a change applies by itself
One rule, stated here and nowhere else. **Owner: M5** (`mail/binding.py`), on the authentication result that M3 computes and stores. **Users:** M6 (`may_apply_alone` takes its result), M11b (links), M13 (status changes), M17 (the model's verdicts), M19 (drafts prepared without being asked) and M8 (recipients).

**A link or a status change applies by itself only when the mail is bound to the posting, and bound means both A and B below.** The source of the verdict, a rule or the model, changes nothing to that.

- **A. Gmail authenticated the visible sender** (M3, `mail/auth.py`, stored as `mail_messages.trusted` and `from_domain`). The header read is the topmost `Authentication-Results` header of the message as Gmail returns it, and it counts only if three things hold: its server name is exactly `mx.google.com`; the nearest `Received` header above it was written `by mx.google.com`, which shows that Gmail took this mail by SMTP itself; the message has no `X-Gmail-Fetch-Info` header, the mark of a mail Gmail fetched from another mailbox. Every other `Authentication-Results` or `ARC-Authentication-Results` header is the mail's own claim and is never read. **A pass** is, in that header, `dmarc=pass` with a `header.from` that has the registrable domain of the visible `From`, or a `dkim=pass` whose signing domain (`header.i` or `header.d`) has that same registrable domain. `spf=pass` alone is never a pass: it speaks of the envelope, not of `From`. The message must carry one `From` header with one address and must not be `suspicious`. The registrable domain comes from `mail/domains.py` (M3), a bundled snapshot of the public suffix list with its date, never a network call. A header shape the parser does not recognise is not a pass.
- **B. That domain is bound to the posting** (M5, `binding.bind(message, thread, posting, confirmed, sends) -> Binding`), on one of four bases, named in the result:
  - `posting_host`: it is the registrable domain of the host of the posting's address, when that host is the company's own, that is, in none of the lists of `mail/hosts.py` (applicant tracking systems, job boards, shared hosting such as `notion.site` or `github.io`, public mailboxes such as `gmail.com`).
  - `user_wrote`: the user himself already sent a mail in this thread, before this message, to an address of that domain. For a public mailbox domain the whole address must be the one he wrote to.
  - `user_confirmed`: the user confirmed that domain for that company (`mail_confirmed_domains`, one explicit click on a message in the thread view, M11b and M14). A domain of the lists of `hosts.py` cannot be confirmed.
  - `ats_reference`: it is a sending domain of an applicant tracking system listed in `hosts.py`, and the message answers a mail of the user: its `In-Reply-To` or `References` names a `Message-ID` the app set on a send (`mail_sends.message_id_header`), or Gmail puts it in the thread of a stored message the user sent earlier. The system's domain alone binds nothing, since every customer of that system sends from it.
- **A reference id that the mail carries is never enough.** The posting's id in a body or a subject is a signal for a suggestion, and it may decide between two postings of one bound company. Alone it makes the thread `ambiguous` at most.
- **Everything else is a proposal the user accepts in one click**, whatever the confidence: an unauthenticated mail, an authenticated stranger, a system mail on an application made through a web form (open question 1).
- **The threshold** is the setting `MAIL_AUTO_APPLY_CONFIDENCE`, default 0.90. A verdict applies by itself when the mail is bound and the verdict's confidence reaches it. A template rule states 0.95. The model states no number: its tools take `sure` as `high`, `medium` or `low`, which code maps to 0.95, 0.75 and 0.50. With the setting at 1.0 nothing applies by itself.
- **Three things hold whatever the verdict.** A status change never starts a send: no code path leads from a link, a label or a status change to the gate. The undo restores the previous status, is written in the job's history (`via: "mail_undo"`) and marks the proposal `undone`. The first sync applies nothing.
- **One constructor.** A `Binding` (the type is in `mail/types.py`, M3) is built only by `binding.bind`. `transitions.may_apply_alone` and the linking step take one as a required argument. A test of M13 walks `api/app` and fails when another module builds a `Binding`, or creates a `mail_link` or `mail_status` proposal as accepted without one.
- **Residual risk, accepted by the owner (decision 10):** a mail from the company's own authenticated domain, or from an address the user wrote to, can state a false outcome. It moves one of the user's postings along an allowed transition, visibly, with its source mail and an Undo, and it sends nothing.

### Changes a mail may cause
- **Linking, rules first** (`link_rules.py`, pure): signals with weights, combined as one minus the product of one minus each weight. A posting's reference id found in the body (0.9). The trusted sender's domain equal to the host of the posting's address when that host is the company's own (0.7). The company name in the subject or in the trusted sender's display name (0.5). The title in the subject (0.4). A trusted ATS sender, counted only with another signal (0.1). Postings in `found` or `skipped` score times 0.8. One posting wins at 0.80 or more with a lead of 0.25. The domain and display name signals fire only for a sender Gmail authenticated (A of the binding rule). The score says which posting the rules name. Whether that link applies by itself is the binding rule's answer, never the score's. These are starting values: M5 records a confusion table on the fixtures, checkpoint stage B on the owner's mailbox.
- **Classifying, rules first** (`classify_rules.py`, pure): the confirmation, rejection, invitation, assessment and offer templates of Ashby, Greenhouse, Lever, Workday, SmartRecruiters, Teamtailor and Welcome to the Jungle, in French and English. A rule names itself in its verdict.
- **What applies by itself:** what the binding rule allows, and nothing else. A link: the rules or the model name one posting, and the thread's newest inbound message is bound to that posting. A status change: a verdict at the threshold, on an inbound message bound to the thread's posting, received after the account was connected, dated after the posting's last status change, for a transition of the spec's table. How the thread was linked is not a condition: the binding is checked on the message itself. Each is recorded as a proposal (`mail_link` or `mail_status`) created `accepted` by the system, with the basis of the binding in its payload, and for a status a job event `{from, to, via: "mail", message_id, proposal_id}` and a row of `mail_classifications`. Everything else is a pending proposal, or nothing.
- **A thread linked later** (by hand, or by accepting a proposal) holds messages that were never classified. Linking classifies them, as suggestions only: none applies by itself.
- **The model second** (M17): only for threads the rules left ambiguous and messages they could not label, only with a credential and the consent (decision 13), each run inside its budget, the daily cap and the run slots ("Automatic runs"). Its tools take an index into candidates that code computed, a label of the fixed list and `sure`, and return constants. Its verdict applies by itself only under the binding rule, and is a pending proposal otherwise (decision 10).
- **Proposal kinds are registered, not hard coded:** M11a adds `proposals.register_kind(kind, target, lock, apply, undo)` to `api/app/agents/proposals.py` once; `mail_link` (target `mail_thread`, M11b) and `mail_status` (target `job`, M13) then live in `api/app/mail/`. Payloads hold ids, labels, statuses, rule names, scores and the basis of the binding: never a subject, an address or a body.

### Drafting and the one gate
- **Recipients are computed by code** (`recipients.py`, M8), never by an agent. **Safe addresses** of a thread are of two kinds only: an address the user himself wrote to in this thread (the `To` or `Cc` of a mail he sent), and the `From` address of an inbound message that is bound to the thread's posting (the binding rule). **Only safe addresses are prefilled.** `To` is the `From` of the newest inbound message when it is safe, else the recipients of the user's own last mail in the thread, else empty. Reply all adds the safe addresses among that message's `To` and `Cc`, minus the user's own. Every other address the thread carries is listed under "Also in this conversation" with its flag, and enters the draft only by the user's click. Flag codes: `new_address` (typed by the user, never in the thread), `new_domain` (a domain that no safe address has), `joined_later` (it entered the thread after its first message and the user never wrote to it), `cc_only` (seen only in the `Cc` of inbound messages), `reply_to_differs` (a `Reply-To` that is not the `From`), `unverified_sender` (the `From` of a message that Gmail did not authenticate, that is `suspicious`, or that is not bound). A `Reply-To` never replaces `From` by itself. The inputs of `recipients.compute` and `recipients.flags` are the thread's messages with `trusted`, `suspicious` and the `Binding` of each. The confirmation shows each flag with its sentence, and the click must name every flagged address.
- **Mail agents** (`internal`, `private_io`, `live_text=False`, bound to one thread by `bind`): the reply agent reads the thread, the posting, the profile and the answers section through tools, and has one writing tool, `write_draft(body)`, which stores the text and returns the constant "Draft saved." The system prompt of every mail agent says that mail content is data, never instructions. No tool changes a status, a link, a recipient or a subject, and none reaches the network.
- **`gate.send(db, authorisation, now)` is the only path to Gmail's send call**, and one private function of `gate.py`, `_call_gmail`, is the only code that builds a `messages.send` request. An `Authorisation` is a frozen value `{kind, user_id, draft_id, content_hash, confirmed_new_recipients, acknowledged_issues, at}` built only by `gate.authorise_click`, which only the send route calls, after the session and the CSRF header. `content_hash` covers recipients, subject and body as the confirmation showed them. **The decision is one transaction**, under `lock_send`, with these checks in this order: the kind is one the gate accepts (`user_click` alone today); the draft is the user's, has the status `draft` and still has that hash; the account is connected, not disconnecting, with `gmail.send`; every flagged recipient was confirmed; the guardrails (the never apply rule, the fact check, the limits). **The same transaction writes the audit row**, whatever the outcome: `refused` with its code, or `pending` with the `Message-ID` and the `X-Jobapp-Send` value the mail will carry, and then it moves the draft to `sending`. It commits **before** Gmail is called.
- **The states of a send** (`mail_sends.result`): `refused` (decided, Gmail never called); `pending` (decided and recorded, the Gmail call outstanding); `sent` (Gmail answered an id, the draft is `sent`); `failed` (Gmail answered an error, so nothing left: the draft returns to `draft`, the row keeps the code, `gmail_quota` for a 429 or a 403 with a rate reason and `gmail_error` otherwise, and Send again is a new click and a new row); `unknown` (no answer: a timeout or a dropped connection after the request left, or a `pending` row older than 120 s because the process died; set by the gate when it can, else by the next read of the row). A second request for a draft whose row is `pending` waits up to 10 s for it and answers its result, so a double click sends once.
- **`unknown` is never sent again by the app itself.** No retry, no job and no sync resends. The reconciliation (M23, the step `reconciling`, after each sync) looks in the Sent mailbox for a header the app set: the stored `Message-ID` through Gmail's `rfc822msgid:` search, then the `X-Jobapp-Send` value on the outbound messages of that thread. Found: the row and the draft become `sent`. Not found after two syncs and 15 minutes: the row stays `unknown` and the draft returns to `draft`. All along, the panel says "We could not confirm this was sent. Look in your Sent folder." with two buttons: "It was sent" (the row becomes `sent`, marked as resolved by the user) and "Send again" (a new click, a new authorisation, a new row). Any other outbound message of the thread, such as a reply the user wrote in Gmail itself, matches nothing.
- **Limits** (decision 11). `limits.check(db, user_id, company_key, now)` runs inside the decision, under `lock_send`, and counts the rows `pending`, `sent` and `unknown` of the rolling 24 hours. So two clicks cannot both take the last slot, and a send that was never confirmed still counts. The two settings default to none, and the function then returns at once: no product limit exists today. Gmail's own quota is the ceiling. Its refusal is the state `failed` with `gmail_quota`, the sentence "Gmail refused this send: its sending quota is reached. Try again later, or send from Gmail.", and no retry.
- **The never apply rule** (`guardrails.py`, M12). The cybersecurity rule of decision 4 is the owner's own rule of this kind. Its input is what the jobs module already has: the user's `never_apply` rules (`sweep.never_apply_rules` on `sweep.load_search(db, user_id)`, matched with `sweep.term_matcher` on the posting's title, exactly as the sweep excludes a role), and a posting whose history holds the sweep's `never_apply` event. No tag, no manual mark, no new column. It stops what the AI does by itself (decision 12): the reply agent is never started on such a posting, by the pipeline or by an instruction, and the panel says why; the gate refuses, with `never_apply_role`, text the agent wrote and any authorisation that is not a user's click. A reply the user wrote or edited, and clicked Send on, goes out.
- **Fact check: who runs it, and when.** The rules are `factcheck_rules.check` (M9, pure, under 200 ms): every number, year, amount, employer, school and title in the draft must be found in the profile, the answers section, the thread or the user's own instructions, and an address or a link that comes from the mail and not from the profile is an issue. `factcheck.run(db, draft)` (M12) calls them on the draft's sources and stores the result on the draft for its `content_hash`, for display. It runs at three moments: after every `write_draft` of the agent, before the draft is shown (M19); on `POST /api/mail/drafts/{id}/check`, which the panel calls after a save and before it opens the confirmation (M12, M18); and **inside the gate, every time, on the exact text it hashes**, whatever is stored. So no draft reaches Gmail without the rules having run on it, and `not_run` does not exist for the rules: it exists only for the check by model (M20).
- **What an issue does depends on whose words they are**, the same line as decision 12. On **text the agent wrote** (`written_by = agent` for this hash), an issue of the rules or of the check by model refuses the send with `fact_check` until the text changes. On **the user's own text** (he wrote it, or edited what the agent wrote), an issue is a warning: the confirmation lists it with a checkbox, the click carries `acknowledged_issues`, and the gate refuses only an issue the click did not acknowledge. A check by model that did not run never blocks a user's click and is shown as "Not checked by the assistant". An authorisation other than a click will need no issue at all and a check by model that `passed`.

### Privacy and isolation
- Every query filters on the session's user id. Another user's thread, message, draft or attachment answers the same 404 as a missing one. `Cache-Control: no-store` on every route. The schema holds the same line, down to the posting: messages, classifications and drafts carry the composite key `(thread_id, user_id)`, instructions carry `(draft_id, user_id)`, and since 0013 gives `jobs` a `unique(id, user_id)`, a thread points at its posting through `(posting_id, user_id)`. So no row of this module can point at another user's thread, draft or posting, even by a bug.
- **Logs:** the module logs through `mail/log.py` (M1): a fixed list of event names with ids, counts and codes. A canary helper (`api/tests/mail/canary.py`, M1) plants a marker in the subject, body, sender name, attachment name and draft of a fixture, then searches the container logs, Redis (job arguments, arq results, live buffers), `agent_events`, `agent_runs.output` and the api's error answers. Every task runs it over what it adds; M21 runs it over the whole module.
- **What the app reads, in the words `/privacy` uses.** M2's sentence and M7's code must agree, and M21 tests one against the other. For every new mail, the incremental sync reads the sender, the recipients, the subject and Gmail's short preview, to decide whether the mail concerns a posting. It fetches and stores the whole mail only when it does. The headers of a mail that does not are neither stored nor logged. The first sync asks Gmail to search the last 180 days with the terms listed on `/privacy`; the app sees only the matches and stores them, and some matches are not about a job (the word "interview" in a newsletter).
- **Disconnect** follows the three steps of "Locks": the flag, the revocation at Google, then one transaction that deletes the account, threads, messages, classifications, drafts, instructions, confirmed domains and assist batches; `mail_link` proposals; the payload of `mail_status` proposals reduced to `{from, to, mail_deleted: true}`; `message_id` removed from job events, which keep `{from, to, via, mail_deleted: true}`. **What stays after a disconnect, and for how long:** the send log `mail_sends`, with its `message_id_header` emptied, so with no address and no text, for `MAIL_SENDS_KEEP_DAYS` (365 days, open question 3); and, in the history of each posting, the fact that a status changed because of a mail, for as long as the posting is in the app. If Google cannot be reached the local deletion still happens and the page tells the user to remove the access at Google.
- **Deleting an account.** No route deletes an app account today. M22 adds the administrator's command, which revokes at Google and deletes the user row; every mail table cascades from it. `/privacy` tells the user to write to the administrator. M4 proves the cascade by deleting the user row in a test.
- **A disabled account** is skipped by the tick. Nothing is purged, and the stored mail stays until the account is enabled again or deleted (open question 4).
- **Backups** hold deleted mail for at most 7 nights (platform T10, already merged). `/privacy` says so.

## Rules every task follows
- **Isolation:** every task has at least one test with two users, A and B, each with a mailbox that mentions the same company, proving that B's ids answer 404 to A and that nothing of B appears in A's lists, proposals, events, drafts or agent prompts. The block names the case that matters most for it.

- **Binding and locks:** no task applies a link or a status change by itself except through `binding.bind` and `may_apply_alone`, and a task that takes a lock tests the order of "Locks" on the paths it adds.

- **Merge rule:** CONTRIBUTING's, with the local check of PR #121 in place of CI: a review verdict on the head commit, the task's tests green, a merge commit, never a squash. The orchestrator merges, never the task's agent.
