## What the guard does, and what remains unknown

`SPEC-browser.md:41` and `S/browser/browserd/chromium.py:529-590` define:

- cgroup v2: `W=max(0,memory.current-inactive_file)`; cgroup v1: usage minus `total_inactive_file`.
- Missing, invalid or unreadable stat data conservatively counts all usage. An unavailable/unlimited accounting source returns no figure. Active file pages remain counted.
- Close the newest tab when `W*100 >= limit*pct`. At limit `1073741824` and pct 90, the threshold is 921.6 MiB. The logged value is `W >> 20`, so 1006 represents a working-set read from 1054867456 through 1055916031 bytes, about 98.24% to 98.34% of the cap. It is not Chrome RSS/PSS.
- The watcher sleeps two seconds, checks CDP, then checks memory (`chromium.py:460-474`); it starts after CDP attachment (`:402-422`). If only one page exists, it opens a blank replacement before closing the victim. Compose retains 1024m memory and memswap limits (`compose.yml:397-398`), default/configured guard 90, sandbox and other containment.

This formula agrees with [Docker's documented CLI cache subtraction](https://docs.docker.com/reference/cli/docker/container/stats/). The retained metadata reader logged active/inactive file values but omitted `anon`, `file`, `shmem`, kernel/slab and mapped-file totals. It also did not record the raw fields used by the actual guard decision. `memory()` reads current/max and stat sequentially, so these are not an atomic snapshot. We cannot retrospectively split the 1006 MiB value or exclude read skew/fallback.

The arithmetic remainder `current-active_file-inactive_file` is approximately 90 MiB at both endpoints. Most endpoint growth is therefore explained by file-list counters. This is evidence for a file-charge investigation, not a measurement of guard-time anonymous memory or a proof of a false positive. A fresh cgroup can fault shared image files itself. Shared pages can be charged to one cgroup while used by others; reclaim-list state is not a process-residency measurement. These are [kernel accounting properties](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-ownership), not proof of another container causing this run.
