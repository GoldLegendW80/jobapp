# Task G6, what the real Claude Code CLI does around a token budget
# 2026-10-10, Mac arm64, claude-agent-sdk 0.2.163, bundled CLI 2.1.286 (the darwin build of the
# pinned wheel), Python 3.12.11. No model, no credential: the CLI talks to a stub of the Messages
# API in the same process. Two sources:
#   budget_probe.py, budget_probe.json   the SDK client alone, six ways of stopping a loop
#   api/tests/agents/test_g6_real_cli.py the product's runner (runner.execute, SdkBackend) on a
#                                        real Postgres, opt-in with JOBAPP_REAL_CLI_STUB=1

## The stub
Every request is answered with a text block and a tool call (a loop of 8 tool calls, then a last
answer), and reports the same usage: input 1,000, cache writes 200, cache reads 300, output 1 at
message_start and 50 at message_delta.

## A15: usage on assistant messages (budget_probe.json, mode observe; the first test)
- Every assistant message carries `usage` and the id of its API message. Claude Code prints one
  assistant message per content block: the text block and the tool call of one answer are two
  messages with the same id and the same usage.
- The input side is complete on each of them (1,000, 200, 300). `output_tokens` is 1: the value
  of message_start. The 50 of message_delta never appear on an assistant message, only in the
  result message, whose usage is cumulative: after 9 requests 9,000, 1,800, 2,700 and 450.
- `stop_reason` is null on every assistant message.
- The product's runner over the same loop: 9 requests, its own count 13,500 input and 9 output,
  the run recorded 13,500 and 450 from the result message.
- The only other HTTP call of a run: one HEAD /api/hello when the CLI starts.

## The hook and its message
- In every run of the probe (122 gate calls) the assistant message of a tool call had reached the
  SDK's user before the PreToolUse hook of that call was asked. The SDK does not promise it: its
  reader hands a hook request to a task of its own and puts messages in a buffer of 100. The
  runner's gate therefore waits until the message of its call is counted.
- The hook's `tool_use_id` is the id of the tool use block.

## Requests after the one whose usage reached the budget (budget 4,000, reached by request 3)
mode             runs  requests after  tools run  how the run ended
stop              10         0             2      result success, terminal reason hook_stopped
interrupt         10         0             2      result error_during_execution, aborted_tools
hold              10         0             2      result error_during_execution, aborted_tools
close              3         6             2      no result, the client was closed
interrupt_close    3         0             2      no result, the client was closed
hold_close         3         6             2      no result, the client was closed

- stop: the gate answers the tool call of request 3 with `continue: false`. The tool does not
  run, its result is the error "PreToolUse:mcp__app__ping hook error: The run reached its token
  budget.", and the CLI ends the turn itself 3 ms later. Its result says success with the
  terminal reason hook_stopped, an empty result text, and cumulative usage (3,000, 600, 900,
  150). This is what the runner does.
- interrupt: `ClaudeSDKClient.interrupt()` sent when the message of request 3 arrives. The CLI
  rejects the tool use and ends the turn 3 to 4 ms later (aborted_tools), with the same
  cumulative usage. No request followed in 10 runs, but nothing orders the interrupt against the
  tool call: it is the backstop, not the mechanism.
- hold: the same interrupt while the hook never answers. The SDK cancels the held hook
  (control_cancel_request) within a millisecond of the interrupt.
- close: the SDK client is closed in the middle of the turn, without an interrupt. The CLI goes
  on by itself: all 6 requests the loop still held reached the stub within 40 ms, the hooks and
  the app tools of each failing and each failure answered by a new request. The SDK closes the
  CLI's input and then gives the process 5 seconds to leave before it terminates it
  (SubprocessCLITransport.close), so against a real model the requests that fit in those
  seconds leave. This is what a stopping worker did to a run in the middle of a turn.
- interrupt_close: an interrupt, then the close: no request.
- hold_close: a hook that only holds, nothing interrupting, the client closed 6 seconds later:
  the same 6 requests leave at the close. A hook that never answers stops nothing by itself.

## The product's runner (the opt-in tests, 6 passed)
- 10 runs with a budget of 4,000: each made 3 requests and ran 2 tools, ended failed with
  "The run reached its token budget and was stopped.", and recorded 4,500 input and 150 output
  (the result message's figures).
- A budget of zero: the stub received nothing.
- An agent with a model per kind of credential, on an API key: every request named
  claude-sonnet-5-5, and the tool events of the private run held names and sizes.
- A worker stop while the first request's tool was still running: 0 requests afterwards as
  built (the turn is interrupted before the client is closed, app/agents/backend.py), 8 when the
  interrupt is taken away (the control). The run recorded 1,500 input and 1 output, its own
  count.

## The bound, as stated in tasks/ingestion/todo.md (Measurements, G6)
A run passes its budget by the one request whose usage reached it, and by no other: 0 requests
after it, on the fake backend for every budget and on the real CLI in 10 of 10 runs. The request
that reaches the budget cannot be prevented, its usage is known when its first message arrives.
A turn that went on without a tool call would be seen at its next request and interrupted there:
one more request, never two; no agent of this app continues that way, and the fake backend holds
the case.
