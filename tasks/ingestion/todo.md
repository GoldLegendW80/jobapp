Spec: [SPEC-ingestion.md](../../SPEC-ingestion.md). Depends on agents (A1 to A5: credentials, the runner, proposals, the fake backend, the real runs of 2026-10-10) and profile (P1 to P6: section models, save with revisions, completeness, the diff helpers of the History drawer).

Two tasks of other modules are planned here because ingestion needs them first: `P7` (profile, branch `profile/p7-year-dates`) and platform task 10, written `T10` (branch `platform/10-backup-keep-7`).

## Decisions of the owner (Harald, 2026-10-10)
Taken through direct questions on 2026-10-10. They replace the three open questions of the first version of this plan and answer the five the review added.
1. **A PDF without a text layer is not refused.** Its pages are rendered to images with `pypdfium2==5.14.0` inside the sandboxed parser child, then transcribed by the model like screenshots (task G8 renders, task G14 transcribes).
2. **Document text is kept until the user deletes it.** No expiry.
3. **Backups keep 7 nightly dumps instead of 14, for everything** (task T10), and the delete dialog says: "Gone from the app now, and from the server's backups within 7 days."
4. **The profile accepts a year alone (`YYYY`) as well as a month (`YYYY-MM`)** for employer and education dates (task P7). The agent proposes exactly what the document says, never an assumed month.
5. **Model by credential.** A run on a subscription credential uses `claude-opus-5-5`; a run on an API key credential uses `claude-sonnet-5-5` automatically. The start dialog shows a token range before the run and, for API key users, a cost range. Every run has a hard token bound enforced in code.
6. **Explicit consent the first time** a user starts an ingestion run: a checkbox, recorded with the date and the version of the text shown, saying that the documents are sent to Anthropic through the user's own credential. Afterwards the start dialog shows a one line reminder.
7. **20 MB per file**, as the spec said before this plan: the Caddy limit is raised for the upload route only, and the parser sandbox memory and the per user quota are sized by measurement (G1, G2, G8).
8. **A failing citation is refused to the agent with the reason**, not dropped silently, with a retry budget per step and the refused count shown to the user.

## Architecture decisions

### Storage of uploads
- **Postgres, not a volume.** `ingestion_documents` holds the bytes (`bytea`) and the extracted text, as the profile photo does (tasks/profile/todo.md). Reason: one place to scope by user, `on delete cascade` from `users`, a hard delete that is one transaction together with the proposals it touches, nothing shared on disk between the api and the worker, and the worker's `/tmp` is a 128m tmpfs counted in its memory limit (compose.yml), which thirty files could not fit.
- **Bytes live only until the text exists.** Once a document's text is stored (`text_status = done`), its `bytes` are set to null in the same transaction. Text formats never store bytes at all. An image, and each rendered page of a scanned PDF, is kept as a small normalised JPEG in `ingestion_images` until a run transcribes it, then deleted. Reason: the text is all a run, a citation check and the preview ever read, so the original is the one copy nobody needs, and the smallest database is the most private one.
- **A failed document keeps its bytes for one retry, then loses them.** A parse that failed for a reason of the server (the wall limit, a worker restart, the queue down) is queued again once by the reaper while its bytes are still there. After the second failure, or after a failure caused by the file itself (encrypted with a password, a zip bomb, no readable page), the bytes are deleted and the row keeps its name, size, hash and the reason.
- **An upload that matches a failed document replaces it** (finding B7). The dedupe `unique(user_id, sha256)` returns the existing row with 200 only when that row is `pending`, `awaiting_transcription` or `done`. When it is `failed`, the upload stores the new bytes on the same row (same id), sets it back to `pending`, clears the reason and queues it again: 201. So a file that failed for a passing reason, or before a later version could read it, is fixed by uploading it again, with no delete first.
- **Limits:** 20 MiB per file (20,971,520 bytes, shown as "20 MB"; decision 7), 100 MB per user counted as bytes currently stored plus text plus images, 500,000 characters of text per document, 100,000 characters per paste, 200 pages per PDF read as text, 30 pages per PDF rendered as images, 200 documents per user. Over a limit: 413 or 422 naming the limit. The quota check and the insert run under a per user advisory lock, so two uploads at once cannot both pass a quota that fits one. At most two uploads are processed at once per api process (a semaphore, as `photo.DECODE_SLOTS`).
- **The edge limit is raised for one route only.** `caddy/Caddyfile` keeps 10 MiB everywhere and accepts 20 MiB on `POST /api/ingestion/documents` alone: a matcher on that path and method, `request_body` and the Content-Length check each in two variants, validated by `caddy validate` in the image build. Owner: G1.
- **Upload shape:** the raw request body with the name in `X-Filename` (RFC 5987), as `PUT /api/profile/photo` does (`_limited_body` checks Content-Length, then the stream). No multipart parser is added. The name is display only: control characters and path separators stripped, 200 characters at most, never used as a path; a name that decodes to nothing becomes "Untitled".
- **Per user isolation:** every query filters on the session's user id, another user's document answers the same 404 as a missing one, dedupe is per user so it never reveals another user's upload, and `Cache-Control: no-store` on every route.
- **Lifetime and deletion:** a document's text stays until the user deletes it (decision 2); deletion is a hard delete in one transaction with its effects on items, proposals and events (rules under "Failure rules"). Deleting the account cascades. The server's backups hold a deleted document for at most 7 days (decision 3, T10). Postgres keeps a deleted row in dead tuples until autovacuum reuses the page: accepted, a dump never contains dead tuples, and the dump test of G15 is the check.

### Text extraction per file type
- **Type from the bytes, never from the name or the Content-Type.** `%PDF-` is a PDF; `PK\x03\x04` is a ZIP, which is a DOCX when it holds `[Content_Types].xml` and `word/document.xml`, else a LinkedIn export when it holds the known CSV names at its root, else refused; the PNG and JPEG magic of `profile.schemas.sniff_photo`; anything else must decode as UTF-8 (a BOM accepted, UTF-16 with a BOM accepted) without NUL bytes and is then text (TXT, MD, JSON, CSV alike). Refused with 415 and one sentence: legacy `.doc` (OLE magic), RTF, ODT, HEIC, GIF, WebP, executables, a `.docm` or any DOCX carrying `word/vbaProject.bin`. The api only looks at magic bytes: it decodes no image and parses no archive.
- **PDF text: `pypdf==6.20.0`** (pure Python, BSD 3 Clause, wheel `py3-none-any`, no dependency on Python 3.12, released 2026-10-09). Pinned on purpose although it is one day old (finding N1): its changelog, read on 2026-10-10, carries the security change "Limit work per stream (filter count, accumulated decoding work)" and the robustness changes "Flatten the page tree iteratively" and "Drop a /Kids entry resolving to null instead of raising a cycle error", which are this module's own hostile cases, and every pypdf advisory of September 2026 (long runtimes, large memory) is patched at or before 6.19.0. G2 checks PyPI again when it starts and takes a 6.20.x fix release if one exists, never a yanked one. `PdfReader(strict=False)`, `page.extract_text()` page by page, stopping at the page cap and the character cap. The URIs of a page's link annotations are appended to that page's text on a line "Links: ...", because a CV shows "LinkedIn" and keeps the address in the annotation (finding N9).
- **Encrypted PDFs (finding N8):** the empty user password is tried first, since many CVs are exported with print or copy restrictions and read with `""`. AES needs `cryptography`, already in the worker image. If the file needs a real password: failed with "This PDF is protected by a password. Remove the protection and export it again."
- **DOCX text: the standard library plus `defusedxml==0.7.1`** (pure Python, PSF licence, wheel `py2.py3-none-any`, no dependency, released 2021-03-08, no advisory listed). `zipfile` opens the archive, `defusedxml.ElementTree` parses `word/document.xml`, the headers and the footers, and a small walker emits the text of `w:t`, `w:tab`, `w:br` and paragraph ends in document order, tables included. Three rules of the walker (finding N9): a `w:hyperlink` with an external target in `word/_rels/document.xml.rels` is emitted as "text (url)"; of an `mc:AlternateContent` only `mc:Choice` is read, never `mc:Fallback`, so a text box is not extracted twice; `w:delText` (deleted tracked changes) is left out and `w:ins` is read. Rejected: `python-docx==1.2.0` (MIT, needs `lxml`, a compiled XML stack, for styles and writing that ingestion does not use). Macros are never run: a DOCX is read as XML only.
- **ZIP (LinkedIn export):** `zipfile` from the standard library, each known CSV becomes a document of its own; every other entry is ignored.
- **Images (PNG, JPEG): no local OCR.** The model transcribes them inside the run. Pillow (`pillow==12.3.0`, already a dependency) decodes and normalises them, **inside the sandbox child, not in the api and not in the worker process** (finding N2): 25 megapixel guard read from the header before decoding, EXIF orientation applied, converted to RGB, longest side at most 1568 px, re-encoded as JPEG of at most 300,000 bytes (quality 80, 70, 60, 50, then the size reduced by 15 percent per step until it fits), stored in `ingestion_images`. The tool that shows an image to the agent only reads those bytes.
- **PDF pages without a text layer (decision 1): rendered with `pypdfium2==5.14.0`** (released 2026-10-04, licence "BSD-3-Clause, Apache-2.0, dependency licenses" for the bundled PDFium, wheel `manylinux_2_17_aarch64` of 3,719,672 bytes for the Jetson and `macosx_13_0_arm64` for the Mac, no dependency, no advisory on PyPI or on its GitHub repository on 2026-10-10). The rule is per page: a page whose extracted text holds fewer than 50 characters that are not whitespace is rendered; the others keep their text. At most 30 pages of one PDF are rendered (the rest are named in the document's reason, "pages 31 to 44 were not read"), each at a scale that puts its longest side at 1568 px (a bitmap of at most 1568 x 1568 x 4 bytes, about 10 MiB), a page larger than 200 inches on a side or narrower than a tenth of its length is skipped, and each bitmap goes through the same JPEG normalisation as an uploaded image. A PDF whose every page has text never loads PDFium. PDFium is a compiled parser of hostile files: it runs only in the sandbox child, under the limits below, and its version is the one thing in this module to update on a Chrome security release (a line in the README, owner G8).
- **Text formats and pastes** are decoded in the api at upload (no queue): normalised to NFC, `\r\n` to `\n`, control characters removed, capped.

### The parser sandbox (finding B1)
- **Where:** in the worker container, in a child process, started by a new arq queue `jobapp:ingestion` (`max_jobs=1`). The api container (512m) parses nothing.
- **A standalone script, started by absolute path.** `api/app/ingestion/sandbox/main.py` imports nothing from `app` and is started as `[sys.executable, "-I", "/app/app/ingestion/sandbox/main.py", kind]` (the path computed from `__file__` of the parent module). `python -I -m app.ingestion.sandbox` cannot work: `-I` implies `-P`, the working directory is not on `sys.path`, and `app` is not an installed package (`[tool.uv] package = false`). `main.py` adds exactly one directory to `sys.path`, its own (`/app/app/ingestion/sandbox`, owned by root and read only for uid 10001 in the image), and imports the handler of `kind` from a fixed table: `pdf_text`, `docx`, `linkedin_zip`, `image`, `pdf_render`. Each handler is one file in that directory, so G2, G7 and G8 add files and never edit the same one. `pypdf`, `defusedxml`, `pypdfium2` and Pillow come from the venv's site-packages (the venv is found through `pyvenv.cfg` next to `sys.executable`; assumption A1, G2 proves it).
- **Environment:** empty, except `OPENSSL_armcap` copied from the worker when it is set there (the Mac only, `compose.mac.yml`: without it, importing `cryptography` for an AES encrypted PDF ends in SIGILL in Docker on an M4). Working directory `/`. Standard input is the file, standard output is the answer, standard error is discarded.
- **Limits, set by `main.py` itself before it imports any handler** (not in `preexec_fn`, which is unsafe in a threaded parent, and because the dumpable attribute is reset by `execve`). Checked against getrlimit(2), prctl(2), core(5) and proc(5) of the Linux man-pages and the Python `resource` documentation on 2026-10-10:

| Limit | Value | Real effect for a Python child on Linux arm64 | What a test must prove |
|---|---|---|---|
| `RLIMIT_AS` | per kind, starting at 512 MiB, then the measured peak plus a margin (G2, G8) | caps the address space: `brk`, `mmap` and `mremap` fail with `ENOMEM`, which Python raises as `MemoryError`. pypdf catches broad exceptions and may swallow it, and PDFium aborts on a failed allocation, so this limit alone does not end a run: the wall kill does. | a handler that allocates past the limit ends with the document failed, the worker alive and the next job run |
| `RLIMIT_CPU` | 45 s soft and hard | `SIGXCPU` at the soft limit, whose default action ends the process, then `SIGKILL` at the hard limit. It counts CPU time only: a child that sleeps or blocks is not stopped by it. | a busy loop is ended near 45 s of CPU with no core file |
| wall clock | 60 s, by the parent: `communicate` with a timeout, then `kill` | the only limit that ends a blocked or swallowing child | a sleeping child is killed at 60 s and reaped (no zombie) |
| `RLIMIT_FSIZE` | 0 | any write that grows a regular file raises `SIGXFSZ` (default: the process ends). Pipes are not files: the answer on standard output is not affected. | creating a one byte file fails; a 3 MiB answer on the pipe arrives |
| `RLIMIT_NOFILE` | 16 | `open` fails with `EMFILE` past 16 descriptors; imports open one file at a time | the handlers import and run under 16; a 17th descriptor fails |
| `RLIMIT_NPROC` | 0 | counts the processes and threads of the real uid; at or above the limit `fork` and thread creation fail with `EAGAIN`. Not enforced for a process holding `CAP_SYS_ADMIN` or `CAP_SYS_RESOURCE`: the worker runs as uid 10001 without them. It does not stop `execve`. | `os.fork()` and `threading.Thread().start()` fail in the child; rendering a page with PDFium works under it (assumption A2, G8) |
| `RLIMIT_CORE` | 0 | no core file. Not enough alone: core(5) says the limit "is not enforced for core dumps that are piped to a program", and Ubuntu on the Jetson host pipes cores to apport. | see the next line |
| `prctl(PR_SET_DUMPABLE, 0)` | set | the process produces no core dump at all, piped or not (a core of this process is the document), its `/proc/<pid>` files belong to root and it cannot be attached with `ptrace` | `prctl(PR_GET_DUMPABLE)` answers 0 in the child; a child ended by `SIGSEGV` and one ended by `SIGXCPU` leave no core |
| `prctl(PR_SET_NO_NEW_PRIVS, 1)` | set | no privilege gained through a set-user-ID binary after an `execve` | the call succeeds |

- **The parent side:** `parser.run(kind, data)` in `api/app/ingestion/parser.py` writes the bytes to standard input and reads standard output with `communicate` and the 60 s timeout, so a 20 MiB input and a large output cannot deadlock; it reads at most 4 MiB of output and kills the child past that (rendering therefore runs in batches of 8 pages per child: 8 x 300,000 bytes in base64 is 3.2 MB). The child writes ASCII JSON (`ensure_ascii`) to `sys.stdout.buffer`, since an empty environment has no locale. Any exit status but 0, any output that is not the expected JSON, any timeout: "could not be read", with the kind of failure (file or server) for the retry rule.
- **Nothing of the document leaves Postgres.** The arq job takes a document id, writes the text or the images to the database itself and returns only a status word: arq keeps return values in Redis, and a text returned there would be a copy outside the database. A test reads the job result in Redis.
- **The worker makes itself non dumpable at start** (`prctl(PR_SET_DUMPABLE, 0)` in `app/worker.py`, owner G2). `drop_secrets_from_environ` deletes from `os.environ` but the kernel still shows the initial environment block in `/proc/<worker pid>/environ`, readable by any process of the same uid, and the parser child has that uid. Per proc(5), the `/proc/<pid>` files of a non dumpable process belong to root. A test starts a child of the same uid and asserts it cannot read the worker's `environ` nor its `mem`. The attribute comes back to 1 at each `execve`, so the Claude Code process is unchanged by this (assumption A3: the kernel resets it at `execve`; the test of G2 reads it in a fresh child).
- **Residual holes, accepted and stated (finding N3).** The sandbox is a resource and crash container, not a security boundary against code execution. Reaching any of these needs code execution inside pypdf, the DOCX walker, Pillow or PDFium:
  1. The child has the worker's uid, so it can read what uid 10001 can read: the app code (no secret in it), and `/proc/<pid>/environ` of a Claude Code process running at that moment for another user's agent run, which holds that user's model credential (that process is dumpable again after its `execve`). A different uid needs root or a user namespace, which the container does not have; a second container for parsing costs about 100 MiB on a 7.4 GB Jetson. Accepted for the first version, listed under "Needs the owner".
  2. The child shares the network namespace: it can reach `db`, `redis` and the internet, with no credential in its environment. Network isolation needs `CAP_NET_ADMIN` or a namespace, neither available.
  3. It can send signals to processes of its uid (stop the worker or a run): a denial of service, repaired by the restart policy and the reapers.
  4. `RLIMIT_NPROC` does not stop `execve`, so a compromised child can become another program under the same limits.
- **Memory budget of the worker (1536m), to be measured, not guessed:** idle 145 MiB and one real run at 308 to 333 MiB on the Jetson (A5), two runs estimated at 525 to 625 MiB, the tmpfs up to 128 MiB, one parser child up to its `RLIMIT_AS`. With a child at 512 MiB that is at most about 1265 MiB. G2 measures the child's peak resident memory on its fixtures (a 20 MiB PDF full of images, a 200 page text PDF) and the worker cgroup's peak with two real CLI runs against the stub and one parse at once, lowers `RLIMIT_AS` to the measured peak plus a margin, and writes the figures under "Measurements". G8 does the same for the image and render kinds (a 25 megapixel decode is about 100 MiB of RGBA).

### What the agent may read, and how
- **No built-in tool, not even `Read`.** The runner as merged starts Claude Code with `tools=[]`, lists `Read` in `FORBIDDEN_TOOLS` and gates every call (`app/agents/runner.py`); ingestion keeps all of that unchanged. The agents read through in-process app tools only.
- **One step is bound to one document part, in code (finding B4).** The step's `agent_runs.input` is `{ingestion_run_id, step_id}` and nothing else. Before the tools are built, the runner asks the agent definition's `bind` hook for the step's binding, and the tools close over it in the `Scope`: for an extraction step `{document_id, part, start, end}` (character offsets of the part in the document's text), for a transcription step `{document_id, first, last}` (positions of its images). So no tool takes a document id, there is no `list_documents`, and a citation is `{excerpt}` alone: code attaches the document. The model cannot name a document, its own or another's, because no argument exists for it. A step whose binding is gone (the document was deleted) fails with "This document no longer exists." before any model call.
- **Tools of `profile_extract` (extraction):** `read_document(offset)` returns at most 30,000 characters and at most 40,000 UTF-8 bytes of the step's part, under the key `untrusted_text` with `next_offset` (null at the end of the part; an offset outside the part is an error); `get_profile_section` (the existing tool, contact details and the board list still left out); `propose_profile_changes(section, items[])`.
- **Tools of `document_transcribe` (transcription):** `view_image(position)` returns one image block, the stored JPEG of that position, and only for a position of the step's range; `store_transcription(position, text)` is the return path of a transcription (finding B3): it may be called once per position, refuses a text over 20,000 characters for one image and a document over 500,000 in all, and stores the text of that image. When every image of the document has its text, the same transaction assembles the document's text in page order, sets `text_source = transcribed` and `text_status = done`, and deletes the document's images. The system prompt asks for the text as it reads on the image and for a final answer of one line ("3 pages transcribed"), so the model's `text` events hold a summary, not the document.
- **Why not the scoped `Read` the agents plan reserved for ingestion:** (1) SPEC-agents lists filesystem tools under "ask first"; (2) `FakeBackend` answers any tool that is not an app tool with "No such tool available", so a `Read` based flow could not be covered by CI, against success criterion 4; (3) files would have to be written into the 128m tmpfs; (4) `Read` renders PDF page ranges with `pdftoppm`, so it would not have spared a rendering dependency either. After G0 the scoped `Read` is no longer a fallback: it is not used.
- **The image path is proven (G0, done on 2026-10-10, `tasks/evidence/ingestion-g0/`).** The real bundled CLI 2.1.286, started through the pinned SDK 0.2.163 with the runner's options against `tests/anthropic_stub.py`, with an in-process tool returning image blocks, 54 cases, no model call and no credential. What reached the stub's `/v1/messages` request:
  1. An image block returned by an app tool is forwarded as an `image` content block (`source.type = base64`, the tool's `mimeType` as `media_type`) inside the `tool_result` of the next request. JPEG and PNG, byte for byte up to 449 kB.
  2. `MAX_MCP_OUTPUT_TOKENS` counts an image as a flat 1,600 tokens whatever its bytes or pixels: a 200 kB image at 1568 px and a 60 kB image at 784 px are both cut at a limit of 1,500 and both pass at 1,600; with the default of 25,000, 15 images pass in one result and the 16th is cut. Base64 length is not counted.
  3. Above the limit nothing fails: the CLI replaces the image by a thumbnail (400 px or less, about 3 kB) and adds a text block that starts with "[OUTPUT TRUNCATED" and names the limit. A transcription from that would be silently wrong, so the limit must never be lowered: the runner leaves the variable unset (it blanks every inherited variable outside `ENV_KEEP`), and a test of G14 asserts the forwarded image has the stored pixel size.
  4. The CLI recompresses a JPEG somewhere between 449 kB and 593 kB (a 1 MB file arrived as 449 kB, a 3 MB file as 490 kB) and resizes anything over 2000 px on its longest side. Under 449 kB and 2000 px the bytes are untouched.
  5. **The binding constraint is the SDK, not the CLI.** The CLI echoes each tool result to the SDK as one JSON line holding the content twice (`content` and `tool_use_result`), and the SDK's reader fails over 1,048,576 bytes with `CLIJSONDecodeError` (`max_buffer_size`, default 1 MiB). So one tool result may carry about 390 kB of image bytes at most: a 385 kB image passes, a 449 kB image ends the run, and so do three images of 200 kB in one result. Hence the rule above: one image per `view_image` call, each at most 300,000 bytes (an echo of about 800 kB), and the SDK default left as it is.
  6. Text: results of 30,000 and 49,000 characters stay inline. A result of 120,000 characters is replaced by an error naming a file under `CLAUDE_CONFIG_DIR/projects/.../tool-results/`, which an agent without `Read` cannot open and which is a copy of the document on the tmpfs until the scratch directory is deleted. Hence 30,000 characters per `read_document` call, and the cap of 40,000 UTF-8 bytes so that a text in a script with more tokens per character stays under 25,000 tokens (assumption A4, verified in G14's real CLI test with a Chinese fixture).
  7. The SDK hands the runner the image inside the `ToolResultBlock`; `runner.result_text` turns it into "[image]", so no event stores image data even without `private_io`.
- **Scratch directory and session persistence:** nothing new. As built in A2 every run gets a scratch directory on the tmpfs holding `HOME`, `CLAUDE_CONFIG_DIR` and the temporary files, `CLAUDE_CODE_SKIP_PROMPT_HISTORY=1` stops transcripts and prompt history, and the directory is deleted on every path. Ingestion writes no document into it.

### The run: steps, the chain and the merge
- **An ingestion run is a chain of steps, each an ordinary agent run.** The runner executes one SDK session per `agent_runs` row with fixed limits and has no sub-runs. So a run is a row of `ingestion_runs` plus ordered `ingestion_run_steps`, `unique(ingestion_run_id, position)`: first the transcription steps (one per document with images and per range of at most 8 images), then the extraction steps (one per document part of at most 100,000 characters, cut at a paragraph end). Each step is an `agent_runs` row of `document_transcribe` or `profile_extract` (40 turns, 15 minutes), queued on the existing agents queue. A part is 100,000 characters, not 200,000, because a part is sent again at every turn of its step: halving it halves the worst case of a step (see "Tokens").
- **Internal agents.** Both definitions carry `internal = True` (added by G6, as `chat`): refused with 422 by `POST /api/agents/runs` and absent from `GET /api/agents`, so a user can never start `profile_extract` outside an ingestion run. Their runs appear on `/runs` like any run, with names, sizes and tokens only.
- **Model by credential (decision 5).** Both definitions say `model = claude-opus-5-5` and `model_by_credential = {anthropic_api_key: claude-sonnet-5-5}`, effort medium for both. The runner picks the model when it has revealed the credential (G6); the model that ran is recorded on the run, as today. Only the two ingestion agents use this: triage and chat stay on `claude-opus-5-5` (see "Needs the owner").
- **`advance(ingestion_run_id)` moves the chain.** It runs in its own transaction, never inside the transaction that ends an agent run: the runner calls an `on_final` hook after it has recorded any final status (done, failed, cancelled), and a cron calls `advance` every minute for every run that is not final, which covers a hook that never ran (the worker died, a reaper failed the run). It locks the `ingestion_runs` row `FOR UPDATE`, reads the steps and the status of their agent runs, and does exactly one of: record the result of the step that ended, create and queue the next step, pause, merge, or finish. The `agent_runs` row of a step is created through `runs.create_run` and written to `step.agent_run_id` in that same transaction; the enqueue comes after the commit, and a failed enqueue is recorded with `runs.fail_queued` and pauses the run. Calling `advance` twice at once is safe because the second call waits for the row lock and then finds nothing to do.
- **One active run per user is a constraint, not a lock:** a partial unique index on `ingestion_runs(user_id)` where the status is `running` or `paused`. `POST /api/ingestion/runs` catches the violation and answers 409 with the id of the active run.
- **Steps count toward `ACTIVE_PER_USER` (4), and a run uses one slot at a time.** When the user already has four runs queued or running (triage, chat), `runs.create_run` raises `ActiveRunsError`: `advance` leaves the step `planned`, records `waiting = "slots"` on the run for the UI ("waiting for your other runs to end") and tries again at the next tick. It never fails the ingestion run for that. Since steps are queued one at a time, other users' runs take their turn on the two worker slots between two steps.
- **Lock order, for every path of this module**, consistent with the agents module (thread, then the user's advisory run lock, then the run row; job, then proposal): (1) the chat thread row, never taken here; (2) the `profiles` row; (3) the `ingestion_runs` row; (4) `ingestion_documents` rows in id order; (5) the user's advisory run lock of `runs.create_run`; (6) the `agent_runs` row; (7) `proposals` rows in id order. Who takes what: accept and accept-section 2 then 7; `advance` 3, then 5 and 6 to create a step, then 7 when it merges; cancel 3 then 6; deleting a document 3 (the user's active run, if any), 4, 6 (cancel of the step reading it), 7. Every path goes up the list, so no two can wait on each other. `test_ingestion_locks.py` (G10) runs each pair of paths that exists then against real Postgres from two connections; G12, G13 and G15 each add the pairs they create in a file of their own (`test_ingestion_locks_<task>.py`), so two tasks of one group never edit the same test file.
- **The merge is code, not a model call.** Steps write checked candidates into `ingestion_items`; a deterministic merge turns them into `proposals` (dedupe, conflicts, comparison with the profile). Reason: cheaper, testable without a model, and the same input always gives the same proposals.

### Failure rules (finding B6)
| What happens | Rule |
|---|---|
| A step fails on the credential or the provider: `NO_CREDENTIAL`, `UNREADABLE`, `REFUSED`, `BUSY`, `API_ERROR` (any HTTP status), `runs.QUEUE_DOWN`. G6 exports `runner.is_provider_failure(error)` so nobody matches message text twice. | The chain stops: the run becomes `paused` with that message, no further step is created (thirty documents never make thirty failed requests on a credential near its limit). Finished steps keep their items. The user fixes the credential and clicks Resume (`POST /api/ingestion/runs/{id}/resume`), which runs the remaining steps, the failed one first. A paused run is still the user's one active run; it is merged with what finished and closed as partial after 24 hours without a resume. |
| A step fails on its own content: the turn limit, the 15 minutes, the token bound, no result. | The step is `failed`, the chain goes on with the next step, and the run's summary names the document. |
| The worker restarts during a step: the reaper fails the agent run with `INTERRUPTED`, `STOPPED`, `LOST` or `STALE`. | `advance` runs that step once more (`attempt = 2`, a new agent run on the same step row). A second such failure is a content failure. |
| The 60 minutes of the whole run pass (`deadline_at`, set at the start; the time spent queued behind other runs counts; a pause stops the clock). | `advance` requests the cancel of the running step, creates no further step and merges what finished: status `done` with `partial = true` and the list of documents not read. Nothing already extracted is lost. |
| The user cancels the run. | Under the run row lock: `cancel_requested_at` set, cancel requested on the active agent run. When that run ends, `advance` sets `cancelled`. No merge; the items of finished steps stay and a later run reuses them. Cancel of a paused run or of a run waiting for a slot is immediate. |
| The user cancels one step through `POST /api/agents/runs/{id}/cancel`. | The same as cancelling the ingestion run: `advance` sees a cancelled step without having asked for it and cancels the whole run. |
| A document is deleted while its own step runs. | The delete transaction (order 3, 4, 6, 7) requests the cancel of that agent run, deletes the events it has written so far, sets `purge_events` on the step, and deletes the document, its images and its items (cascade). The runner may still write events for a few seconds: `advance` deletes the step's events again when the agent run reaches a final status, and the cron deletes them at every tick until five minutes after `finished_at`, since a cancelled `emit` can leave one write running in its thread. A tool call arriving after the delete finds no document and answers "not found". The test asserts on `agent_events` after the step has ended and after one more tick, not when the delete returns (success criterion 5). |
| A document is deleted during the merge or while one of its proposals is being accepted. | The delete waits for the run row (merge) or for the proposal row (accept), then applies its rules to what it finds: an accepted item keeps its value and shows "source deleted". |
| Redis is down when `advance` enqueues. | `runs.fail_queued`, then the run is `paused` with "The agent queue is unavailable." |

### Proposal kinds and targets
- **One kind, reusing the table as built in A3:** `proposals` rows with `target = "profile"`, `target_id = null`, `kind = "profile_item"`, `run_id = null` (a merge is not an agent run) and `payload = {ingestion_run_id, section, key, action, value, value_hash, citations[], base_revision, flags[], conflict?}`. `proposals.create` is called as is: with a null `target_id` it takes no lock and supersedes nothing, so ingestion supersedes its own older pending items itself.
- **Stable keys per section** (spec): identity field name, or `languages:<name>`, `links:<label>`; experience `employers:<key>` or `education:<school>:<start>`; facts `blocks:<title>`; skills `<have|adjacent|none>:<name>`, `gates:<name>`; search field name, `boards:<ats>:<org>`, `never_apply:<hash>`; answers field name or `work_authorization:<country>`. Never proposable by the agent: `skills.years_experience` (computed, see "Citations"), `search.sweep_schedule` (it would start scheduled sweeps), the photo, and anything outside the six section models.
- **Facts block keys are only as stable as the model's wording (finding N10).** `blocks:<title>` uses a title the model chose. A rejected block can come back under another title when its document is read again, or after `EXTRACTOR_VERSION` or the model changes. Success criterion 3 therefore holds through the reuse of stored items (an unchanged document is not read again), and the "read again" choice says: "Items you rejected may be proposed again."
- **Accepting dispatches on the target.** As merged, `proposals.accept` reads `ProposalKind(proposal.kind)` first, so for a `profile_item` it raises `InvalidValueError(UNKNOWN_KIND)` and the proposal stays pending (the first version of this plan said "marked invalid", which was wrong). G5 inserts the dispatch on `proposal.target` before that line, so the job path is untouched and the A3 tests pass unchanged: a profile item is applied to the current section under the `profiles` row lock, the result validated by the section's Pydantic model, saved through `profile.service.save_section` (one revision), `edited_value` validated the same way. `POST /api/ingestion/runs/{id}/accept-section` applies several items in one save. Locked items (identity contact fields and languages, all of experience) and flagged items are refused in bulk (spec). `POST /api/ingestion/runs/{id}/reject-section` rejects several items at once, with no exclusion (finding N7).
- **UI reuse:** `proposals-api.ts` (`acceptProposal`, `rejectProposal`), `RunPanel` and `useRunStream` for the live step, `flattenSection` and `diffFields` of `profile/diff.ts` for the before and after of each item, the completeness bar of the profile page.

### Citations: the checker, as a normative table (finding B5)
The agent gives `{excerpt}` per citation; the server stores `{document_id, excerpt, start, end, transcribed}` where `start` and `end` are character offsets in the document's stored text, so the review opens the preview at the quote. The check runs in `propose_profile_changes` before anything is stored. `app/ingestion/citations.py` is a pure module (no database, no SDK): G4 implements this section and nothing else.

**Normalisation `N(text)`**, the same function for the document text and for the excerpt, steps in this order. It returns the normalised string and, for each character of it, the index of the character of the original it came from (the map is per output character, because steps 1 and 5 change lengths).

| Step | What | Detail |
|---|---|---|
| 1 | NFKC | `unicodedata.normalize("NFKC", s)`: "\uFB01" becomes "fi" (the ligature forms U+FB00 to U+FB06), full width digits become ASCII digits, U+00A0 and U+202F become a space, U+2026 becomes "...". The letters "œ" and "æ" are letters and stay. |
| 2 | Strip invisible characters | U+00AD (soft hyphen), U+200B to U+200D, U+2060, U+FEFF, the bidi controls U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069, and every other character of category Cc or Cf except tab, line feed and carriage return. |
| 3 | Fold apostrophes and quotes | U+2018, U+2019, U+201A, U+201B, U+2032, U+02BC, U+0060, U+00B4 become `'`. U+201C, U+201D, U+201E, U+201F, U+2033, U+00AB, U+00BB become `"`. |
| 4 | Fold dashes | U+2010 to U+2015, U+2212, U+FE58 become the ASCII hyphen. |
| 5 | Case fold | `str.casefold()` ("ß" becomes "ss"). |
| 6 | Whitespace | every run of whitespace becomes one space; leading and trailing space removed. |

**Matching.** The skeleton `S(x)` is `N(x)` with every space and every ASCII hyphen removed. An excerpt matches when `S(excerpt)` is a substring of `S(document text)`; `start` and `end` are the original offsets of the first match, through the two maps. This is the symmetric rule for hyphenation: "full-\nstack" in the document and "full-stack" or "fullstack" in the excerpt all have the skeleton "fullstack". It only forgives spaces and hyphens: it cannot make a quote match letters or digits that are not in the document. All value checks below read the **cited span**, `N(document text[start:end])`, never the agent's own typing of the excerpt.

**Length bounds**, counted in characters of `N(excerpt)`: at least 20 and at most 600, and `S(excerpt)` at least 12 characters. One exception: when `N(document text)` is itself shorter than 20 characters, the excerpt must match the whole document.

**Rules per field type.** `v` is the proposed value, `C` the cited spans of the item (one per citation).

| Rule | Applies to | Check |
|---|---|---|
| V, verbatim | `identity.email`, `identity.linkedin_url`, `identity.website`, every other URL, `identity.languages[].name`, `links[].label`, `experience.employers[].organisation`, `experience.education[].school`, `search.boards[].org` | `S(N(v))` is a substring of `S(c)` for one `c` in `C`. For a URL, every "http://", "https://" and "www." is removed from the value and from the span first, and one trailing "/" from the value. This closes the path where an instruction inside a document gets a foreign address proposed next to an unrelated real quote. |
| D, dates | `start` and `end` of employers and education, and any other field typed as a date | A value `YYYY`: the year is a number of one `c` (rule N). A value `YYYY-MM`: one `c` holds the year next to its month, as one of: a month name or abbreviation followed by the year with at most three characters among space, "." and "," in between ("January 2023", "janv. 2023", "Sept, 2021"); the year followed by the month name; `MM/YYYY`, `MM.YYYY`, `MM-YYYY`, `M/YYYY`, `YYYY-MM`, `YYYY/MM`, where the month is a whole run of one or two digits from 1 to 12 and the year a whole run of four. Month words are compared without accents; the accepted words are the English and French names and the abbreviations jan, feb, mar, apr, jun, jul, aug, sep, sept, oct, nov, dec, janv, fev, fevr, avr, juil, aout, dec. A month that is not in the source is refused with the reason "month not in the source: propose the year alone". `end = null` (present) carries no number and is not checked. |
| P, phones | `identity.phone` | The digits of `v` (at least 6) are a contiguous substring of the digits of one `c` with every other character removed. No national to international conversion: the value is proposed as the document writes it. |
| N, numbers | every other string and every JSON number of the value, at any depth, except stable keys and enum fields | Each number of `v` has a reading in common with a number of one `c`. A **run** is a maximal sequence of digits that may hold, between two digits, one single character among space, ".", "," and "'". Its **readings**, compared as decimal numbers: (a) no separator: the integer; (b) every separator is the same character and is followed by exactly three digits, the first group having one to three digits: the integer without separators ("10 000", "10,000" and "10.000" read 10000); (c) exactly one separator, a "." or a ",": the decimal ("3,5" and "3.5" read 3.5; "1,234" has readings b and c); (d) groups as in b followed by one different separator among "." and "," and more digits: the grouped integer with its decimals ("1 234,56" reads 1234.56); (e) only when none of b, c and d applies, the run is split at its separators and each piece is a number of its own ("2019 2021" and "12.05.2023" give their pieces). Because runs are maximal, "2023" inside "12023" and "3" inside "3,5" are not numbers of the source, and "10" is not a number of "10 000". Letters and signs next to a run are not part of it: "10k", "50 %" and "Python 3" hold 10, 50 and 3, and "10k" is not 10000. Digits inside names are numbers and must be cited ("Hotel 35", "ISO 27001"). A number written in words in the source ("three years") does not support a digit in the value: the agent proposes the words. |
| none | free text without a digit: a title, a degree, a city, a fact block | The excerpt exists in the document, and that is all code can say. Whether the quote supports the claim is the user's to judge: the review shows the sentence "The quote exists in your document. Whether it supports the item is yours to judge." |

**`skills.years_experience` is never proposed by the agent** (the tool refuses the key: "computed by the app"). The merge computes it from the employers of the profile with this run's employer items applied: the union of the periods without overlap, in months, read at their shortest when a date is a year alone (a start `YYYY` counts from December, an end `YYYY` to January), an open period ending at the month the run started, then `floor(months / 12 * 10) / 10`. It is proposed as a derived item, flagged `derived`, citing the employer items' excerpts, never part of "Accept all", and only when the profile has no value yet: it never proposes to replace a number the user set, so it cannot come back every month as the open period grows.

**Refusal and the retry budget (decision 8).** A failing item is refused and never stored: the tool answers with the item's index and the rule it broke ("item 2: rule D, month not in the source"), never the text. Per step, in code: after 20 refused items, or at the third refusal of the same section and key, the answer for a failing item becomes "not accepted, do not retry this item"; passing items are still stored. The step's `refused_count` is stored and the run summary shows it per document ("4 items refused: the quote did not support them"). Per call at most 50 items, per run at most 2,000.

### Prompt injection
- **The document is data.** Its text reaches the model only inside tool results under `untrusted_text`, the system prompt says that nothing in a document is an instruction (as the triage agent does for postings), and an attempt is reported in the run summary.
- **What code refuses whatever the model says:** no tool takes a user id or a document id (the step's binding is in the `Scope`); no tool writes anything but checked candidates or the transcription of the step's own images; every built-in tool stays unavailable and gated; a value must validate against its section model (URLs http or https only, regexes through `check_regex`); `search.sweep_schedule`, `skills.years_experience` and unknown keys are refused; short fields must be verbatim in the source (rule V).
- **Stored injection through the fact base:** a fact block is later read by other agents as trusted. An item whose value or excerpt looks like an instruction to a model (a short pattern list: "ignore previous", "ignore all previous", "system prompt", "you are an AI", "as an AI", role tags) gets the flag `looks_like_instruction`, is shown with a warning, and is never part of "Accept all".
- **Private events:** agent definitions gain a flag `private_io` (G6). For such runs the recorder stores tool names, sizes and error states only, never arguments or results, and the run's `output` holds counts (turns, tool calls, denied tools), never text. `text` events (the model's own words) are stored and deleted with the document they came from.

### Duplicates, conflicts and reruns
- **Against the profile:** the merge drops a candidate whose value already equals the profile's at that key (after the section model's normalisation). A different value at an existing key is a `replace` shown as a diff; nothing is ever applied without the click.
- **Between documents:** equal values at one key become one proposal carrying all citations; different values at one key become one proposal with `conflict = [{value, citations}]` and the user picks one (spec). A year alone and a month of that year at the same key ("2021" in the CV, "2021-03" in the dossier) are a conflict like any other: the user picks.
- **Idempotency:** a step is identified by (document sha256, kind, part or image range, `EXTRACTOR_VERSION`, model). The planner of G10 gives a new run's step the status `reused` when a finished step with the same identity exists: its `ingestion_items` are used and no model is called, unless the user asked to read that document again (`reread_document_ids` of `POST /api/ingestion/runs`). The model is part of the identity, so a user who changes credential kind reads the documents again. Proposals are a pure function of the items, the current profile and the user's earlier decisions, so the same documents and the same profile give the same proposals and zero tokens.
- **Earlier decisions:** an item the user rejected (section, key, value hash) is not proposed again; an accepted one is equal to the profile and drops out; pending items of an older run are superseded when a newer merge runs.

### Tokens: the estimate and the hard bound (decision 5, finding N5)
Characters divided by 4 is the size of the input read once, and it understates twice: French prose and Markdown run nearer 3 characters per token, and a step sends its growing context again at every turn. The dialog therefore shows a range and a bound, computed by `app/ingestion/estimate.py` (pure, G10), and says which is which.
- **Inputs.** `T = ceil(characters of the part / 3)` (assumption A5). An image is 1,600 tokens. `F = 7,000` tokens of fixed context per turn: the system prompt, the tool definitions and the harness (assumption A6, from A5's real triage run: 43,100 input tokens over 6 turns on a small job). `R = ceil(characters of the part / 30,000)` reads.
- **Input tokens of an extraction step run in `n` turns:** `input(n) = n*F + T*(2n+1-R)/2`: every turn pays `F`, and a chunk read at turn `i` is sent again at each later turn. A transcription step of `k` images: `n*F + 1,600*k*(2n+1-k)/2`.
- **The range shown:** low with `n = R + 2` (read, propose once, finish), high with `n = min(40, 2 * R + 8)`. Output tokens are added at 1,500 per step for the low end and 8,000 for the high end (assumption A7). Reused steps count zero. Example, a 30,000 character document: `T = 10,000`, `R = 1`, low `3*7,000 + 10,000*3 = 51,000`, high `10*7,000 + 10,000*10 = 170,000` input tokens. A 100,000 character part (`T = 33,334`, `R = 4`): low about 192,000, high about 595,000.
- **The hard bound.** Each step gets `token_budget = ceil(1.25 * input(40)) + 100,000`, written into the step's run by `advance`. The runner (G6) adds up the usage of every assistant message (input, cache writes, cache reads and output; one count per API message id) and, past the budget, interrupts the run, which ends failed with "The run reached its token limit." (a content failure: the chain goes on). The bound can be passed by one model call at most. The run's bound is the sum of its steps' budgets: about 1.7 million tokens for a full part of 100,000 characters, near 3.8 million for a typical dossier of three documents of 50,000 characters (expected range 0.26 to 0.83 million), and about 34 million for the largest selection the limits allow (1,500,000 characters and 60 images). The 40 turns and 15 minutes per step and the 60 minutes per run stay. This is a technical bound in tokens, not a spending cap in money: SPEC-agents' decision of no spending cap stands, and the dialog says that tokens on a subscription are quota, not money.
- **Cost, for API key users only.** A price table per model in `app/ingestion/pricing.py` with the date it was read; figures to verify against the pricing page in G10 before they ship: `claude-sonnet-5-5` at 2 USD per million input tokens, 10 output, 0.20 cache read; `claude-opus-5-5` at 4, 20 and 0.20. Low cost: the first appearance of each token at 1.25 times the input price (a cache write, assumption A8), every later appearance at the cache read price, plus the low output. High cost: every input token of the high range at the full input price (no cache hit at all) plus the high output. The dialog shows "between X and Y USD, stops at Z" where Z prices the bound at the full input price.
- **What the dialog shows:** the documents, characters and images that will be read, how many are reused at no cost, the model and why (subscription or API key), the number of steps, "about L to H tokens", "stops at B tokens", for an API key the cost range, and the limits (15 minutes per step, 60 minutes in all). After the run the page shows the real tokens and, for an API key, the real cost of every step, as any run does. Checkpoint G replaces `F`, the divisor 3 and the turn counts by the ratios measured on Harald's dossier.

### Limits
- Per file 20 MiB, per PDF 200 pages of text and 30 rendered pages, per document 500,000 characters, per paste 100,000, per user 100 MB and 200 documents.
- Per run: 30 documents, 1,500,000 characters, 60 images or rendered pages, 60 steps, 60 minutes, the sum of its steps' token budgets. Per step: 100,000 characters or 8 images, 40 turns, 15 minutes, its token budget, 20 refused items. Per tool call: 30,000 characters and 40,000 bytes read, one image, 50 items proposed; 2,000 items per run.

### Malicious files
- **Zip bombs:** DOCX and ZIP are opened with caps checked on the central directory before any entry is read and again while reading: 200 entries, 50 MiB uncompressed in total, 20 MiB per entry, a compression ratio of at most 100, no nested archive, no path used for anything but a name match.
- **Huge or hostile PDFs:** page cap before extraction, character cap during it, the child's memory, CPU and wall limits, pypdf 6.20.0's own limit of work per stream, any exception is "could not be read".
- **XML bombs:** `defusedxml` forbids DTDs, entities and external references.
- **Macros and active content:** never executed; `vbaProject.bin` is a refusal so the user knows why.
- **Wrong extension:** the type comes from the bytes; a PNG named `.txt`, a PDF named `.docx`, a polyglot with a PDF header and ZIP tail are tested.
- **Images and rendered pages:** the 25 megapixel guard read from the header, the one sniffed format allowed, decoded only in the sandbox child.

### Privacy
- Logs carry ids, sizes, counts, statuses and rule names, never a file name, an excerpt, a value or text; tests assert it on the captured log of every flow.
- Nothing is written to disk outside Postgres: no upload spool, no parser temporary file (`RLIMIT_FSIZE` 0), no document in the scratch directory, no SDK transcript, no text in Redis.
- Documents go to one place outside the app: the model, through the user's own credential (Harald's subscription token, a friend's own API key, SPEC-agents). Without a credential the page says what is missing and nothing is sent.
- **Consent (decision 6, finding N6).** `ingestion_consents(user_id, text_version, accepted_at)`. `POST /api/ingestion/runs` answers 409 `consent_required` with the current version while the user has not accepted the current text; `POST /api/ingestion/consent {version}` records it. The text, a constant with `CONSENT_VERSION` in code: what is sent (the text and page images of the documents selected, and the current profile sections without contact details), to whom (Anthropic, through your own subscription or API key), and that deleting a document here does not delete what the provider has already received. The first start shows the text with an unticked checkbox; later starts show one line, "Your documents are sent to Anthropic through your own credential." A new version of the text asks again.
- Text matching common secret patterns sets `secret_warning`; extraction refuses the document until the user confirms or deletes it (spec). The pattern set is a small port of gitleaks default rules (MIT licence, credited next to the file).
