# Tasks: ingestion

Spec: [SPEC-ingestion.md](../../SPEC-ingestion.md). Depends on agents (A1 to A4: credentials, the runner, proposals, the fake backend) and profile (P1 to P6: section models, save with revisions, completeness, the diff helpers of the History drawer).

Task ids use the prefix `G` (inGestion): `I` is identity, `P` profile, `J` jobs, `A` agents, and the platform tasks are plain numbers. Branches are `ingestion/g<n>-<slug>`.

## Architecture decisions

### Storage of uploads
- **Postgres, not a volume.** `ingestion_documents` holds the bytes (`bytea`) and the extracted text, as the profile photo does (tasks/profile/todo.md). Reason: one place to scope by user, `on delete cascade` from `users`, a hard delete that is one transaction together with the proposals it touches, nothing shared on disk between the api and the worker, and the worker's `/tmp` is a 128m tmpfs counted in its memory limit (compose.yml), which thirty files could not fit.
- **Bytes live only until the text exists.** Once a document's text is stored (`text_status = done`), its `bytes` are set to null in the same transaction. Text formats never store bytes at all. An image keeps its bytes until a run transcribes it. A document whose extraction failed loses its bytes at once and keeps only its name, size, hash and the reason. Reason: the text is all a run, a citation check and the preview ever read, so the original is the one copy nobody needs, and the smallest database is the most private one.
- **Limits:** 10 MiB per file (the edge limit of `caddy/Caddyfile` as merged, so no Caddy change and at most about 30 MiB held by the api while one upload is hashed and stored; the spec said 20 MB), 100 MB per user counted as stored bytes plus text, 500,000 characters of text per document, 100,000 characters per paste, 200 pages per PDF, 200 documents per user. Over a limit: 413 or 422 naming the limit. At most two uploads are processed at once per api process (a semaphore, as `photo.DECODE_SLOTS`).
- **Upload shape:** the raw request body with the name in `X-Filename` (RFC 5987), as `PUT /api/profile/photo` does (`_limited_body` checks Content-Length, then the stream). No multipart parser is added. The name is display only: control characters and path separators stripped, 200 characters at most, never used as a path.
- **Per user isolation:** every query filters on the session's user id, another user's document answers the same 404 as a missing one, dedupe is `unique(user_id, sha256)` so it never reveals another user's upload, and `Cache-Control: no-store` on every route.
- **Lifetime and deletion:** a document's text stays until the user deletes it (reruns and the citation view need it); deletion is a hard delete in one transaction with its effects on items, proposals and events (spec, Documents). Deleting the account cascades. Open question 2 asks Harald whether text should also expire by itself. Database backups (`deploy.sh backup`, 14 kept) still hold a deleted document until they rotate: open question 3.

### Text extraction per file type
- **Type from the bytes, never from the name or the Content-Type.** `%PDF-` is a PDF; `PK\x03\x04` is a ZIP, which is a DOCX when it holds `[Content_Types].xml` and `word/document.xml`, else a LinkedIn export when it holds the known CSV names at its root, else refused; the PNG and JPEG magic of `profile.schemas.sniff_photo`; anything else must decode as UTF-8 (a BOM accepted, UTF-16 with a BOM accepted) without NUL bytes and is then text (TXT, MD, JSON, CSV alike). Refused with 415 and one sentence: legacy `.doc` (OLE magic), RTF, ODT, HEIC, GIF, WebP, executables, encrypted PDFs, a `.docm` or any DOCX carrying `word/vbaProject.bin`.
- **PDF text: `pypdf==6.19.0`** (pure Python, BSD 3 Clause, wheel `py3-none-any`, no dependency on Python 3.12, released 2026-09-16; 6.20.0 came out on 2026-10-09, one day before this plan, so the previous release is pinned as the agents plan did for the SDK). Source: pypi.org/pypi/pypdf/6.19.0/json (no advisory listed) and pypdf.readthedocs.io (security page: "We consider it the task of the library user to catch exceptions which could cause their service to crash", and the reading limit `root_object_recovery_limit`). `PdfReader(strict=False)`, `page.extract_text()` page by page, stopping at the page cap and the character cap.
- **DOCX text: the standard library plus `defusedxml==0.7.1`** (pure Python, PSF licence, wheel `py2.py3-none-any`, no dependency, released 2021-03-08; pypi.org/pypi/defusedxml/0.7.1/json, no advisory listed). `zipfile` opens the archive, `defusedxml.ElementTree` parses `word/document.xml`, the headers and the footers, and a small walker emits the text of `w:t`, `w:tab`, `w:br` and paragraph ends in document order, tables included. Rejected: `python-docx==1.2.0` (MIT, needs `lxml`, a compiled XML stack we would not configure ourselves, for a feature set, styles and writing, that ingestion does not use). Macros are never run by either approach: a DOCX is read as XML only.
- **ZIP (LinkedIn export):** `zipfile` from the standard library, each known CSV becomes a document of its own; every other entry is ignored.
- **Images (PNG, JPEG): no local OCR.** The model transcribes them inside the run (decision below). Pillow (`pillow==12.3.0`, already a dependency) checks and downscales them.
- **PDF pages without a text layer** are not read in the first version: the document is marked failed with "This PDF has no text layer. Upload screenshots of its pages or a text version." This is the spec's "ask first" on a rendering dependency, put to Harald as open question 1 with the verified options.
- **Where it runs: in the worker, in a child process.** PDF, DOCX and ZIP are parsed by `python -I -m app.ingestion.sandbox`, started by a new arq queue `jobapp:ingestion` (`max_jobs=1`) in the existing worker container. The child reads the bytes on stdin, answers JSON on stdout, gets an empty environment, and limits itself before importing any parser: `RLIMIT_AS` 768 MiB, `RLIMIT_CPU` 45 s, `RLIMIT_FSIZE` 0, `RLIMIT_NOFILE` 16; the parent kills it after 60 s. Reason: pypdf's own documentation leaves crashes, loops and memory to the caller, the api container has 512m and must not parse hostile files, and the worker has 1536m of which two agent runs take about 400 MiB at peak (A2 measurement) and a sweep the rest of its share, so one parser child capped at 768 MiB of address space fits. G2 measures the real peak on the fixtures and records it here.
- **Text formats and pastes** are decoded in the api at upload (no queue): normalised to NFC, `\r\n` to `\n`, control characters removed, capped.

### What the agent may read, and how
- **No built-in tool, not even `Read`.** The runner as merged starts Claude Code with `tools=[]`, lists `Read` in `FORBIDDEN_TOOLS` and gates every call (`app/agents/runner.py`); ingestion keeps all of that unchanged. The agent reads through in-process app tools only: `list_documents`, `read_document(document_id, offset)` (at most 30,000 characters per call, returned under the key `untrusted_text` with `next_offset`), `get_profile_section` (the existing tool, contact details and the board list still left out) and, for images, `view_document_image(document_id)`, which returns an image content block built from the stored bytes (Pillow, 25 megapixel guard, longest side 1568 px, re-encoded).
- **Why not the scoped `Read` the agents plan reserved for ingestion:** (1) SPEC-agents lists filesystem tools under "ask first"; (2) `FakeBackend` answers any tool that is not an app tool with "No such tool available", so a `Read` based flow could not be covered by CI, against success criterion 4; (3) files would have to be written into the 128m tmpfs; (4) verified on code.claude.com/docs/en/tools-reference: `Read` reads a PDF whole only up to 10 pages, and "Page-range reads render pages with `pdftoppm` from poppler-utils", so it would not have spared the rendering dependency either. The scoped `Read` stays the documented fallback if the image tool fails its real CLI check in G8.
- **Verified SDK facts this rests on:** an in-process tool may return image blocks (`claude_agent_sdk/__init__.py` of the pinned 0.2.163: "Text and image blocks pass through", binary embedded resources such as a PDF are skipped); MCP tool output is capped by `MAX_MCP_OUTPUT_TOKENS` ("default: 25000", warning above 10,000 tokens, "image content from those tools is still subject to this variable", and "a successful text result longer than 50,000 characters ... is saved to a file", which an agent without `Read` could never open: hence 30,000 characters per `read_document` call); `dontAsk` denies everything not allowed (code.claude.com/docs/en/env-vars and /permissions, read 2026-10-10). To verify in G8 through the real bundled CLI against `tests/anthropic_stub.py`: that an image block returned by an app tool reaches the model request as an image and how its size counts against `MAX_MCP_OUTPUT_TOKENS`.
- **Scratch directory and session persistence:** nothing new. As built in A2 every run gets a scratch directory on the tmpfs holding `HOME`, `CLAUDE_CONFIG_DIR` and the temporary files, `CLAUDE_CODE_SKIP_PROMPT_HISTORY=1` stops transcripts and prompt history (the Python SDK has no `persistSession` option), and the directory is deleted on every path. Ingestion writes no document into it.
- **One run is one document part, not one long session.** The runner executes one SDK session per `agent_runs` row with the definition's fixed `max_turns` and `wall_time_s`; it has no sub-runs, and `Agent` and `Task` are forbidden tools. So an ingestion run is a row of `ingestion_runs` plus ordered `ingestion_run_steps` (one per document part of at most 200,000 characters, cut at a paragraph end), each step an ordinary `agent_runs` row of the agent `profile_extract` (`claude-opus-5-5`, effort medium, 40 turns, 15 minutes) queued on the existing agents queue. When a step's run ends, an `advance(ingestion_run_id)` function, idempotent, called by the runner's end hook and by a cron every minute, queues the next step or runs the merge. Reason: it reuses the runner, the two slots, the reapers and cancel as merged; a worker restart loses one step, not the hour; and the context of one session stays small. The whole ingestion run is limited to 60 minutes and 30 documents.
- **The merge is code, not a model call.** Steps write checked candidates into `ingestion_items`; a deterministic merge turns them into `proposals` (dedupe, conflicts, comparison with the profile). Reason: cheaper, testable without a model, and the same input always gives the same proposals.

### Proposal kinds and targets
- **One kind, reusing the table as built in A3:** `proposals` rows with `target = "profile"`, `target_id = null`, `kind = "profile_item"`, `run_id = null` (a merge is not an agent run) and `payload = {ingestion_run_id, section, key, action, value, value_hash, citations[], base_revision, flags[], conflict?}`. `proposals.create` is called as is: with a null `target_id` it takes no lock and supersedes nothing, so ingestion supersedes its own older pending items itself.
- **Stable keys per section** (spec): identity field name, or `languages:<name>`, `links:<label>`; experience `employers:<key>` or `education:<school>:<start>`; facts `blocks:<title>`; skills `years_experience`, `<have|adjacent|none>:<name>`, `gates:<name>`; search field name, `boards:<ats>:<org>`, `never_apply:<hash>`; answers field name or `work_authorization:<country>`. Never proposable: `search.sweep_schedule` (it would start scheduled sweeps), the photo, and anything outside the six section models.
- **Accepting dispatches on the target.** `proposals.accept` as merged only knows the two job kinds and marks a proposal without a job invalid ("The job no longer exists"). G4 makes it dispatch on `target`: a profile item is applied to the current section under the profile row lock, the result validated by the section's Pydantic model, saved through `profile.service.save_section` (one revision), `edited_value` validated the same way. `POST /api/ingestion/runs/{id}/accept-section` applies several items in one save. Locked items (identity contact fields and languages, all of experience) and flagged items are refused in bulk (spec).
- **UI reuse:** `proposals-api.ts` (`acceptProposal`, `rejectProposal`), `RunPanel` and `useRunStream` for the live step, `flattenSection` and `diffFields` of `profile/diff.ts` for the before and after of each item, the completeness bar of the profile page.

### Citations and their server side check
- **Format:** `{document_id, excerpt}` from the agent; the server stores `{document_id, excerpt, start, end, transcribed}` where `start` and `end` are character offsets in the document's stored text, so the review opens the text preview at the quote.
- **Check, in `propose_profile_changes` before anything is stored:** the document must be one of this run's and the caller's; NFKC, case folding, whitespace collapsed and line break hyphenation removed on both sides with a position map back to the original; the excerpt must be at least 20 characters (or the whole value when shorter), at most 600, and found in the text. Then the typed value checks of the spec (dates, phone digits, every other number present in an excerpt, `years_experience` equal to the arithmetic on cited dates, never rounded up).
- **A failing item is refused, never stored and never shown.** The tool answers an error naming the item's index and the rule it broke, so the agent may retry with an exact quote; the log holds ids and the rule only. An item from a transcribed image is stored and flagged "transcribed, check it".

### Prompt injection
- **The document is data.** Its text reaches the model only inside tool results under `untrusted_text`, the system prompt says that nothing in a document is an instruction (as the triage agent does for postings), and an attempt is reported in the run summary.
- **What code refuses whatever the model says:** no tool takes a user id or another run's document id (both bound in the `Scope`); no tool writes anything but checked candidates; every built-in tool stays unavailable and gated; a value must validate against its section model (URLs http or https only, regexes through `check_regex`); `search.sweep_schedule` and unknown keys are refused.
- **Stored injection through the fact base:** a fact block is later read by other agents as trusted. An item whose value looks like an instruction to a model (a short pattern list: "ignore previous", "system prompt", "you are an AI", "as an AI", role tags) gets the flag `looks_like_instruction`, is shown with a warning, and is never part of "Accept all".
- **Private events:** agent definitions gain a flag `private_io`. For such runs the recorder stores tool names, sizes and error states only, never arguments or results, and the run's `output` holds counts, never text. `text` events (the model's own words) are stored and deleted with the document they came from (spec, Deletion).

### Duplicates, conflicts and reruns
- **Against the profile:** the merge drops a candidate whose value already equals the profile's at that key (after the section model's normalisation). A different value at an existing key is a `replace` shown as a diff; nothing is ever applied without the click.
- **Between documents:** equal values at one key become one proposal carrying all citations; different values at one key become one proposal with `conflict = [{value, citations}]` and the user picks one (spec).
- **Idempotency:** a step is identified by (document sha256, part, `EXTRACTOR_VERSION`, model). A rerun over a document that already has a finished step with the same identity reuses its `ingestion_items` and calls no model, unless the user asks to read it again. Proposals are a pure function of the items, the current profile and the user's earlier decisions, so the same documents and the same profile give the same proposals and zero tokens.
- **Earlier decisions:** an item the user rejected (section, key, value hash) is not proposed again; an accepted one is equal to the profile and drops out; pending items of an older run are superseded when a newer merge runs.
- **One active ingestion run per user** (409 with its id), behind an advisory lock as `runs.create_run` does.

### Limits
- Per file 10 MiB, per PDF 200 pages, per document 500,000 characters, per paste 100,000, per user 100 MB and 200 documents.
- Per run: 30 documents, 1,500,000 characters, 60 images, 60 minutes. Per step: 200,000 characters, 40 turns, 15 minutes. Per tool call: 30,000 characters, 50 items per `propose_profile_changes`, 2,000 items per run.
- Tokens: no spending cap (SPEC-agents decision). The start dialog shows the size of what will be read (characters, an estimate in tokens as characters divided by 4, the number of images); every step shows its tokens and cost as any run does.

### Malicious files
- **Zip bombs:** DOCX and ZIP are opened with caps checked on the central directory before any entry is read and again while reading: 200 entries, 50 MiB uncompressed in total, 20 MiB per entry, a compression ratio of at most 100, no nested archive, no path used for anything but a name match.
- **Huge or hostile PDFs:** page cap before extraction, character cap during it, the child's memory, CPU and wall limits, encrypted files refused, any exception is "could not be read".
- **XML bombs:** `defusedxml` forbids DTDs, entities and external references.
- **Macros and active content:** never executed; `vbaProject.bin` is a refusal so the user knows why.
- **Wrong extension:** the type comes from the bytes; a PNG named `.txt`, a PDF named `.docx`, a polyglot with a PDF header and ZIP tail are tested.
- **Images:** the 25 megapixel guard and decode slots of `profile/photo.py`, decoded with the one sniffed format allowed.

### Privacy
- Logs carry ids, sizes, counts, statuses and rule names, never a file name, an excerpt, a value or text; tests assert it on the captured log of every flow.
- Nothing is written to disk outside Postgres: no upload spool, no parser temporary file (`RLIMIT_FSIZE` 0), no document in the scratch directory, no SDK transcript.
- Documents go to one place outside the app: the model, through the user's own credential (Harald's subscription token, a friend's own API key, SPEC-agents). Without a credential the page says what is missing and nothing is sent.
- Text matching common secret patterns sets `secret_warning`; extraction refuses the document until the user confirms or deletes it (spec). The pattern set is a small port of gitleaks default rules (MIT licence, credited next to the file).

### The laptop-analysis prompt
- **Where:** `api/app/ingestion/prompts/laptop_dossier.md`, one template with a Claude Code and a Codex preamble, served filled by `GET /api/ingestion/prompt` (the user's name and an output folder; the folders to analyse stay placeholders the user fills on their machine).
- **Versioned:** a `PROMPT_VERSION` integer in the file's front matter, returned by the endpoint with the file's SHA-256 and written by the prompt into the dossier's first line (`dossier-format: <n>`), so a dossier says which prompt made it. A test fails when the template changes without the version.
- **It must never ask the user to collect:** secrets, tokens, API keys, passwords, `.env` files, SSH, AWS or GPG folders, key and certificate files, keychains, password managers, browser profiles, history or cookies, mail, messages, photos, other people's personal data, or anything outside the folders the user listed. It is read only outside the output folder, with no network, no install and no git push, and it ends with the optional `gitleaks` pass and a reminder to read the dossier before uploading. A test asserts each of these lines is present.
- The page states that Claude Code or Codex sends what it reads to its own provider under the user's own account.

## Open questions for Harald
1. **A PDF without a text layer (a scanned CV): what should the first version do?**
   - a. Recommended: refuse it with a clear message and ask for screenshots of the pages (PNG or JPEG, which the model transcribes) or a text version. No new dependency.
   - b. Add `pypdfium2==5.14.0` (free, arm64 wheel, 3.7 MB) to render pages to images inside the sandboxed child, then transcribe them like screenshots. One more compiled parser of hostile files, one more task of size S.

2. **How long does the app keep the text of an uploaded document?** (The original bytes are dropped as soon as the text exists, in every option.)
   - a. Recommended: until you delete it, as the spec says. Reruns and "show me where this comes from" keep working.
   - b. Deleted by itself 30 days after its last run, with the date shown; a later rerun needs a new upload.
   - c. Deleted as soon as you finish the review of a run; accepted items keep "source deleted".
3. **Backups keep a deleted document for up to 14 nightly dumps. Is that acceptable?**
   - a. Recommended: yes, and the delete dialog says so ("gone from the app now, from backups within 14 days").
   - b. Leave the documents' text and bytes out of the backups (`pg_dump --exclude-table-data`): deletion is immediate everywhere, but a restore loses every uploaded document (accepted profile content is kept).
   - c. Keep them in backups and shorten `BACKUP_KEEP` for everything.

## G7: Reruns, idempotency and deleting a document
**Acceptance:** a rerun reuses the items of unchanged documents (same sha256, part, `EXTRACTOR_VERSION`, model) and calls the model only for new ones, with a "read again" choice per document; rejected items (section, key, value hash) are never proposed again, accepted ones drop out as equal to the profile, pending items of the older run are superseded by the newer merge; the hard delete of a document in one transaction: its items gone, its citations stripped from proposals of every status, a pending proposal left without citation deleted, accepted ones showing "source deleted", rejected and superseded ones keeping only section, key and value hash, every `agent_events` row of the steps that read it deleted, the step rows kept with ids, status, tokens and cost; the delete dialog saying what will happen (and the backup sentence per question 3); the UI showing "deleted" for a document id that is gone.
**Edge cases to test:** the same documents and profile run twice (identical proposals, zero model calls, asserted on the fake backend's call count); one document added (only its step runs); a rejected item whose value changed in a new document (proposed again); a rejected item whose only source is deleted then uploaded again (still not proposed); `EXTRACTOR_VERSION` bumped (everything is read again); deleting a document during its own step, during the merge, while its proposal is being accepted in another tab; deleting the only source of a pending item and one of two sources; deleting a document cited by an accepted locked item; account deletion (documents, runs, steps, items, events and proposals gone); a database dump after deletion holding none of the document's text (searched for a marker string).
**Playwright journey:** run on two documents, reject one item and accept another, upload a third document and run again: only new items appear and the rejected one does not come back; delete the first document: its pending items disappear, the accepted item shows "source deleted", and the run page shows the document as deleted.
**Scope:** M. **Depends on:** G5. Parallel with G6 and G8 (G6 owns the review components, G7 the services and the delete dialog).
