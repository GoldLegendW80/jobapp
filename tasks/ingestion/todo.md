## Decisions of the owner (Harald, 2026-10-10)
Taken through direct questions on 2026-10-10.
1. **A PDF without a text layer is not refused.** Its pages are rendered to images with `pypdfium2==5.14.0` inside the sandboxed parser, then transcribed by the model like screenshots (G8 renders, G14 transcribes).
2. **Document text is kept until the user deletes it.** No expiry.
3. **Backups keep 7 nightly dumps instead of 14, for everything** (T10), and the delete dialog says: "Gone from the app now, and from the server's backups within 7 days."
4. **The profile accepts a year alone (`YYYY`) as well as a month (`YYYY-MM`)** for employer and education dates (P7). The agent proposes exactly what the document says, never an assumed month.
5. **Model by credential.** A run on a subscription credential uses `claude-opus-5-5`; a run on an API key credential uses `claude-sonnet-5-5` automatically. The start dialog shows a token range before the run and, for API key users, a cost range.
6. **Explicit consent the first time** a user starts an ingestion run: a checkbox, recorded with the date and the version of the text shown, saying that the documents are sent to Anthropic through the user's own credential. Afterwards the start dialog shows a one line reminder.
7. **20 MB per file**: the Caddy limit is raised for the upload route only, and the parser's memory and the per user quota are sized by measurement (G1, G2a, G2b, G8).
8. **A failing citation is refused to the agent with the reason**, not dropped silently, with a retry budget per step and the refused count shown to the user.
9. **The parsers run in a separate `parser` compose service from the start**, not as a child of the worker: the same image, its own unprivileged uid, its own PID namespace, no `CREDENTIALS_KEY`, no model credential, and no network beyond what it needs to receive work and return results (G2a).
10. **Token ceiling.** A run pauses when it has used twice the high estimate shown in the start dialog. An explicit Continue by the user raises the ceiling by one more high estimate and is recorded. It applies to every user, subscription included, and is enforced in code at the level of the run, between steps and inside a step.

**Defaults decided by the orchestrator (2026-10-10)**, which the owner may change later:
- A date written with a two digit year ("09/21", "Jan '23", the school year "2019-20") is refused and reported to the user, never guessed, unless the same document gives the four digit year for the same period.
- Model by credential applies to the two ingestion agents only: triage and chat stay on `claude-opus-5-5`.
- "Within 7 days" is a promise about the server: a dump pulled to the Mac with `./deploy.sh backup --pull` is the owner's to delete, and the dialog says "the server's backups".
- A rejected fact block may come back under another title after "read again" or a new extractor version; the dialog warns.
- **A file whose reader does not exist yet is stored, not refused** (chosen for G1 on 2026-10-10, written here after the review of PR #98). A PDF, a ZIP, a PNG or a JPEG uploaded before its parser ships is kept with `text_status = pending` and its bytes, and the list says "This version cannot read PDF files yet. Your file is kept, and it will be read as soon as it can." 415 is for the types that are never read. `READABLE_KINDS` in `api/app/ingestion/documents.py` is the one list of the kinds that have a reader: text alone after G1, then one kind more with each of G2b, G7 and G8. The reason: a refused file would have to be found and added again several task groups later, a kept one is read on the day its reader ships. The costs, accepted: private files sit unused in the production database and in its backups until their reader ships; they count in the user's 100 MB, so a user can fill the quota with files nothing reads yet; and a ZIP that is neither a DOCX nor an export is kept "to be read" only to fail when G7 opens it.

## Architecture decisions

### Storage of uploads
- **Postgres, not a volume.** `ingestion_documents` holds the bytes (`bytea`) and the extracted text, as the profile photo does. Reason: one place to scope by user, `on delete cascade` from `users`, a hard delete that is one transaction together with the proposals it touches, and nothing shared on disk between containers.
- **Bytes live only until the text exists.** Once a document's text is stored (`text_status = done`), its `bytes` are set to null in the same transaction. Text formats never store bytes at all. An image, and each rendered page of a scanned PDF, is kept as a small normalised JPEG in `ingestion_images` until a run transcribes it, then deleted.
- **How pages are kept (migration 0011, complete for every later task).** `ingestion_documents.text` holds the pages of a PDF in order, joined with a form feed (U+000C); a page that waits for its transcription is the empty string between two form feeds. `ingestion_images.position` is the zero based page index of a PDF page, and 0 for an uploaded image. `store_transcription` writes `ingestion_images.text`; when the last image of a document has its text, the page slots are filled (form feeds inside a transcription are replaced by line breaks first) and the images are deleted. Citation offsets index into `text` as stored, form feeds included; normalisation treats a form feed as whitespace. The same table carries `note text null` (what was not read and why, on a document that is not failed), `truncated bool`, `pages_text int null` and `pages_image int null` (shown per document as "12 pages read as text, 3 as images", so a user can see a scan that was taken for text), `parser_version smallint`, `failed_reason`, `failed_kind` and `attempts`.
- **A failed document keeps its bytes for one retry, then loses them.** A parse that failed for a reason of the server (the wall limit, the parser service down or restarted, the queue down) is queued again once by the reaper while its bytes are still there. After the second failure, or after a failure caused by the file itself (a password, a zip bomb, no readable page), the bytes are deleted and the row keeps its name, size, hash and the reason. **All of this applies to the kinds in `READABLE_KINDS` only.** A row whose kind has no reader yet (stored by G1 before its parser shipped) is never queued, never failed and never stripped of its bytes: it waits, as the page promised. The reaper takes the `pending` rows of readable kinds, the old ones included: on its first tick after a deploy that adds a kind to the list, it queues the rows that were waiting for that kind. `ingestion_documents.pending_since` (set at upload, at a replacement and at each new try; a replaced row keeps its `created_at`) is how it tells a row queued a moment ago from one that was lost.
- **An upload that matches a failed document replaces it**, and so does one that matches a `done` document carrying a `note` and parsed by an older `PARSER_VERSION` (a PDF whose scanned pages G2b could not read yet is read again once G8 has merged). Otherwise the dedupe `unique(user_id, sha256)` returns the existing row with 200. A replacement stores the new bytes on the same row (same id), sets it back to `pending`, clears the reason and the note and queues it again: 201. A replacement empties the old text and page images as a deletion does, so it asks the delete guards first (G1): a row a guard protects is returned as it is, with 200.
- **Limits:** 20 MiB per file (20,971,520 bytes, shown as "20 MB"), 100 MB per user counted as bytes currently stored plus text plus images, 500,000 characters of text per document, 100,000 characters per paste, 200 pages per PDF read as text, 30 pages per PDF rendered as images, 200 documents per user. Over a limit: 413 or 422 naming the limit. The quota check and the insert run under a per user advisory lock. At most two uploads are processed at once per api process (a semaphore, as `photo.DECODE_SLOTS`).
- **The edge limit is raised for one route only.** `caddy/Caddyfile` keeps 10 MiB everywhere and accepts 20 MiB on `POST /api/ingestion/documents` alone: a matcher on that path and method, `request_body` and the Content-Length check each in two variants, validated by `caddy validate` in the image build. Owner: G1.
- **Upload shape:** the raw request body with the name in `X-Filename` (RFC 5987), as `PUT /api/profile/photo` does. No multipart parser. The name is display only: control characters and path separators stripped, 200 characters at most, never used as a path; a name that decodes to nothing becomes "Untitled".
- **Per user isolation:** every query filters on the session's user id, another user's document answers the same 404 as a missing one, dedupe is per user, and `Cache-Control: no-store` on every route.
- **Lifetime and deletion:** a document's text stays until the user deletes it; deletion is a hard delete in one transaction with its effects on items, proposals and events ("Failure rules"). Deleting the account cascades. The server's backups hold a deleted document for at most 7 days (T10). Postgres keeps a deleted row in dead tuples until autovacuum reuses the page: accepted, a dump never contains dead tuples, and the dump test of G15 is the check.

### Text extraction per file type
- **Type from the bytes, never from the name or the Content-Type.** `%PDF-` is a PDF; `PK\x03\x04` is a ZIP, which is a DOCX when it holds `[Content_Types].xml` and `word/document.xml`, else a LinkedIn export when it holds the known CSV names at its root, else refused; the PNG and JPEG magic of `profile.schemas.sniff_photo`; anything else must decode as UTF-8 (a BOM accepted, UTF-16 with a BOM accepted) without NUL bytes and is then text. Refused with 415 and one sentence: legacy `.doc`, RTF, ODT, HEIC, GIF, WebP, executables, a `.docm` or any DOCX carrying `word/vbaProject.bin`. The api only looks at magic bytes: it decodes no image and parses no archive.
- **PDF text: `pypdf==6.20.0`** (pure Python, BSD 3 Clause, wheel `py3-none-any`, released 2026-10-09). Pinned although it is one day old: its changelog carries the security change "Limit work per stream (filter count, accumulated decoding work)" and "Flatten the page tree iteratively", which are this module's own hostile cases, and every pypdf advisory of September 2026 is patched at or before 6.19.0. G2b checks PyPI again when it starts and takes a 6.20.x fix release if one exists. `PdfReader(strict=False)`, `page.extract_text()` page by page, stopping at the page cap, the character cap and the time budget. The URIs of a page's link annotations are appended to that page's text on a line "Links: ...".
- **`cryptography` is never imported by the parser.** Verified on 2026-10-10: importing pypdf 6.20.0 imports `cryptography` when it is installed, and with `sys.modules["cryptography"] = None` set first pypdf falls back to its own provider (`local_crypt_fallback`), which reads RC4 and not AES. The parser's `main.py` sets that line before importing pypdf. So the parser needs no `OPENSSL_armcap` and `compose.mac.yml` gets no entry for it.
- **Encrypted PDFs:** the empty user password is tried first, since many CVs are exported with print or copy restrictions. RC4 files are read by pypdf (G2b). AES files are opened by PDFium, which reads their text layer itself (G8; assumption A8). Until G8, and for a file that needs a real password: failed with "This PDF is protected. Remove the protection and export it again.", and a later upload replaces the row.
- **DOCX text: the standard library plus `defusedxml==0.7.1`** (pure Python, PSF licence, no dependency). `zipfile` opens the archive, `defusedxml.ElementTree` parses `word/document.xml`, the headers and the footers, and a small walker emits the text of `w:t`, `w:tab`, `w:br` and paragraph ends in document order, tables included. Three rules: a `w:hyperlink` with an external target in `word/_rels/document.xml.rels` is emitted as "text (url)"; of an `mc:AlternateContent` only `mc:Choice` is read; `w:delText` is left out and `w:ins` is read. Rejected: `python-docx==1.2.0` (needs `lxml`).
- **ZIP (LinkedIn export):** each known CSV becomes a document of its own, named "<archive name>: <file name>"; every other entry is ignored; the row of the archive itself is deleted in the same transaction (uploading the archive again finds each CSV by its own hash).
- **Images (PNG, JPEG): no local OCR.** The model transcribes them inside the run. Pillow (`pillow==12.3.0`) decodes and normalises them in the parser, never in the api or the worker: 25 megapixel guard read from the header, EXIF orientation applied, RGB, longest side at most 1568 px, JPEG of at most 300,000 bytes (quality 80, 70, 60, 50, then the size reduced by 15 percent per step until it fits).
- **PDF pages without a text layer: rendered with `pypdfium2==5.14.0`** (released 2026-10-04, licence "BSD-3-Clause, Apache-2.0, dependency licenses", wheel `manylinux_2_17_aarch64` of 3,719,672 bytes, no dependency, no advisory on PyPI or on its GitHub repository on 2026-10-10). The rule is per page, with two triggers: the page's text holds fewer than 50 characters that are not whitespace, or it holds fewer than 200 and the page carries an image that covers at least half of it (a scan under a footer or a watermark; assumption A9, G8 says how PDFium reports it). At most 30 pages of one PDF are rendered (the rest named in `note`), each at a scale that puts its longest side at 1568 px, a page larger than 200 inches on a side or narrower than a tenth of its length is skipped, and each bitmap goes through the same JPEG normalisation. A PDF whose every page has text never loads PDFium. A text layer with an unusable character map yields garbage of any length, which no rule catches: the counts "N pages read as text, M as images" and the preview are what let the user see it.
- **Text formats and pastes** are decoded in the api at upload (no queue): normalised to NFC, `\r\n` to `\n`, control characters removed, capped.

### The parser service (decision 9)
- **A service of its own.** `compose.yml` gains a service `parser` that runs the image `jobapp-worker:latest` (no second image, no build section of its own; assumption A1; `compose.dev.yml` and `tests/compose.a2-e2e.yml`, which run the worker from `jobapp-worker:dev` and `jobapp-worker:a2-e2e`, give the parser the same override, and the dev file the same bind mount of the code) with `user: "10002:10002"`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `read_only: true`, no tmpfs, no volume, `pids_limit: 32`, a `mem_limit` (640m to start, then the measured figure), the restart policy of the other services, and an `environment` of its own listing only `PARSER_PORT`: no `env_file`, so no `CREDENTIALS_KEY`, no `SECRET_KEY`, no database or Redis address, no model credential. It has its own PID namespace and its own uid, so no file under `/proc` and no scratch directory of an agent run exists for it.
- **Network: one internal network, shared with the worker alone.** A compose network `parsing` with `internal: true`. The parser is attached to it and to nothing else; the worker is attached to `default` and to `parsing`. The parser therefore cannot open a connection to `db`, `redis`, the api or the internet, and nothing but the worker can reach it.
- **What it may read and write in Postgres and Redis: nothing.** The obvious shape, the parser consuming the `jobapp:ingestion` queue, was considered and turned down: it needs a route to Redis and to Postgres and a credential for each, a narrower database role is cheap but a narrower Redis is not (arq's keys are global, not per queue), and a parser that holds no credential at all is simpler to reason about. So the queue stays in the worker: the job `parse_document(document_id)` runs in the worker, reads the bytes from Postgres, sends them to the parser over the internal network, validates what comes back and writes it to Postgres itself.
- **Protocol.** One TCP connection per job to `parser:7070`: a JSON header line of at most 4 kB (`{kind, size, options}`), the bytes, then the answer as a JSON header line (`{ok, failure: file or server, length, ...}`) and a UTF-8 JSON body of exactly `length` bytes (the end of the body is the length, never the end of the stream). The server refuses a `size` over 20 MiB before reading a byte and gives up on a connection that sends nothing for 10 s. One job runs at a time; a second connection waits its turn, bounded by the worker's own 75 s; a `ping` is answered at once even while a job runs, so a parse of 60 s does not turn the service unhealthy. The worker reads at most 4 MiB of answer and waits at most 75 s. The parser serves nothing to a browser, now or later. `kind` is one of `pdf_text`, `docx`, `linkedin_zip`, `image`, `pdf_render`, `ping`. The worker treats the answer as hostile data: `json.loads` guarded against `ValueError` and `RecursionError`; the JSON shape; the caps (characters, pages, images, bytes per image); a text holding U+0000 or a lone surrogate refused (Postgres refuses both, and the job would fail in a loop); the number of form feeds equal to the pages minus one, and the counts consistent with each other; every image starting with the JPEG magic. A note comes as a code with integers (`{code: "pages_not_read", from: 31, to: 44}`) and the app writes the sentence: the parser never sends free text for the user. The worker never decodes an image or parses anything itself.
- **Two standalone files, no `app` import.** `api/app/ingestion/sandbox/server.py` is the service: standard library only (`asyncio.start_server`), started as `python -I /app/app/ingestion/sandbox/server.py`, one job at a time, non dumpable. It parses nothing: for each job it starts the child `[sys.executable, "-I", "/app/app/ingestion/sandbox/main.py", kind]` with an empty environment, the bytes on standard input and the answer on standard output. `python -I -m app.ingestion.sandbox` cannot work (`-I` implies `-P`, and `app` is not an installed package). `main.py` adds exactly one directory to `sys.path`, its own (owned by root and read only in the image), and imports the handler of `kind` from a fixed table; each handler is one file, so G2b, G7 and G8 add files and never edit the same one. `pypdf`, `defusedxml`, `pypdfium2` and Pillow come from the venv's site-packages (assumption A2).
- **Limits and hardening set by `main.py` itself, before it imports any handler** (not in `preexec_fn`, and because the dumpable attribute is reset by `execve`). Checked against getrlimit(2), prctl(2), core(5), proc(5) and the Python `resource` documentation:

| Limit | Value | Real effect for a Python child on Linux arm64 | What a test must prove |
|---|---|---|---|
| `RLIMIT_AS` | per kind, starting at 512 MiB, then the measured peak plus a margin (G2b, G8) | caps the address space: `brk`, `mmap` and `mremap` fail with `ENOMEM`, raised by Python as `MemoryError`. pypdf may swallow it and PDFium aborts on a failed allocation, so this limit alone does not end a job: the wall kill does. | a handler that allocates past the limit ends with the document failed, the service alive and the next job run |

The `ping` child reports `PR_GET_SECCOMP == 2` and the healthcheck requires it. On the Jetson (kernel 5.15, assumption A4) the filter installs. |

- **The answer is UTF-8, written to `sys.stdout.buffer`** (`json.dumps(..., ensure_ascii=False).encode("utf-8", "replace")`): an empty environment has no locale, and ASCII escapes would cost 6 to 12 bytes per character, so 500,000 characters outside the basic plane would pass the 4 MiB cap. In UTF-8 they are at most 2 MB. Rendering runs in batches of 8 pages per child (8 x 300,000 bytes in base64 is 3.2 MB).
- **Nothing of the document leaves Postgres and the two processes.** The arq job takes a document id and returns only a status word (arq keeps return values in Redis); the parser keeps nothing after a job (read only root, no tmpfs, `RLIMIT_FSIZE` 0).
- **What is left, stated.** The parser is now a container with no credential, no route out and no neighbour process to read. What an attacker who executes code inside a handler can still do: return wrong text or a hostile JPEG for the document being parsed (the worker checks shape and sizes, the user sees the text in the preview, and the JPEG goes to the model and to the owner's own browser); use the CPU and memory of the container up to its limits until the kill; and attack the kernel through the system calls the filter allows. The deny list is short on purpose (a deny list cannot be complete); the container boundary is the control.
- **Health, deploy, CI.** The compose healthcheck runs `python -I /app/app/ingestion/sandbox/server.py --check` (a `ping` job through the loopback, which starts a child and so proves the filter and the limits install). The worker stays healthy without the parser: a parse job that cannot connect fails as a server failure and the reaper queues it again once. `tests/compose_smoke.sh` and `tests/jetson_smoke.sh` gain the service in their lists (set of services, healthy, memory limit), `tests/compose_smoke.sh` asserts its hardening keys, its network and the absence of every secret in `docker inspect`'s environment. The deploy workflow and `deploy.sh` build and tag three images and need no change: the parser follows the worker's tag, forward and on rollback. CI's e2e stack starts it with the rest of `compose.yml`. Owner of all of it: G2a.
- **Memory.** Sum of the limits on the Jetson today: api 512, caddy 128, db 768, redis 256, worker 1536, tailscale 128, in all 3,328 MiB of 7,619. The parser adds 640 MiB at most, and the worker's own budget is no longer shared with a parser child (idle 145 MiB, one real run 308 to 333 MiB, two estimated at 525 to 625 MiB, A5). Idle, the service is one Python process with the standard library: about 15 to 25 MiB expected (assumption A5), to add to the idle table of `tasks/plan.md`.
- **What G2a and G2b measure, and where.** On the Mac and in CI, in the image: the child's peak resident memory and its CPU and wall time per fixture (a 20 MiB PDF full of images, a 200 page text PDF, a deeply nested one), the service's idle memory. On the Jetson, after the merge, by the orchestrator with a read only script that G2a writes and G2b extends with the PDF fixtures (`tests/ingestion_parser_jetson.sh`, which sends the generated fixtures to the deployed parser through the worker container): idle memory of the parser (`docker stats`), the cgroup's peak per fixture sampled every second as A5 did, CPU seconds and wall seconds per fixture and per page on the Cortex-A78AE (is 45 s enough for 200 pages), that the seccomp filter installs on the Tegra kernel, and the host's lowest available memory. `RLIMIT_AS`, the time budget and `mem_limit` are then set from those figures in a follow up commit, and all of it is written under "Measurements". G8 repeats the memory and time measurements for the image and render kinds.

### What the agent may read, and how
- **No built-in tool, not even `Read`.** The runner starts Claude Code with `tools=[]`, lists `Read` in `FORBIDDEN_TOOLS` and gates every call; ingestion keeps all of that. The agents read through in-process app tools only.
- **One step is bound to one document part, in code.** The step's `agent_runs.input` holds exactly four keys: `ingestion_run_id`, `step_id`, `token_budget`, and `script` (written only when the fake backend is on). Before the tools are built, the runner asks the agent definition's `bind` hook for the step's binding, and the tools close over it in the `Scope`: for an extraction step `{document_id, part, start, end}` (character offsets of the part in the document's text), for a transcription step `{document_id, positions}`. So no tool takes a document id, there is no `list_documents`, and a citation is `{excerpt}` alone: code attaches the document. A step whose binding is gone (the document was deleted) fails with "This document no longer exists." before any model call.
- **Tools of `profile_extract` (extraction):** `read_document(offset)` returns at most 30,000 characters and at most 40,000 UTF-8 bytes of the step's part, under the key `untrusted_text` with `next_offset` (null at the end of the part); `get_profile_section` (the existing tool); `propose_profile_changes(section, items[])`.
- **Tools of `document_transcribe` (transcription):** `view_image(position)` returns one image block, the stored JPEG, and only for a position of the step; `store_transcription(position, text)` may be called once per position, refuses a text over 20,000 characters for one image and a document over 500,000 in all, and stores the text of that image ("How pages are kept" says what happens at the last one). The system prompt asks for the text as it reads on the image and for a final answer of one line, so the model's `text` events hold a summary, not the document.
- **Why not the scoped `Read` the agents plan reserved for ingestion:** SPEC-agents lists filesystem tools under "ask first"; `FakeBackend` cannot replay a built-in tool, so CI could not cover it; files would go through the tmpfs; and `Read` renders PDF page ranges with `pdftoppm`. It is not used and not kept as a fallback.
- **The image path is proven (G0, `spike.py`, 54 cases through the real bundled CLI 2.1.286 and the pinned SDK 0.2.163 against `tests/anthropic_stub.py`, no model call):**
  1. An image block returned by an app tool is forwarded as an `image` content block inside the `tool_result` of the next request. JPEG and PNG, byte for byte up to 449 kB.
  2. `MAX_MCP_OUTPUT_TOKENS` counts an image as a flat 1,600 tokens whatever its bytes or pixels; with the default of 25,000, 15 images pass in one result and the 16th is cut.
  3. Above the limit nothing fails: the CLI replaces the image by a thumbnail (400 px or less) and adds a text block that starts with "[OUTPUT TRUNCATED". The limit must never be lowered: the runner leaves the variable unset, and a test of G14 asserts the forwarded image has the stored pixel size.
  4. The CLI recompresses a JPEG somewhere between 449 kB and 593 kB and resizes anything over 2000 px.
  5. **The binding constraint is the SDK:** the CLI echoes each tool result to the SDK as one JSON line holding the content twice, and the SDK's reader fails over 1,048,576 bytes. A 303,202 byte image makes a line of 808,722 characters, a 385 kB image passes, a 449 kB image ends the run. Hence one image per `view_image` call, each at most 300,000 bytes.
  6. Text results of 30,000 and 49,000 characters stay inline; one of 120,000 is replaced by an error naming a file under the scratch directory. Hence 30,000 characters per `read_document` call, and 40,000 UTF-8 bytes (assumption A6).
  7. `runner.result_text` turns an image block into "[image]", so no event stores image data.
- **What the spike does not prove: that a model reads a dense page at this size.** The API scales an image down before the model sees it (about 1.15 megapixels, so an A4 page at 1568 px on its long side arrives near 1270 by 900; assumption A7). G14 therefore includes one real transcription of a dense A4 scan on the Jetson. If it is not faithful, the fix is two tiles per page, which changes G8's renderer, the meaning of `position` and the limits of 30 and 60 images: that would be a new task, decided on the result.

### The run: steps, the chain and the merge
- **An ingestion run is a chain of steps, each an ordinary agent run.** A row of `ingestion_runs` plus ordered `ingestion_run_steps`, `unique(ingestion_run_id, position)`: first the transcription steps (one per document with images and per group of at most 8 images), then the extraction steps (one per document part of at most 100,000 characters, cut at a paragraph end). Each step is an `agent_runs` row of `document_transcribe` or `profile_extract` (40 turns, 15 minutes), queued on the existing agents queue.
- **Steps planned during the run.** The text of a transcribed document does not exist when the run starts, so its extraction steps are planned by `advance` when its transcription has finished. The estimate counts them in advance at 3,000 characters per image (assumption A10). A run has at most 60 steps: when planning would pass 60, the documents that do not fit are left unread, named in the summary, and the run ends partial.
- **Internal agents.** Both definitions carry `internal = True` (G6): refused with 422 by `POST /api/agents/runs` and absent from `GET /api/agents`. Their runs appear on `/runs` with names, sizes and tokens only.
- **Model by credential.** Both definitions say `model = claude-opus-5-5` and `model_by_credential = {anthropic_api_key: claude-sonnet-5-5}`, effort medium for both. The runner picks the model when it has revealed the credential (G6) and records it on the run, next to `agent_runs.credential_kind` (added by PR #71 of the agents module, nullable, written by the worker when it reads the credential), which the cost shown after a run reads: a step is priced only when its `credential_kind` is an API key.
- **`advance(ingestion_run_id)` moves the chain.** It runs in its own transaction, never inside the transaction that ends an agent run: the runner calls an `on_final` hook after it has recorded any final status, and a cron calls `advance` every minute for every run that is not final. It locks the `ingestion_runs` row `FOR UPDATE`, reads the steps and the status and tokens of their agent runs, and does exactly one of: record the result of the step that ended, plan the extraction steps of a document just transcribed, create and queue the next step, pause, merge, or finish. The `agent_runs` row of a step is created through `runs.create_run` and written to `step.agent_run_id` in that same transaction; the enqueue comes after the commit, and a failed enqueue is recorded with `runs.fail_queued` and pauses the run. It calls `merge.run`, a stub in `merge.py` until G12 replaces that file.
- **One active run per user is a constraint:** a partial unique index on `ingestion_runs(user_id)` where the status is `running` or `paused`. `POST /api/ingestion/runs` catches the violation and answers 409 with the id of the active run.
- **Steps count toward `ACTIVE_PER_USER` (4), and a run uses one slot at a time.** When the user already has four runs queued or running, `advance` leaves the step `planned`, records `waiting = "slots"` and tries again at the next tick. It never fails the ingestion run for that.
- **Lock order, for every path of this module**, consistent with the agents module: (1) the chat thread row, never taken here; (2) the `profiles` row; (3) the `ingestion_runs` row; (4) `ingestion_documents` rows in id order; (5) the `ingestion_run_steps` row; (6) the user's advisory run lock of `runs.create_run`; (7) the `agent_runs` row; (8) `proposals` rows in id order. Who takes what: accept and accept-section 2 then 8; `advance` 3, then 5, 6 and 7 to create a step, then 8 when it merges; cancel 3 then 7; a tool call during a step takes its document `FOR KEY SHARE` (4), then its step row (5), and inserts its items or its transcription, never the run row; deleting a document 3 (the user's active run, if any), 4, 7 (cancel of the step reading it), 8, so it waits for a tool call in flight and the tool call after it finds no document. Every path goes up the list. `test_ingestion_locks.py` (G10) runs each pair of paths that exists then against real Postgres from two connections; G12, G13 and G15 each add the pairs they create in a file of their own (`test_ingestion_locks_<task>.py`).
- **The merge is code, not a model call.** Steps write checked candidates into `ingestion_items`; a deterministic merge turns them into `proposals`.

### Failure rules
| What happens | Rule |
|---|---|
| A step fails on the credential or the provider: `NO_CREDENTIAL`, `UNREADABLE`, `REFUSED`, `BUSY`, `runs.QUEUE_DOWN`, or `API_ERROR` with any status other than 400, 413 and 422. G6 exports `runner.is_provider_failure(error)`. | The chain stops: the run becomes `paused` with that message, no further step is created. Finished steps keep their items. The user fixes the credential and clicks Resume, which runs the remaining steps, the failed one first. A paused run is still the user's one active run; it is merged with what finished and closed as partial after 24 hours without a resume. |
| The API refuses one step's request for its content: `API_ERROR` with 400, 413 or 422. | A content failure, as below: resuming would fail the same way. |
| A step fails on its own content: the turn limit, the 15 minutes, its technical token backstop, no result. | The step is `failed`, the chain goes on, and the summary names the document. |
| The run reaches its token ceiling (see "Tokens"), between two steps or inside one. | The run becomes `paused` with the reason `token_ceiling`. A step interrupted for it goes back to `planned` and keeps the items it stored. The user reads what was spent and clicks Continue, which raises the ceiling and is recorded, or Cancel. |
| The worker restarts during a step: the reaper fails the agent run with `INTERRUPTED`, `STOPPED`, `LOST` or `STALE`. | `advance` runs that step once more (`attempt = 2`). A second such failure is a content failure. |
| The 60 minutes of the whole run pass (`deadline_at`; time queued counts, a pause stops the clock). | `advance` requests the cancel of the running step, creates no further step and merges what finished: `done` with `partial = true` and the list of documents not read. |
| The user cancels the run. | Under the run row lock: `cancel_requested_at` set, cancel requested on the active agent run. When that run ends, `advance` sets `cancelled`. No merge; the items of finished steps stay and a later run reuses them. |
| The user cancels one step through `POST /api/agents/runs/{id}/cancel`. | The same as cancelling the ingestion run. |
| A document is deleted while its own step runs. | The delete transaction requests the cancel of that agent run, deletes the events it has written so far, sets `purge_events` on the step, and deletes the document, its images and its items. `advance` deletes the step's events again when the agent run reaches a final status, and the cron deletes them at every tick until five minutes after `finished_at`. The test asserts on `agent_events` after the step has ended and after one more tick. |
| A document is deleted during the merge or while one of its proposals is being accepted. | The delete waits for the run row or for the proposal row, then applies its rules to what it finds. |
| A document that a step has read is deleted before G15 has merged. | 409 "This document was read by a run and cannot be deleted yet." (a guard that G10 adds in a file of its own, `delete_guard.py`, registered in the list of guards that G1's delete consults, and that G15 removes, so `main` never deletes a document while leaving its excerpts in proposals and events). |
| Redis is down when `advance` enqueues. | `runs.fail_queued`, then the run is `paused` with "The agent queue is unavailable." |

### Proposal kinds and targets
- **One kind, reusing the table as built in A3:** `proposals` rows with `target = "profile"`, `target_id = null`, `kind = "profile_item"`, `run_id = null` and `payload = {ingestion_run_id, section, key, action, value, value_hash, citations[], base_revision, flags[], conflict?, depends_on?}`.
- **Stable keys per section** (spec): identity field name, or `languages:<name>`, `links:<label>`; experience `employers:<key>` or `education:<school>:<start>`; facts `blocks:<title>`; skills `<have|adjacent|none>:<name>`, `gates:<name>`; search field name, `boards:<ats>:<org>`, `never_apply:<hash>`; answers field name or `work_authorization:<country>`.
- **Settings are never proposable by the agent.** A setting is a choice of the user about how the app behaves, not a claim a document can support: `skills.gates[].penalty` (a proposed gate takes the default of 25), `search.min_fit`, `search.days`, `search.boards[].enabled`, `search.sweep_schedule`, and every `advanced` regular expression of a term list. Also never proposable: `skills.years_experience` (computed, below), the photo, and anything outside the six section models. G5's field type table gives every path of every section one type among `email`, `url`, `name`, `date`, `phone`, `text`, `term`, `enum` and `setting`.
- **Where a new entry goes.** `apply` inserts a new employer or school by `period_key` (P7), newest first, an open end before any dated one; other lists append.
- **Facts block keys are only as stable as the model's wording.** A rejected block can come back under another title when its document is read again. Success criterion 3 holds through the reuse of stored items, and the "read again" choice says so.
- **Accepting dispatches on the target.** As merged, `proposals.accept` reads `ProposalKind(proposal.kind)` first, so for a `profile_item` it raises `InvalidValueError(UNKNOWN_KIND)` and the proposal stays pending. G5 inserts the dispatch on `proposal.target` before that line: a profile item is applied to the current section under the `profiles` row lock, validated by the section's Pydantic model, saved through `profile.service.save_section` (one revision). `accept-section` applies several items in one save; locked and flagged items are refused in bulk. `reject-section` rejects several at once, with no exclusion.
- **UI reuse:** `proposals-api.ts`, `RunPanel` and `useRunStream`, `flattenSection` and `diffFields` of `profile/diff.ts`, the completeness bar.

### Citations: the checker, as normative tables that were executed
The agent gives `{excerpt}` per citation; the server stores `{document_id, excerpt, start, end, transcribed}` with character offsets in the document's stored text. The check runs in `propose_profile_changes` before anything is stored. `app/ingestion/citations.py` is a pure module: G4 implements this section and nothing else. **This section was run before it was committed:** `tasks/evidence/ingestion-g0/citation_rules.py` implements the rules as written here, and `citation_rules.txt` is its output on the 108 examples of the table below (108 as stated, 0 not). The script also asserts, on every example, that the cited span starts and ends on a token boundary. The script is throwaway code and the seed of G4's tests; where this text and the script differ, the script's behaviour on the examples is the reference and the text is corrected.

**Normalisation `N(text)`**, the same for the document text and for the excerpt. It works cluster by cluster (a character with the combining marks that follow it) and returns the normalised string and, for each character of it, the index of the cluster it came from. Order matters: the folds come before NFKC, which would otherwise consume two of the characters they fold.

| Step | What | Detail | The example that proves it fires |
|---|---|---|---|
| 1 | Fold apostrophes, quotes and dashes | U+2018, U+2019, U+201A, U+201B, U+2032, U+02BC, U+0060, U+00B4, U+FF07 become `'`. U+201C to U+201F, U+2033, U+00AB, U+00BB, U+FF02 become `"`. U+2010 to U+2015, U+2212, U+FE58, U+FE63, U+FF0D become the ASCII hyphen. | 1 (U+2019), 39 (U+00B4, which NFKC alone would turn into a space and a combining accent), 40 (U+2033, which NFKC alone would turn into two U+2032), 4 (U+2013) |

**Matching and anchoring.** The skeleton `S(x)` is `N(x)` without spaces, breaks and ASCII hyphens. An excerpt matches when `S(excerpt)` is a substring of `S(document)`, which forgives hyphenation and line breaks on both sides ("full-\nstack", "full-stack" and "fullstack" share a skeleton). A **token** of the document is a maximal run of letters, or a number run (digits that may hold, between two digits, one single character among space, ".", "," and "'"; a break is not a space). **The cited span never cuts a token:** among the occurrences of the excerpt, the first that starts and ends on token boundaries is taken; when there is none, the first occurrence is taken and its start and end are moved outwards to the boundaries of the tokens they fall in. So an excerpt that begins at the "5" of "3,5 ans" cites "3,5 ans", and one that begins at the second "1" of "11/2023" cites "11/2023" (examples 31 to 33). All value checks read the **cited span**, `N(document)[start:end]`, never the agent's typing.

**Length bounds**, in characters of `N(excerpt)`: at least 20 and at most 600, and `S(excerpt)` at least 12 characters. When `N(document)` is itself shorter than 20 characters, neither bound applies: the excerpt's skeleton must equal the document's (examples 26, 68, 69).

**Rules per field type.** `v` is the proposed value, `C` the cited spans of the item (one per citation).

| Rule | Field types | Check |
|---|---|---|
| V, address | `email`, `url` | Compared on `N` itself, spaces and hyphens kept, since a hyphen is part of an address: `N(v)` is a substring of one `c`, **bounded on both sides**. Before it: not a letter, a digit or one of ".", "_", "%", "+", "-", "@", "/". After it: not a letter, a digit or one of "_", "%", "+", "-", "@", and a "." or "/" there counts as punctuation only when what follows it is not a letter or a digit. For a URL, "http://", "https://" and "www." are removed from the value and from the span first, only where an address starts (not after a letter, a digit or an address character, so "awww.site.fr" keeps its letters), and the trailing "/" of the value. **Forms of a month next to its year (rule D).** Month words are whole words (a maximal run of letters) compared without accents: the English and French names, and the abbreviations jan, feb, mar, apr, jun, jul, aug, sep, sept, oct, nov, dec, janv, fev, fevr, avr, juil, juill. Only an abbreviation may carry a full stop ("janv. 2023"); a full name may not, so "may. 2023" is not May. **A month word belongs to the year that follows it, never to a year written before it, and nothing pairs across a break**: a line that ends with a year, followed by a line that starts with a month and its own year, is the layout of most CVs (examples 77 to 80). "sept" without a full stop or a comma is not a month when its year is followed by a word it would count ("sept 2021 collaborateurs", example 105).

**`skills.years_experience` is never proposed by the agent.** The merge computes it from the employers of the profile with this run's employer items applied: the union of the periods without overlap, in months, read at their shortest when a date is a year alone (a start `YYYY` counts from December, an end `YYYY` to January, and a period that comes out negative, such as a start and an end in the same year alone, counts zero), an open period ending at the month the run started, then `floor(months / 12 * 10) / 10`. It is proposed as a derived item, flagged `derived`, with `depends_on` naming the employer items it used, never part of "Accept all", and only when the profile has no value yet. It is shown stale ("check again") as soon as one of the items it depends on is rejected or accepted with an edit.

**Refusal and the retry budget.** A failing item is refused and never stored: the tool answers with the item's index and the rule it broke, never the text. Per step, in code: after 20 refused items, or at the third refusal of the same section and key, the answer for a failing item becomes "not accepted, do not retry this item"; passing items are still stored. A refusal of type `setting` does not count toward the 20. The step's `refused_count` is stored and the run summary shows it per document. Per call at most 50 items, per run at most 2,000.

**Instruction patterns** (a hint for the user, not a control): an item whose value or cited span matches one of "ignore previous", "ignore all previous", "ignore the previous", "ignore les instructions", "ignorez", "system prompt", "you are an AI", "as an AI", "tu es une IA", "vous êtes une IA", "en tant qu'IA" (compared without accents and case) carries `looks_like_instruction`, is shown with a warning and is never part of "Accept all" (examples 30, 76).

**Examples, produced by the script** (`python3 tasks/evidence/ingestion-g0/citation_rules.py --markdown`). Where a character matters the source is written with `\u` escapes; `\n` is a line break. Examples 31 to 47 are the counter examples of the second review, 77 to 108 those of the third. The identity in the examples is fictitious (an `example.org` address, a French number of the range reserved for fiction). ### Prompt injection
- **The document is data.** Its text reaches the model only inside tool results under `untrusted_text`, the system prompt says that nothing in a document is an instruction, and an attempt is reported in the run summary.
- **What code refuses whatever the model says:** no tool takes a user id or a document id; no tool writes anything but checked candidates or the transcription of the step's own images; every built-in tool stays unavailable and gated; a value must validate against its section model; settings, `skills.years_experience` and unknown keys are refused; addresses and names must be verbatim in the source.
- **Stored injection through the fact base:** a fact block is later read by other agents as trusted. The `looks_like_instruction` flag above keeps such an item out of "Accept all" and shows a warning.
- **Private events:** agent definitions gain a flag `private_io` (G6). For such runs the recorder stores tool names, sizes and error states only, and the run's `output` holds counts. `text` events are stored and deleted with the document they came from.

### Duplicates, conflicts and reruns
- **Against the profile:** the merge drops a candidate whose value already equals the profile's at that key. A different value at an existing key is a `replace` shown as a diff.
- **Between documents:** equal values at one key become one proposal carrying all citations; different values become one proposal with `conflict = [{value, citations}]` and the user picks one. A year alone and a month of that year at the same key are a conflict like any other.
- **Idempotency:** a step is identified by (document sha256, kind, part or image positions, `EXTRACTOR_VERSION`, model). The planner gives a new run's step the status `reused` when a finished step with the same identity exists, unless the user asked to read that document again (`reread_document_ids`). The model is part of the identity. Proposals are a pure function of the items, the current profile and the user's earlier decisions.
- **Earlier decisions:** a rejected item (section, key, value hash) is not proposed again; an accepted one is equal to the profile and drops out; pending items of an older run are superseded when a newer merge runs.

### Tokens: the estimate and the ceiling (decisions 5 and 10)
Characters divided by 4 understates twice: French prose runs nearer 3 characters per token, and a step sends its growing context again at every turn. `app/ingestion/estimate.py` (pure, G16) computes a range and a ceiling; every figure below can be checked by hand.

- **Constants.** `F = 7,000` tokens of fixed context per turn (assumption A11, from A5's real triage run: 43,100 input tokens over 6 turns). `T = ceil(characters of the part / 3)` (assumption A12). An image is 1,600 tokens (G0). `R = ceil(characters of the part / 30,000)` reads. Output per step: 1,500 at the low end, 8,000 at the high end (assumption A13). A transcribed image is counted as 3,000 characters of text to extract afterwards (A10).
- **Extraction step in `n` turns:** `input(n) = n*F + T*(2n+1-R)/2` (every turn pays `F`; the chunk read at turn `i` is sent again at each later turn, and the `R` chunks sum to that). Low: `n = R + 2`. High: `n = min(40, 2R + 8)`.
- **Transcription step of `k` images in `n` turns:** `input(n) = n*F + 1,600*k*(n+1-k)` (image `i` is viewed at turn `2i-1` and stored at turn `2i`, so it is in context for `n-2i+2` turns, and the sum over `i` from 1 to `k` is `k*(n+1-k)`). Low: `n = 2k + 1`. High: `n = min(40, 3k + 4)`.
- **The range of a run:** `L` and `H` are the sums over its steps of input plus output, low and high, computed exactly (halves included) and each rounded up once, at the end. Reused steps count zero. The transcription formula counts each image one turn longer than it stays in context (the exact sum is `k*(n-k)`): kept as it is, on the safe side.
- **The ceiling (decision 10): `C = 2 * H`.** `advance` adds up the tokens of the run's agent runs (input, cache writes, cache reads and output, as recorded) into `tokens_spent`. The ceiling is checked only before a step that will call the model: a run whose every step is reused (`L = H = C = 0`) spends nothing and goes straight to the merge. Before such a step: when `tokens_spent >= C`, or when what remains is less than that step's low estimate (it would start, be interrupted at its first call, and be paid twice after Continue), the run pauses with `token_ceiling`. Inside a step: the step's `token_budget` is the smaller of its backstop and of what remains (`C` minus `tokens_spent`), the runner (G6) counts the usage of every assistant message (one count per API message id) and interrupts the run past the budget; when the budget that ended it was the remainder of the ceiling, the run pauses, otherwise it is a content failure. The ceiling can be passed by the call in flight when the sum crosses it, and by one more if the CLI has already sent the next request when the interrupt lands: at most two requests of the step's context. G6 measures which it is, and the run's page states the measured overshoot next to "pauses at C". **Continue** (`POST /api/ingestion/runs/{id}/continue`, only for a run paused on `token_ceiling`) raises `C` by one more `H`, appends `{at, spent, from, to}` to the run's `ceiling_history`, and resumes. One more `H` per Continue was kept as the rule: it is a figure the user has already seen, and each click buys at most one more "high estimate" of work. The rule applies to every user, on a subscription as on an API key.
- **The technical backstop per step** stays: `backstop = ceil(1.25 * input(40)) + 100,000`. It is not the protection of the user (the ceiling is); it stops a single step whose context grows faster than the formula assumes.

### Limits
- Per file 20 MiB, per PDF 200 pages of text and 30 rendered pages, per document 500,000 characters, per paste 100,000, per user 100 MB and 200 documents.
- Per run: 30 documents, 1,500,000 characters, 60 images or rendered pages, 60 steps, 60 minutes, its token ceiling. Per step: 100,000 characters or 8 images, 40 turns, 15 minutes, its token budget, 20 refused items. Per tool call: 30,000 characters and 40,000 bytes read, one image, 50 items proposed; 2,000 items per run.

### Malicious files
- **Zip bombs:** DOCX and ZIP are opened with caps checked on the central directory before any entry is read and again while reading: 200 entries, 50 MiB uncompressed in total, 20 MiB per entry, a compression ratio of at most 100, no nested archive, no path used for anything but a name match.
- **Huge or hostile PDFs:** page cap, character cap, time budget, the child's memory, CPU and wall limits, pypdf 6.20.0's own limit of work per stream, any exception is "could not be read".
- **XML bombs:** `defusedxml` forbids DTDs, entities and external references. **Macros:** never executed; `vbaProject.bin` is a refusal. **Wrong extension:** the type comes from the bytes. **Images and rendered pages:** the 25 megapixel guard, the one sniffed format, decoded only in the parser.

### Privacy
- Logs carry ids, sizes, counts, statuses and rule names, never a file name, an excerpt, a value or text; tests assert it on the captured log of every flow.
- Nothing is written to disk outside Postgres: no upload spool, no parser file, no document in the scratch directory, no SDK transcript, no text in Redis. The live answer text of the agents module (PR #40, a Redis buffer) is off for ingestion's `private_io` runs, in code (G6).
- Documents go to one place outside the app: the model, through the user's own credential. Without a credential the page says what is missing and nothing is sent.
- **Consent (decision 6).** `ingestion_consents(user_id, text_version, accepted_at)`, one row per user and version of the text (primary key `(user_id, text_version)`, migration 0011): accepting a new version adds a row, and the earlier one stays with its date, so what a user had accepted when a run started remains answerable. The current consent of a user is the row of the current version of the text (`CONSENT_VERSION`); a user without that row has not consented to the current text. `POST /api/ingestion/runs` answers 409 `consent_required` with the current version while the user has not accepted the current text; `POST /api/ingestion/consent {version}` records it. The text, a constant with `CONSENT_VERSION`: what is sent (the text and page images of the documents selected, and the current profile sections without contact details), to whom (Anthropic, through your own subscription or API key), and that deleting a document here does not delete what the provider has already received. The first start shows the text with an unticked checkbox; later starts show one line. A new version asks again.
- Text matching common secret patterns sets `secret_warning`; extraction refuses the document until the user confirms or deletes it. The pattern set is a small port of gitleaks default rules (MIT licence, credited next to the file).

## T10: Platform: keep 7 nightly backups
**Issue:** #49.
**Acceptance:** `BACKUP_KEEP` defaults to 7 in `deploy.sh`, in `ops/db.sh` and in the cron line written by `backup-schedule install`. **One variable, two rules:** after a new dump has been written and verified in the same run, `ops/db.sh backup` keeps the newest `BACKUP_KEEP` dumps of its folder (as today) and deletes every dump older than `BACKUP_KEEP` days, in its own folder (`BACKUP_DIR`) and, when that folder exists, in the predeploy folder `BACKUP_DIR/deploys` that the deploy workflow writes; run by the deploy workflow with `BACKUP_DIR` already set to the predeploy folder, it prunes that folder alone. The age of a dump is read from the UTC timestamp in its file name, never from its mtime. The newest dump of each folder is always kept. A backup that fails deletes nothing, and `db.sh prune` alone never deletes by age. The README's backup section and SPEC-platform's command comment say 7, say why (a deleted document leaves the server's backups within 7 days), and say what it costs: after 7 days no restore point predates a bad migration, predeploy dumps included, which used to stay until ten newer deploys. After the merge the orchestrator runs `./deploy.sh backup-schedule install` and checks `status` on the Jetson: the installed cron line says 14 until then, **so that reinstall is a condition of merging G15**, whose dialog makes the promise.

**Playwright journey:** none, no UI and no HTTP surface. `tests/backup_test.sh` and `tests/deploy_test.sh` are the checks, with the live run of `tests/backup_test.sh` on the Jetson after the merge.
