## Decisions of the owner (Harald, 2026-10-14)
All eighteen are in the spec under "Decisions", with his words. What a task must not decide again:
- **The chain first.** Documents, then browser, then apply. Tasks D1 to D13 are the first end to end slice: a base CV built from the profile with the default template, a CV and a letter written automatically for each found posting at or above the fit threshold, the preview, the PDF. Upload conversion and design capture (D24 to D26) come right after.
- **A list of base CVs**, one the default; each from the profile (default template), built in the app, or uploaded and converted into an editable base CV whose design is captured as a template; a posting's CV is generated from the base CV chosen and inherits its template; switching one posting's CV template does not change the base. Each document can be seen, edited by hand, changed through a chat, and switched among twenty templates.
- **Fit score, not count.** Automatic generation is limited by a threshold in the Advanced settings (default 70, changeable); a safety ceiling of 100 a day stays as a backstop against a broken sweep; under the threshold, "Write now". When a base CV first exists, the last 30 days' postings at or above the threshold get documents, highest fit first.
- **Filling the profile from an uploaded CV** is one click ("Complete my profile from this CV", ingestion's run), never automatic.
- **Renderer: builders' choice,** taken: WeasyPrint in the parser sandbox if D1 passes, else a headless Chromium container. It is not an owner question.
- **Correct, never block.** The writer is careful; the fact check corrects what it finds (a correction pass of the writer, then code removes what remains) and records each correction on the version. Hand edits get notes, never changes. Nothing refuses a render, a download or a send.
- **Import** of the command line's documents; `applied` postings keep their sent PDF byte for byte.
- **Kept from the draft:** structured fields; the profile's job title under each employer; a send freezes the sent version only; the writing rules row; each template carries its own free fonts; English and French; the chat is the revision; the first one page CV moves `found` or `shortlisted` to `cv_ready`.
- **Cost:** the consent pattern of ingestion and mail, the threshold and the safety ceiling in the Advanced part of the profile's search options, the spend shown, "Write now" under the threshold and "Documents waiting" when the ceiling is reached.

## Open questions for the owner
None. Planner defaults that stand until he says otherwise: 30 unfrozen versions kept per document; 5 minutes and 10 turns per writer run; 200 chat messages kept per document; an automatic generation retried once after 10 minutes; at most 10 base CVs per person; the capture of a design takes at most one repair pass and one fidelity pass.

## Architecture decisions
Everything below is detailed in the spec; this section names only what a task must not decide again.
- **The module lives in `api/app/documents/`** and in `web/src/features/documents/`. It registers its agents with `definitions.register` and its tools with `tools.register`; it never edits `api/app/agents/definitions.py` or `tools.py`. Each writer is its own file (`writer_cv.py`, `writer_letter.py`, `writer_base.py`, `writer_design.py`, `chat.py`), imported by `writers.py`, which D7 writes complete and which skips a file that does not exist yet (mail's `routers.py` pattern).
- **Content is structured** (`content.py`, `SCHEMA = 1`). Fixed facts are never fields of a posting document's content; the base CV has its `fixed` block.
- **One draft, immutable versions.** The trigger of 0015 protects frozen rows.
- **Checks and corrections are pure** (`rules.py`, `checks.py`, `corrections.py`): the same content and the same sources give the same issues and the same corrections in the same order. `checks.run(kind, content, sources, settings) -> Checks` and `corrections.remove_remaining(content, checks, fallbacks) -> (content, [Correction])` are the entry points; the submit tool, the api and the chat all call them.
- **Base CVs are documents** (`scope = base`), listed with one default; a posting's CV names the base CV it was written from and takes its template when first written. **A template from an upload** is a row of `document_user_templates`, resolved by `templates.resolve(db, user_id, slug)` (a bundled folder first, else the person's own row through a loader that D25b registers; before D25b it is a no op), validated by the same authoring rules as a folder.
- **A template is a folder** (`templates/<slug>/`: manifest, two Jinja2 files, CSS, two thumbnails), discovered at start by `templates.registry()`. No list of templates is written anywhere else, so the template tasks share no file.
- **The renderer is behind one client** (`render_client.py`: `render(html) -> Rendered(pdf, pages)`), and `fit.fit(steps, build) -> Fitted` above it. Nothing else knows which engine runs.
- **Automatic generation is a tick,** not a hook in jobs: `tick.py`, an arq cron job every minute, finds eligible postings by query. The jobs module is edited once, by D14, for the freeze on `applied`.
- **Ids in jobs, data in the database.** arq arguments are ids; a job's return value is `None`; results are rows.
- **Logging** follows the agents and mail modules: event names `documents.<area>.<what>`, values that are ids, counts, durations, step numbers or codes of a fixed list.

## Rules every task follows
- **No personal data in the repository.** Fixtures are invented: a profile of "Alex Example" at "Example Corp" and "Sample Labs", postings of invented companies. Nothing from the owner's `profile/` or `data/` folders is ever copied in, not even as a test.
- **Isolation:** every task that adds a route, a job or a table adds a test where user B gets 404 on user A's ids.
- **Privacy:** every task that handles content runs the canary of D2 (`canary.marker`) over logs, arq arguments and Redis.
- **Never block:** no task adds a refusal of a render, a download, a freeze or a send on content grounds. A test per task that touches the pipeline asserts it.
- **Text shown to users** uses no dashes as separators (no em dash, no en dash, no spaced hyphen).
- **Evidence:** the commands run and their output under `tasks/evidence/documents-d<n>/`, with screenshots of the journey. Journeys run against the stack on the fake model backend (`AGENTS_FAKE_BACKEND`, the run input of each writer carrying a `script` key that names a stream of `api/app/agents/fake_streams/`, as ingestion's journey does); `tests/anthropic-stub.compose.yml` is used only for the credential check, it cannot call `submit_cv` or `submit_template`. They use `e2e-*@example.org` accounts.
- **Merge rule:** CONTRIBUTING's, with the local check (`ops/local-check.sh`) in place of CI: a review verdict on the head commit, the task's tests green, a merge commit, never a squash. The orchestrator merges, never the task's agent.

## For the apply module
Written by D14 (`api/app/documents/freeze.py`, delivered with its pull request). Import it as `from app.documents import freeze as documents`; the two calls then read `documents.current(...)` and `documents.freeze(...)` as in the apply plan. The module registers its status hook when it is imported: the api imports it through `freeze_router`, the worker through `REGISTRATION_MODULES`, so the hook runs in every process that can move a status. The apply module never renders and never edits a document.

- **`documents.current(db, user_id, posting_id) -> Current(cv, letter)`**, each a `Slot(version, coming)`. `version` is the approved version, else the latest rendered one (a PDF stored, or an imported file), else `None`; a newer version without a PDF is never chosen. It is a `SentVersion`: `document_id`, `version_id`, `number`, `kind`, `approved`, `frozen`, `frozen_reason`, `frozen_at`, `template_slug`, `template_version`, `language`, `fit` (`one_page` or `overflow`), `fit_step`, `pages`, `corrections` (the records stored with the version), `pdf_sha256`. `coming` is why a document is still on its way, whether or not an older version exists: a wait reason (`daily_ceiling`, `consent`, `credential`, `base_cv`), `"writing"` (a generation is queued or running) or `"rendering"` (the draft is queued or being rendered), else `None`. Apply waits on `version is None and coming is not None`, ends `no_documents` on `version is None and coming is None`, and takes `version` when it is there. It reads nothing else and writes nothing. A posting of another person has no documents (both slots empty).
- **`documents.pdf(db, user_id, version_id) -> bytes | None`**: the bytes on demand (the stored PDF, else the imported file of the command line, else `None`). `current` never loads them.
- **`documents.freeze(db, user_id, version_id, FreezeReason.apply, at) -> SentVersion`**, in the transaction that records the submission (the caller commits, a rollback takes the freeze with it; the posting's row lock is held there, so the document locks come after it). It never refuses on content: an overflow, corrections and notes freeze like a clean version, and the answer carries `fit`, `fit_step`, `pages` and `corrections` for the run report. Freezing a frozen version changes nothing (the first reason and time stay). It raises `store.NotFoundError` for an id that is not one of the person's posting documents, and `DocumentBusyError` (a `JobBusyError`, the api's 409) when a render holds the document past the lock timeout; the caller rolls back and retries.
- **The order with `set_status`**: both calls go in one transaction, in either order. Freeze the versions actually sent first, then `set_status(..., applied)`: the hook then finds each document already frozen and adds nothing. Done the other way round, the hook first freezes the approved (else latest rendered) version of each document with the reason `applied`, and `freeze` then freezes the sent version too when it is a different one. A `submit_unknown` freezes the sent versions and does not move the status.
- **The hook (`on_status`)**: a posting that reaches `applied` by any path (the job page, a bulk change, the undo of a later status, a mail's accepted proposal, apply) freezes, per document, the approved version, else the latest rendered one, with the reason `applied`, in the status transaction; an approved version whose PDF is still being rendered then is frozen by the render job when its PDF is stored (`freeze.on_rendered`), never an older rendered one in its place. A document that already has a frozen version freezes nothing more: a status that goes back to `applied` after an `interview`, or after an undo, never turns a later edit into "what was sent". Leaving `applied` (an undo of `applied` included) unfreezes nothing. No rendered version: nothing is frozen and nothing fails.
- **`POST /api/documents/{id}/versions/{n}/mark-sent`** (the person's "Mark as sent", reason `marked_sent`): 200 with the version; again, 200 with the version as it is; 409 for a version without a PDF; 404 for another person's, a missing one or a base CV.
- **The jobs service**: `jobs.service.register_status_callback(callback)`, `callback(db, job, previous_status, status, at)`, called by `set_status` after the event is written, in registration order, once per real change (not when the status is unchanged). An exception leaves `set_status` like its own.
