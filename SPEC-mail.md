# Spec: mail

Module of [CAPABILITY-MAP.md](CAPABILITY-MAP.md). Depends on `agents` and `jobs`. Intent: [agent-features.md](../docs/intent/agent-features.md).

## Objective

Every email about a job lives next to that job in the app. Each user connects their own Gmail; the app finds the conversations that concern their jobs, keeps the full history per job, updates the job's status from what the mails say (application received, rejection, interview invitation), and prepares reply drafts. On a job, the user drafts a reply together with an agent ("let's draft a mail, I want to say this"), iterates by chat or edits by hand, and sends it with one click. **Nothing is ever sent without that click.**

User stories:
- As a user, I connect Gmail once from Account settings and can disconnect at any time.
- As a user, I open a job and see its whole mail history, newest first, threads grouped, attachments listed.
- As a user, I trust the status on my board because confirmations, rejections and invitations move it automatically, with the mail that caused each change shown in the job's history; I can undo any automatic change.
- As a user, I see "Waiting for your answer" on jobs where the last message is from the company and needs a reply, with a draft already prepared.
- As a user, I click "Draft a reply", say what I want in the chat, see the draft update, edit it by hand if I like, then click Send; the reply goes out from my Gmail in the same thread.
- As a user, I can link a mail thread to a job by hand, or unlink it, when the automatic matching is wrong.

## Gmail through the app's own MCP server (owner, 2026-10-21)

Decided on PR #509 (option A of `docs/proposals/mail-mcp.md`): every Gmail call of the app goes through **one MCP server of the app's own, `gmailmcp`**, built from the merged M1 client (task M1b). It is the only process that talks to the Gmail API. Reading, the first and the incremental sync, the agents' mail tools and the send request all go through it. What does not move: Google's OAuth endpoints (consent, token exchange, refresh, revocation, `userinfo`), which stay with M4 in the api and the worker, because Google gives an access token to no one without the consent and the refresh token of M4.

**The service.**
- `gmailmcp` runs the api's image with its own command (`python -m app.gmailmcp`), no new image, a memory limit of 128 MB, measured by M1b against the 5 GB budget of `compose.yml`. It speaks MCP over streamable HTTP (the `mcp` package already locked as a dependency of the agent SDK), plus one plain streamed HTTP route for attachment bytes.
- Two networks of its own: `mailmcp`, internal, joined by the api, the worker and Redis only (no Caddy route, no Funnel, no published port), and `gmail_egress`, joined by `gmailmcp` alone, its only way out. It is not on the `default` network, so no other service can reach it.
- **Its way out is filtered like the browser's.** The host firewall of `ops/browser-egress.sh` (browser B6) covers the bridge of `gmail_egress` too: DNS to Docker's resolvers passes, every other UDP is dropped, private, loopback, link local, CGNAT (the tailnet), documentation and reserved ranges are dropped, the host itself is dropped, and the rest (Google) passes. So a compromised `gmailmcp` cannot reach the host, the home network or the tailnet. The deploy applies and checks the rules before it starts `gmailmcp`, and the boot unit of B6 covers its bridge before Docker starts. The test stack puts `gmailstub` on `gmail_egress` and applies no rule.
- **Redis, and only one thing in it.** Redis joins `mailmcp` so `gmailmcp` can mark used send keys. Redis holds the arq queue, the live text of runs and the other locks, so `gmailmcp` connects as a Redis ACL user of its own, `gmailmcp`, allowed the one command `SET` on the keys `mailmcp:send:*` and nothing else (`-@all +set ~mailmcp:send:*`); its code always sends that `SET` with `NX` and `EX`. Its password lives in a file of its own (not `.env`), never on the `redis-server` command line, which `docker inspect` and `ps` would show: an ACL file or a config file mounted read only. The Redis healthcheck uses `REDISCLI_AUTH` once `default` has a password, and the ACL tests run against their own Redis with passwords. Redis's `default` user gets a password too, carried in the `REDIS_URL` of the api and the worker, so that `gmailmcp` cannot connect as `default` and pass its own limits. A `GET` of a queue key, a `SET` of any other key, a `KEYS` and a connection as `default` without its password are refused (tests).
- **Its environment is a list, never the stack's `.env`.** It holds no database connection, no `CREDENTIALS_KEY`, no `SECRET_KEY`, no model credential, no Google client secret and no refresh token. Its compose service has no `env_file` of the stack: an explicit `environment:` names each variable it gets (`APP_ENV`, `GOOGLE_API_BASE_URL`, `MAIL_SEND_KEY`, its Redis address with the `gmailmcp` user, the log settings), as the comments of the parser and the renderer in `compose.yml` say for theirs. Its only secret besides its Redis password is `MAIL_SEND_KEY` (below), which lives in a file of its own, `.env.mailsend` (mode 600, git ignored, never read by an agent), loaded by the api and `gmailmcp` only: it is `gmailmcp`'s only env file, and the key is never interpolated from `.env`. The worker loads `.env` alone, so it never holds the key. A test reads `docker compose config` and fails when the worker's environment holds `MAIL_SEND_KEY`, or when `gmailmcp`'s holds `DATABASE_URL`, `CREDENTIALS_KEY`, `SECRET_KEY`, `GOOGLE_OAUTH_CLIENT_SECRET` or a model credential.
- It keeps M1's behaviour whole: the timeouts, the retries and backoff on 429, 403 with a rate reason and 5xx (never on a send), the caps per call of "Sizes", the streamed read of `attachments.get`, the typed errors that carry a code and never Google's text, `log.py` and its scrubber. The quota counter per user moves into it, so one process now counts every call of a person: at most 3,000 units a minute per user (half of Google's 6,000), and a sync batch stays under 150 `messages.get` a minute (owner, 2026-10-21, #175).

**Its tools.** Each returns Gmail's JSON as Gmail answers it, so M3 parses exactly what it parses today (every header that rule A of the binding rule reads, `format=full` and `metadata`, never `raw`).

| Tool | Gmail call | Used by |
|---|---|---|
| `get_profile()` | `users.getProfile` | M4's callback (the history id), the address check of every call |
| `list_messages(q, page_token, max_results)` | `messages.list` | M7, M10, M23, the agents' search |
| `get_message(id, format, metadata_headers)` | `messages.get` | M7, M10, M12 (headers of the sent message), the agents' read |
| `get_thread(id, format)` | `threads.get` | M7, the agents' read |
| `list_history(start_history_id, history_types, page_token)` | `history.list` | M10 |
| `send_message(send_key, raw, thread_id)` | `messages.send` | the send gate alone (M12) |
| route `GET /attachments/{message_id}/{attachment_id}` | `attachments.get`, decoded and streamed in 64 KB pieces | M15 |

**Who the caller is, and whose mailbox.** The app calls `gmailmcp` through one client of its own, `app/mail/mcp_client.py` (M1b), with the method names of M1's contract (`get_profile`, `list_messages`, `get_message`, `get_messages`, `list_all_messages`, `list_history`, `get_thread`, `download_attachment`), so M7, M10, M15 and M23 call it as they would have called `google.py`. Every call carries, in transport headers set by that client's code and never in a tool argument, the app's user id, the address of `mail_accounts.email` and a short lived Google access token. No model ever writes one of them.

**Tokens.** The refresh token stays where M4 stores it, encrypted with `CREDENTIALS_KEY` in `mail_accounts` (owner, 2026-10-21). The caller (the worker for the sync and the agent runs, the api for the callback, attachments and the send) refreshes through M1's OAuth functions, keeps the access token in memory only until it expires, and passes it per call. `gmailmcp` uses it for that call and keeps nothing at rest: no file, no row, no Redis key, nothing in a log (`log.hide` registers it while the call runs). A Gmail 401 answers the typed error `token_expired`; the caller refreshes once and calls again; `invalid_grant` at the refresh sets `needs_reconnect`, as before.

**Isolation between people (absolute).**
- The address check: on its first call with a given access token, `gmailmcp` reads `getProfile` and compares `emailAddress` with the address the caller sent; it caches the verdict for that token's lifetime only, keyed by the SHA-256 of the token, so no raw token sits in memory past its call. A mismatch refuses every call with `not_connected`. Only the connected address counts as the person (owner, 2026-10-21): no alias, no "send as" address, no delegated mailbox.
- The user id, the address and the token travel together: a token that belongs to another address than the one sent is refused, whatever the user id says.
- **Isolation rests on the client.** `gmailmcp` has no database, so it cannot tell user A's id sent with user B's address and B's token. The guarantee is that `mcp_client.py` takes all three from one `mail_accounts` row, the one of the request's user or of the run's user, through one function of its own; no caller passes a user id, an address and a token separately. A client side test proves that every call's three headers come from one row, and that no method takes them apart.
- Two people's calls share nothing but the process: no cache keyed by anything but the hash of the token, no global state about a mailbox. A test with two users, A and B, whose mailboxes hold the same Gmail ids, proves that A's calls never answer B's mail, through every tool and the attachment route.
- The canary of M1 runs over `gmailmcp`'s logs, its error answers and its Redis keys.

**The send: a one time key.** `send_message` sends only with a key the send gate creates after it has recorded the person's click (owner, 2026-10-21). The gate (M12, in the api) first commits its decision transaction with the `pending` row of `mail_sends`, then builds the MIME message itself, then mints `send_key`: a payload `{send_id, user_id, address, draft_id, thread_id, content_hash, raw_sha256, expires_at}` (expiry 60 s) and its HMAC SHA-256 under `MAIL_SEND_KEY`. `gmailmcp` sends only when the HMAC is valid, the key has not expired, its user and address are the call's, its `thread_id` is the call's `thread_id` (so a key fits exactly one request), the SHA-256 of the `raw` it receives is `raw_sha256`, and the key was never used. It marks the key used **before** it calls `messages.send`, never after: `SET mailmcp:send:<send_id> 1 NX EX 600` in Redis, as the `gmailmcp` ACL user; a `SET` that finds the key refuses the send, so a used key is refused even after a restart, and a `SET` that fails (Redis down) sends nothing. It then calls `messages.send` once, never retries, and answers `sent` with Gmail's id and thread id, `gmail_4xx` with the code of a 4xx answer (the gate's `failed`), or `unknown` (a 5xx, a timeout, a dropped connection). The gate maps them to its states as before; a hop to `gmailmcp` that fails before the request was accepted (the connection refused) is `failed` with `mail_server_down`, nothing having left, and anything later is `unknown`. `MAIL_SEND_KEY` is in the environment of the api and `gmailmcp` only: the worker, which runs every agent and every schedule, cannot mint a key, so no worker, schedule or agent can send even through a bug. No agent's allow list names `send_message`, no app tool proxies it, and `gmailmcp` is never an MCP server of an agent's Claude Code process (`strict_mcp_config`).

**Agents read the person's own mailbox (owner, 2026-10-21).** The mail agents (M17's `mail_link` and `mail_label`, M19's `mail_reply`) get the server's full read tools on the person's own mailbox, not only the thread they are bound to. They reach them as app tools of the per run in process MCP server of SPEC-agents (`app/mail/mailbox_tools.py`, task M1c), never by a connection of their own:
- `mailbox_search(query, page_token)`: Gmail's search on the person's mailbox. Code wraps the model's query in parentheses and appends the suffix, `(<query>) -in:spam -in:trash`, so an `OR` in the query cannot escape it; a query with unbalanced parentheses, or that names `in:anywhere`, is refused with a constant before any Gmail call. At most 20 results a page, each answered as `{message_id, thread_id, date, from, subject, snippet}`.
- `mailbox_read_message(message_id)` and `mailbox_read_thread(thread_id)`: the message parsed by M3's `parse` into plain text, newest first, with sender, recipients, date, subject and the attachment list (names, types and sizes: an agent never gets attachment bytes), each message clipped at 6,000 characters and 24,000 per thread.

Their limits:
- **Own mailbox only.** The tools take the run's user, its account and its access token from the runner's binding (one `mail_accounts` row, through `mcp_client.py`), never from an argument; the address check of `gmailmcp` holds for them as for the sync. Without the consent of decision 13 (`accounts.assistant_allowed`), the mail agents do not start, so the tools are never reached; the consent's text names the mailbox search and its version (`accounts.CONSENT_VERSION`, the one `assistant_allowed` compares) is raised from 1 to 2 by M4b, so a consent given before decision 18 does not count.
- **Rate limits.** Per run: at most 40 mailbox calls and 120,000 characters returned in all, then every mailbox tool answers the constant "Mailbox limit reached for this run.". Per user: the agents' calls count in `gmailmcp`'s quota counter and take at most 1,000 units a minute, a third of the user's budget, so the sync is never starved. The run's `token_budget` and the daily cap of automatic runs hold as before.
- **Mail content is data, never instructions.** Every result is wrapped under `untrusted_mail` keys as quoted data, and every mail agent's system prompt says so. What an agent reads changes nothing by itself: a mailbox read is never stored, never makes a mail bound (the binding rule reads stored messages only), never adds a candidate posting, a recipient or a fact check source (a number or an address the reply agent took from another mail is flagged by the rules of M9 as from nowhere). The run is `private_io`: its tool results reach `agent_events` as names, sizes and counts only.
- **Never a send.** No read tool writes, no tool sends, and the key of the gate cannot be minted in the worker.
- The fact check by model (M20) keeps no mail tool at all: it judges a draft against the profile only, so no mail can talk to it.

**Tests.** `gmailmcp` is pointed at the fake Google of M1 through `GOOGLE_API_BASE_URL`, in process for pytest (its ASGI app with an in memory transport) and as a service in `tests/gmail-stub.compose.yml`; a real Google address is refused under `APP_ENV=test` as today. A test walks `api/app` and fails when a module outside `app/gmailmcp/` names a Gmail API path, so no module calls Gmail itself.

- OAuth with PKCE and a signed `state` bound to the session; after the callback the connected address is read from `userinfo.email` and stored; one Gmail address can be connected to only one app user (409 otherwise); refresh token encrypted with the same `CREDENTIALS_KEY` mechanism as model credentials; access tokens kept in memory only.
- **The real account only (owner, 2026-10-21, #190).** Each person connects his real Gmail account, and only the connected address counts as the person: no alias, no "send as" address. A thread written from an alias is someone else's mail to the app and fails closed (the binding basis `user_wrote` misses it, the classifier may read it as inbound).
- **Starting the connection (owner, 2026-10-21, #187).** `POST /api/mail/oauth/start` with the app's CSRF header (`X-Requested-With: jobapp`) and the session answers the address of Google's consent page, which the page then opens; a link from another site cannot start the flow. On return the Gmail card shows the connected address, so a person who allowed another Google account sees it at once.
- **The consent tick (owner, 2026-10-21, #187).** The tick waits in the tab as `{version, user_id, time}`, is recorded only for the same signed in user within 10 minutes, and is cleared at sign out.
- **A callback without a session (owner, 2026-10-21, #187).** The callback consumes nothing and redirects to `/login`; the code and the state leave the address (the redirect carries neither), Caddy masks any query of an `oauth/` path in its access log, `code=` and `login_hint` included, and after sign in the page reopens the Connect dialog with its consent checkbox and its tick as they were, one click away from Google. It never sends the person to Google by itself: anyone can link `/account?gmail=resume`.
- **Every Gmail call goes through `gmailmcp`** ("Gmail through the app's own MCP server"); the sync code below calls `app/mail/mcp_client.py`, never `google.py`.
- **Initial sync:** messages from the last 180 days matching a job-related query (sender or recipient domains of the user's job companies and ATS domains, plus keywords such as application, candidature, interview, entretien), limited to 5,000 messages.
- **Incremental sync:** every 5 minutes per connected user in the worker (Gmail `history.list` from the stored `historyId`; full resync when the history id expired). No Pub/Sub (keeps everything free and avoids exposing a webhook).
- Bodies stored as plain text and as HTML sanitized with `nh3` (allow-list of tags and attributes, no scripts, no event handlers, no `style` URLs), capped at 500 KB per message; remote images are blocked by default with a per-message "Show images" choice. The quote depth limit of the parser stays 100 (owner, 2026-10-21). A message's `In-Reply-To` is appended to its stored `references_header` by M7 when `References` lacks it (owner, 2026-10-21, no migration), so the binding rule and the reconciliation read one list.
- **Attachments** are listed with name, type and size and never stored. Download (`GET /api/mail/messages/{id}/attachments/{att}`) checks ownership before any Gmail call, streams the bytes from the attachment route of `gmailmcp` with `Content-Disposition: attachment` and a sanitised ASCII filename (plus RFC 5987 UTF-8 name), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, and a content type sniffed from the bytes (unknown types served as `application/octet-stream`); never inline, except PDFs opened through the same blob preview as job files; 25 MB cap.
- Rate limits and backoff on 429 and 5xx; a revoked token sets `needs_reconnect` and shows a banner.

## Automatic changes: an explicit exception

SPEC-agents says nothing changes user data until the user accepts a proposal. The mail module is the one named exception, wanted by Harald: **links between mail threads and jobs** (above the confidence threshold) and **status changes from mail** (the transitions below) are applied automatically, **only under the binding rule** of the task plan (`tasks/mail/todo.md`, "The binding rule", decided 2026-10-13): Gmail's own authentication result passes for the visible sender, that sender's domain is bound to the job (the company's own domain, an address the user wrote to, a domain he confirmed, or, for a mail of an applicant tracking system, a reply to a mail he sent or a posting in the status `staged`, `applied` or `interview` hosted on that same system whose company the mail names; for a `staged` posting only the confirmation of the application applies by itself), and the verdict, of a rule or of the model, reaches `MAIL_AUTO_APPLY_CONFIDENCE` (default 0.90). A reference id that the mail carries is never enough alone. Anything else is a proposal the user accepts. Two precisions of the owner (2026-10-21, #190): a `dkim=pass` with an explicit `dmarc=fail` in Gmail's own header is not a pass (the DMARC failure vetoes it); and against imported mail that fakes Gmail's authentication lines, nothing older than the connection ever applies by itself, and checkpoint stage B also looks on the owner's mailbox for a mark that real imports carry, which `auth.py` then treats as not trusted. A status change never triggers a send. They are recorded as `proposals` rows created directly with status `accepted` and `decided_by = system`, plus a job event, so every automatic change is visible, attributable to its mail, and undoable. Drafts are never sent automatically: no exception there. SPEC-agents is amended in this PR to name this exception.

## Retention and privacy

- **Disconnect** revokes the token at Google and deletes the user's `mail_accounts`, `mail_messages`, `mail_threads`, drafts and mail classifier results; job events keep only "status changed from a mail (mail deleted)". **Account deletion** cascades to every mail table.
- Nothing is pruned by age (decided 2026-10-13): the 180 days are the window of the first sync only. Storage is bounded at 20,000 stored messages or 300 MB of mail text per user, and the user can delete one thread from the app. The log of sends, which holds no address and no text, is kept 365 days, also after a disconnect.
- `/privacy` states what is read: the sender, the recipients, the subject and the preview of each new mail, and the whole mail stored only when it concerns a job; the search terms of the first sync; and, after the recorded consent, any mail of the person's own mailbox that the assistant searches and reads (never spam or trash), which is never stored and is sent to Anthropic only for that run (decision 18). It states where it is stored (the user's app instance on the owner's Jetson), that message content is sent to the user's own model provider, named on the page as Anthropic, only to classify, match and draft, and only after a recorded consent whose text names the mailbox search (`accounts.CONSENT_VERSION` raised to 2 by M4b, so everyone who consented before consents again), that nothing is shared with anyone else, retention as above, what stays after a disconnect, how to disconnect, and that the administrator deletes an account on request. It includes the Google API Services User Data Policy **Limited Use** disclosure. `/terms` is a short plain statement.
- **The wording of the two pages (owner, 2026-10-21, #182).** The thirteen sentences of M2 are approved with two changes: the provider is named (Anthropic), and the page states how long third parties' text lives (until the person disconnects, deletes the thread in the app, or deletes the mail in Gmail, after which the next sync deletes the app's copy too, and at most 7 more days in the backups). The home page drops "the documents you prepare for them". The search terms that `/privacy` lists are rendered from the same constants as the sync's query, and a test compares the two. The contact address of both pages is the owner's Gmail address, given as a build setting on the Jetson and never committed. Decision 18 came after that approval: the sentence on what is read and the assistant's sentence are rewritten by M4b to say that the assistant may search and read any mail of the mailbox, and M21 tests them against the code.

## Matching mails to jobs

- Deterministic first: sender or recipient domain equal to the job's company domain or ATS domain (ashbyhq.com, greenhouse.io, lever.co, workday, smartrecruiters, teamtailor, welcometothejungle, linkedin jobs, and the French market systems the owner added on 2026-10-21 before M5 ships: welcomekit.co, join.com, flatchr.io, taleez.com, digitalrecruiters.com, jobaffinity.fr, beetween.com, breezy.hr, applytojob.com, pinpointhq.com, comeet.com, homerun.co, eightfold.ai, avature.net, csod.com, oraclecloud.com, each row corrected from the real mailbox at checkpoint stage B), job title or company name in the subject, a reference id from the posting URL in the body. Score with confidence; one job wins when its confidence is clearly above the others.
- Ambiguous threads go to a small **mail triage agent** (agents runtime, model chosen by the credential: `claude-opus-5-5` on a subscription, `claude-sonnet-5-5` on an API key; read-only tools: get_thread, list_candidate_jobs, and the mailbox read tools of "Gmail through the app's own MCP server" with their limits) that proposes a link; a proposal is applied automatically only under the binding rule and at the threshold, otherwise listed in an "Unmatched mail" inbox for the user.
- Manual link and unlink always win and are never overridden by later syncs.

## Status updates from mail

- A **mail classifier** (deterministic rules for common ATS templates first, then the agent for the rest) labels each inbound message: `application_received`, `rejection`, `interview_invitation`, `assessment`, `offer`, `info_request`, `other`.
- **Active statuses** are `found`, `shortlisted`, `cv_ready`, `staged`, `applied`, `interview`. `rejected`, `closed` and `skipped` are final for automation: mail never moves a job out of them.
- Allowed automatic transitions: `found`, `shortlisted`, `cv_ready`, `staged` → `applied` on `application_received` (fills `applied_on` if empty); any active status → `rejected` on `rejection`; `applied` → `interview` on `interview_invitation` or `assessment`. Nothing moves a job backwards.
- **Only newer mail moves a status:** a message changes a status only if its date is later than the job's last status change (manual or automatic). The **initial 180-day sync never applies transitions**: it only links threads and lists "suggested status changes" the user can apply in one click per job or all at once; transitions apply automatically only for messages arriving after the account was connected.
- **Recording:** a `job_events` row of kind `status` with `data = {from, to, via: "mail", message_id, proposal_id}`, the keys the jobs module writes.
- **Undo** (`POST /api/mail/status-changes/{event_id}/undo`, owned by this module): allowed only while the job still has the status that event set (else 409 with the current status); restores `from`, writes a new `status` event with `via: "mail_undo"`, marks the event and its proposal `undone`; an undone message is **never re-applied** by later syncs (the classifier result is kept with `applied = false, undone = true`).
- `needs_reply` is true when the last message of a linked thread is inbound and classified `interview_invitation`, `assessment`, `offer` or `info_request`; the board shows these as "Waiting for your answer".

## Drafting and sending

- When a thread gets `needs_reply`, the **reply agent** prepares a draft in the user's language and tone using the job, the thread, the profile (facts only, same no-invention rule as documents) and the user's answers section (availability, notice, salary policy). It may also search and read the rest of the person's own mailbox with the read tools and limits of "Gmail through the app's own MCP server"; what it reads there is no source for the fact check. The draft is stored in `mail_drafts`, never sent.
- **The fact check rules (owner, 2026-10-21, #183):** a duration below the profile's ("3 years" against 3.5) is flagged softly with its own code, `duration_below_profile`, never silently allowed; the participants the rules accept as organisations are the posting's company and the domains of its addresses only, never a display name.
- The reply agent cannot change recipients: the draft's recipients are computed by code from the addresses the user himself wrote to in the thread and from a sender bound to the job (reply or reply-all chosen by the user); any other address is flagged, never prefilled (a sender bound only as a mail of an applicant tracking system is a shared sender: flagged, never prefilled), and confirmed one by one in the Send confirmation. Mail content is data for agents, never instructions (stated in every mail agent's system prompt).
- On a job: "Draft a reply" opens the chat panel (agents threads) bound to that mail thread; each message to the agent updates the draft; the user can edit the draft text directly at any time; the latest of either wins and the agent sees manual edits.
- **Send** is a button, enabled only on an explicit click by the signed-in owner, with a confirmation showing recipients and subject; the server sends in the same Gmail thread (`threadId`, `In-Reply-To`, `References`) through the `send_message` tool of `gmailmcp`, with the one time key the gate mints after its audit row is committed, records the sent message, marks the draft `sent`. Every send passes one function, `mail.gate.send`, which accepts three authorisations: `user_click`, the click of the signed-in owner on that exact draft; and, for an application draft only (SPEC-apply A14), `person_approval`, the person's Approve of that application, and `full_auto_like`, the Like given while Full auto is on, once its hold is over. No worker or agent tool can build one, and the API's dispatch loop only carries out an approval or a Like already given. The gate writes its audit row before Gmail is called, and a send whose result is unknown (also a 5xx answer of Gmail) is never sent again by the app itself, and its draft waits in `send_unknown`.
- Sending is idempotent per draft (a double click sends once). Send is a POST protected by the app's CSRF rule (`X-Requested-With: jobapp`) and the session.
- Applications sent by e-mail (#251) stay behind M12, M18 and M23, as planned (owner, 2026-10-21): they pass the same gate.
- **Model spend:** without a model credential, matching falls back to rules only, classification to rules only, and no drafts are prepared (the UI says why). Automatic runs (triage, classification, drafts) need the user's recorded consent, are capped at 100 per user per day, and share the user's four active runs, one at a time: the runner has no priority. No agent drafts for a job the user's never apply rules exclude. There is no sending limit as a product rule (decided 2026-10-13): Gmail's own quota is the ceiling.

## Frontend

Account: "Gmail" card (connect, status, last sync, sync now, disconnect). Jobs list: "Waiting for your answer" badge and filter. Job detail: Mail tab with threads, messages (sanitized HTML in an iframe with `sandbox="allow-popups allow-popups-to-escape-sandbox"`, since an empty sandbox cannot open a link, and a strict CSP, links opened with `noopener noreferrer`, plain text fallback), attachments, link and unlink; automatic status changes shown with Undo; Draft panel with chat on the side, editable draft, Send with confirmation. `/mail/unmatched` inbox. Public `/privacy`, `/terms`, home. Mobile friendly.

## Testing strategy

- Unit: OAuth state and PKCE, token encryption, query building, history sync (new, changed, deleted messages, expired history id), MIME parsing (multipart, encodings, French accents, inline images, attachments), HTML sanitization (scripts, event handlers, remote images, CSS tricks), matching scores, classifier rules on real-looking ATS templates (Ashby, Greenhouse, Lever, Workday, WTTJ, French and English), allowed transitions, undo, needs_reply.
- Integration: a fake Gmail API server (recorded shapes) behind `gmailmcp` in each task's tests and in the local check (`ops/local-check.sh`; there is no CI); isolation between users, through `gmailmcp` too; send idempotency; no path to Gmail's send call outside `mail.gate.send` (tests assert that the gate is reachable from the send endpoint alone, that `gmailmcp` refuses a send without a valid unused key, and that the worker's settings hold no `MAIL_SEND_KEY`); no Gmail API path named outside `app/gmailmcp/`. The canary fixtures move to `api/tests/conftest.py` in the first mail task after the pause (owner, 2026-10-21, #175), so every module's tests can plant them.
- Agents (matching, classification, reply) run on the fake model backend in the same tests.
- End to end on the Jetson with Harald's real Gmail (connected by him through the OAuth screen; read-only checks first, one real reply sent only to his own address as a test, never to a company).

## Boundaries

- **Always:** user click before any send; undo for every automatic status change; owner-only access; sanitized rendering.
- **Ask first:** widening scopes; auto-send of any kind; keeping attachment contents; syncing beyond 180 days.
- **Never:** send mail outside `mail.gate.send`, or from a worker, a schedule or an agent tool; give an agent a send tool or `MAIL_SEND_KEY`; call the Gmail API outside `gmailmcp`; store a Gmail token in `gmailmcp`; give `gmailmcp` the stack's `.env`, or the worker `MAIL_SEND_KEY`; let `gmailmcp` reach Redis beyond `mailmcp:send:*`; let an agent read another person's mailbox; log message bodies or tokens; delete mail in Gmail.

## Success criteria

1. Harald connects Gmail and sees, on his real jobs, the mail threads that belong to them, with few wrong links and an inbox for the rest.
2. Confirmations, rejections and invitations move statuses automatically, each with its source mail and an Undo.
3. "Waiting for your answer" jobs have a prepared draft; drafting with the agent and editing by hand both work; Send replies in the same Gmail thread.
4. No mail is ever sent without the user's click (automated test and code review).
5. Each task's tests and the local check cover sync, matching, classification, drafting and send with a fake Gmail and a fake model; no cross-user access.
