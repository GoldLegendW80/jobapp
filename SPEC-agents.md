# Spec: agents

Module of [CAPABILITY-MAP.md](CAPABILITY-MAP.md). Depends on `jobs`. `ingestion`, `mail`, `documents` and `apply` run their agents on it. Intent: [agent-features.md](../docs/intent/agent-features.md).

## Objective

One runtime that every agentic feature uses: a worker that runs Claude agents for a given user, with that user's own model credential, streams progress to the browser, keeps a log of every run, and lets the user chat with an agent about a job or a document. This module ships the runtime, the credentials, the run log and the chat primitives, plus one real agent to prove it end to end: the **job triage agent** (reads a posting against the profile and writes a short assessment and suggested status into the job's notes as a proposal the user accepts).

User stories:
- As Harald, my agents run on my Claude subscription.
- As a friend, I paste my Anthropic API key once in Account settings; it is stored encrypted and only used for my runs. Without a credential, agent buttons explain what is missing.
- As a user, I start an agent on a job ("Assess this posting"), see it work live (steps, tool calls, text), stop it, and find the run later with its cost and duration.
- As a user, I chat with an agent in a side panel on a job; the conversation is kept per job and can be resumed.

## Runtime

- **Claude Agent SDK (Python)** in the `worker` container (the one J5 adds for sweeps; this module adds the agent queue to it). The SDK is the Claude Code harness: it needs the Claude Code CLI available in the image (Node runtime); the image stays arm64.
- **Facts to verify against the official Agent SDK docs before coding** (code.claude.com/docs/en/agent-sdk; never guess the API): the options object and its fields (system prompt, allowed tools, permission mode, MCP servers, subagent definitions, model, max turns, working directory, session resume), streaming message types, how usage and cost are reported, and how authentication is read (an Anthropic API key, or a Claude subscription OAuth token produced by `claude setup-token`). The plan records the verified answers.
- **Tools:** no shell, no filesystem outside a per-run scratch directory, no web by default. Each agent gets an explicit allow list of tools, mostly in-process app tools exposed as an MCP server inside the worker (for example `get_job`, `get_profile_section`, `propose_note`, `propose_status`), which read and write through the same service layer and user scoping as the API. Write tools only create **proposals**; nothing changes user data until the user accepts. One named exception, defined in SPEC-mail: automatic mail-to-job links and status changes from mail are recorded as proposals created already `accepted` (`decided_by = system`) with an undo.
- **Models:** `claude-opus-5-5` for every agent by default, configurable per agent definition in code, except where a definition names a model per credential kind (`model_by_credential`: the worker then picks the model when it reads the run's credential and writes it on the run next to `credential_kind`; only the ingestion agents do, `claude-sonnet-5-5` on an API key). Thinking is adaptive; effort set per agent.
- **Isolation:** one run = one SDK session in a fresh scratch directory, user id bound into every tool call server side (the model never chooses whose data it touches), technical limits per run (max turns, wall time) to stop runaway loops, no spending cap (decision below), cancellation from the UI.
- **Concurrency:** at most 2 agent runs at a time on the Jetson (RAM), per-user queue order, the worker keeps within its 1536m budget.
- **As built in A2 (2026-10-10):** SDK facts in `tasks/agents/todo.md`. `claude-agent-sdk==0.2.163` bundles the Claude Code CLI 2.1.286 as a native binary, so the worker needs no Node: the `worker` target of `api/Dockerfile` (image `jobapp-worker`) adds the SDK to the api's code, the api image does not change. Queue `jobapp:agents` in the existing worker (`max_jobs=2`, a run is tried once); a later lane for automatic runs gets its own queue name. A run: claim (queued to running), decrypt the credential, scratch directory on the worker's `/tmp` tmpfs (HOME, Claude Code config, temporary files, working directory; deleted on every path), Claude Code started with `tools=[]`, the agent's app tools as an in-process MCP server bound to the user, every built-in tool also in `disallowed_tools`, `permission_mode="dontAsk"`, no settings sources, strict MCP config, and a PreToolUse hook that denies anything outside the allow list. Credential in the CLI process environment only (`ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`); every other inherited variable is blanked in that process's environment, the SDK's `claude -v` probe (started without env=) is turned off with `CLAUDE_AGENT_SDK_SKIP_VERSION_CHECK`, and the worker drops its secrets from its own environment once its settings are read, so no Claude Code process sees them; the secret is scrubbed from anything stored. Events: `status`, `init`, `text`, `thinking` (content never stored), `tool_call` (name and clipped arguments), `tool_result` (clipped), `tool_denied`, `usage` (tokens, cost, turns), `rate_limit`, `api_error`. Limits: `max_turns` per agent, wall time 10 minutes by default; cancel sets `agent_runs.cancel_requested_at` (a column added to the data model), polled by the runner, which interrupts the SDK. Worker start fails runs left `running`; a cron fails runs running past any limit or queued for 6 hours. At most 4 queued or running runs per user (429 beyond). The first successful run with a subscription token marks it verified (`set_verified_if_unchanged`). Tests run the runner against `FakeBackend`, which replays recorded CLI message streams through the SDK's own parser; `AGENTS_FAKE_BACKEND` is refused in production twice (settings, and the backend factory). The stream (`GET /api/agents/runs/{id}/stream`, A2b) replays `agent_events` after the Last-Event-ID header or `?after=` (`app/sse.py` `replay`; each step's id is its seq, `end` without an id once the run has ended); the web `RunPanel` reconnects by itself (EventSource, then its own retry from the last seq with backoff, ending on a 404) and `/runs` lists the runs, with a test run card only when the server offers a test agent.
- **The answer streams while it is written (issue #33, 2026-10-10; decision and SDK facts in `tasks/agents/todo.md`).** The runner asks Claude Code for partial messages (`include_partial_messages`) and reads only the text deltas of the text block being written; the worker appends them every 100 ms to a per-block buffer in Redis (`app/agents/live.py`), never to `agent_events`. The run stream relays what a connection has not had yet as `partial` events without an id, `{block, after, offset, text}`, polled every 150 ms; the `text` event, stored when the block is complete exactly as before, replaces the live text in the browser. A reconnect resumes the stored steps by Last-Event-ID as before and the block being written from its beginning (offset 0, everything so far), so the browser never shows a fragment twice or misses one. Thinking and tool input are never live, the credential is scrubbed, a block's live text is capped at the 20,000 characters of the stored event. A run cancelled or failed in the middle of an answer stores no answer, as before: the unfinished text leaves the chat when the run ends, and the run log keeps the cut block only when Claude Code reports it. `AGENTS_LIVE_TEXT=false` turns the live text off for the server, and an agent definition turns it off for its own runs (`live_text=False`: nothing of them is written to Redis or read from it; for agents reading private documents). Since issue #80 the stream reads Redis only while the run is running, a Redis that does not answer costs a run at most one second per attempt with a back off between attempts, and every stored text is scrubbed whole before it is shortened. Since issue #155 no write to Redis starts once the run has ended, a pump the run could not stop clears behind its call when that call comes back (what the call wrote may land after the final clear), and an attempt is counted slow on its own calls, not on its wait for the lock. The fake backend replays partial messages too: a recording of the pinned CLI (`partial_recorded`) and, for the other streams, stream events built in the recorded order, so CI covers the path with zero model calls.

## Credentials

```
model_credentials(user_id pk fk, kind enum(claude_subscription, anthropic_api_key),
                  secret_encrypted bytea, last4 text, verified_at, created_at, updated_at)
```

- Secrets encrypted with a key from `.env` (`CREDENTIALS_KEY`, Fernet or AES-GCM via `cryptography`), never logged, never returned by the API (only kind, last4, verified_at). Never logged holds for the libraries too (issue #90, 2026-10-13): the one log handler of the api and of the worker rewrites every record of every logger (the SDK, the HTTP clients, arq, uvicorn, SQLAlchemy) before it is written, replacing the credential a run holds, character for character, and anything shaped like an Anthropic credential (`sk-ant-` and what follows), which also covers a credential a library cut before logging it (`app/logging_config.py`). A stored credential off the shape the save accepts (the `sk-ant-` prefix, then only letters, digits, `-` and `_`, 40 to 400 characters: `credentials.shape_error`, issue #155) never reaches a run nor Verify: the run fails with "The saved credential is not a whole one. Paste it again." and Verify answers 409 "The saved credential does not have the form of an Anthropic key or token. Paste it again.", because scrubbing a few characters out of everything would mangle the run, and the log filter's shape must cover the whole secret.
- Account page: "Model access" card (also the first step of the welcome wizard): choose Claude subscription token or Anthropic API key, paste, save; the credential is then verified at once (a minimal call), and once on opening while it never was, the token field showing a spinner, then green when Anthropic accepts it or red with the reason (owner, 2026-11-07: no separate block of the saved credential, no Verify button); remove asks first. The subscription option is shown to everyone but labelled for the owner's personal use; friends are guided to API keys (Anthropic's terms do not allow sharing one person's subscription with others).
- As built in A1 (2026-10-10): AES-256-GCM (`cryptography`), `CREDENTIALS_KEY` is 32 random bytes in base64, required in production (api and worker refuse to start without it), `key_version` is a fingerprint of the key that wrote the row. Rotation: the old key goes to `CREDENTIALS_KEY_PREVIOUS`, rows are re-encrypted when read or all at once with `python -m app.agents.cli rotate` (with the Gmail refresh tokens and the job feed keys). The ciphertext is bound to the user id and the kind (associated data), so a row copied to another user or relabelled does not decrypt.
- Verify (A1 decision): an API key is checked with one `GET /v1/models?limit=1` through the official `anthropic` SDK (no tokens spent); 401 and 403 mean invalid, 429, 503 and 529 mean try again later, network errors and anything else 503. A subscription token is checked by one Claude Code run in the worker (owner, 2026-11-07, replacing the A1 choice of no check; only the worker image holds the CLI, `api/app/agents/token_check.py`): Verify queues one turn of `claude-haiku-5-5` with no tool and answers `checking`, and the credential's `check` then reads `verified` (verified_at set), `invalid` (refused, verified_at cleared), `busy` (busy, rate limited or a usage limit reached) or `unavailable` (anything else), kept in Redis for that save only. Formats: API keys start with `sk-ant-api`; subscription tokens are today `sk-ant-oat01-`, but the docs do not state the prefix, so any `sk-ant-` value that is not an API key is accepted for that kind.
- The worker decrypts the credential only for the duration of the run and passes it to the SDK through the process environment of that run, never written to disk.

## Data model (runs and chat)

```
agent_runs(id uuid, user_id, agent text, job_id null, status enum(queued, running, done, failed, cancelled),
           input jsonb, output jsonb, error text, model text, input_tokens int, output_tokens int,
           cost_usd numeric null, started_at, finished_at, created_at)
agent_events(id bigserial, run_id fk, seq int, at, kind text, data jsonb)   -- streamed steps, kept for replay
agent_threads(id uuid, user_id, job_id null, title, created_at, updated_at)   -- each message rebuilds the conversation from agent_messages (no SDK session kept on disk)
agent_messages(id bigserial, thread_id fk, role enum(user, assistant), content jsonb, run_id null, at)
proposals(id uuid, user_id, run_id null, target text, target_id uuid null, kind text, payload jsonb,
          status enum(pending, accepted, rejected, superseded, invalid, undone), decided_by enum(user, system) null, decided_at,
          edited_value jsonb null, reason text null, created_at)
```

As built in A3 (2026-10-10, migration 0008): `run_id` is nullable (a rule-based system proposal of SPEC-mail has no run, issue #17 item 1) and set to null when its run is deleted. `decided_by` and `decided_at` are null exactly while a proposal is pending (a check constraint), then `user` when the user accepts or rejects it, `system` when it is superseded (a newer pending proposal of the same kind for the same target replaces it), invalid (its job was deleted when the user accepted it) or created already accepted (SPEC-mail's exception). `edited_value` keeps what the user applied instead of the proposed value, `reason` why the system decided. Kinds of A3, on target `job`: `job_note` {text} (appended to the notes on a new line) and `job_status` {status, from, reason}. Accepting goes through the jobs service on the locked job row: a job event with `via: "agent"` and the proposal id, `applied_on` filled on applied, and the job version checked when the client sends it (409 `stale`). The triage agent (`triage`, `claude-opus-5-5`, effort medium, 12 turns) needs a job, reads it with `get_job` (posting text included) and the profile with `get_profile_section` (contact details and the board list left out), and may propose only `shortlisted` (from found), `skipped` or `closed`, and only while the job is found, shortlisted, cv_ready or staged; refused proposals come back to it as tool errors and nothing is stored. It writes in English whatever the posting's language (the profile has no answer language setting yet). Guards added in review: the posting text, description and notes reach the model only under `untrusted_*` keys and the prompt treats them as third-party data, never instructions; identity is an allow list (headline, city, country, languages); a pending status proposal is superseded whenever the job's status changes by any path, and an unedited one whose `from` is no longer the job's status is marked invalid on accept (409 `status_changed`); creating a proposal takes a transaction advisory lock per (user, target, kind), so two runs at once leave one pending; `input.script` (recorded streams) is refused in production. Fixed after review (issue #25): accepting locks the job first, then re-reads the proposal under lock and checks it is still pending and still the caller's, the same lock order as PATCH, bulk and undo (job, then its proposals), so an accept racing a bulk status change on the same job no longer deadlocks: the bulk supersedes the proposal and the accept answers 409 `not_pending`. A bulk status change and its undo supersede the pending status proposals of all their jobs in one statement (`target_id = ANY(:ids)`). Undoing a status change does not restore the status proposals it superseded: they stay superseded, and the agent proposes again if asked.

As built in A4 (2026-10-10, migration 0009, stacked on A3's 0008): lock order, for every transaction that touches a thread and its run: the thread's row first, then the user's run lock (the advisory lock taken when a run is created), then the run's row, so a send, a delete and the worker ending a run wait for each other in turn and never deadlock; the worker's wait for the thread is bounded (`lock_timeout`, 10 seconds); when it passes, no answer is stored and the run is failed at once, with a sentence the user reads under the message, in a transaction of its own that locks no thread, only the run's row, so the thread takes the next message as soon as it is free (issues #27, #37 and #161). A send and a delete wait 5 seconds at most for each lock they take, the thread's row first, then answer 409 "This conversation is being updated. Try again in a moment." with nothing written (issue #161). `agent_threads` has no `sdk_session_id`; one thread per user and job (a partial unique index, `job_id` stays nullable for later chats not about a job); a thread goes with its job or its user. `agent_messages.content` is `{text}`, ordered by id; a user message's `run_id` is the run that answers it, an answer's `run_id` the run that wrote it (set to null if the run is deleted). Each message starts a run of the chat agent (`job_chat`, `claude-opus-5-5`, effort medium, 8 turns, read only tools `get_job` and `get_profile_section`, `get_job` bound to the thread's job: any other id answers "not found"). The worker rebuilds that run's prompt from the database every time (`app/agents/chat.py`): the job id, the earlier messages of the thread oldest first, then the new message; no SDK session is resumed and no resume option is passed. History budget: the newest earlier messages that fit about 30k tokens (estimated as characters / 4 plus 4 per message), always one unbroken tail; the older ones are replaced by one deterministic note saying how many are left out. A stored summary was not chosen: it would cost a second model call per long thread on the user's credential, add latency and a failure mode, and could drift from what was said, while the facts that matter (posting, profile) are read again through the tools at every answer. The run's final text is stored as the answer in the transaction that marks the run done, so a client that sees `done` finds it; a failed or cancelled run stores no answer and the user message shows why. One answer at a time per thread (409 with `active_run_id`, the thread row locked for the check). Deleting a thread deletes its messages and cancels a pending answer; its runs stay in the run log. A chat agent is never started through POST /api/agents/runs (422) and is not listed by GET /api/agents.

As built for issue #33 (2026-10-10, migration 0010): `agent_runs.credential_kind enum(claude_subscription, anthropic_api_key) null` is the kind of model credential the run used, written by the worker when it reads the credential (the kind only, never the secret), and returned with the run. `cost_usd` is the SDK's amount at API prices on every run: with an API key it is the cost and is shown as "Cost"; with a subscription it is shown as "Estimate at API prices" and said to be an estimate, not a bill: the run counts toward the plan's usage limits and what the user pays is set by the plan, which the app cannot see (a plan may charge for extra usage), so no wording says "not billed" (issue #80); a run with no recorded kind (older than the column, or failed before its credential was read) shows "Amount at API prices" and says that whether it was billed is not known. The `usage` event carries the same kind next to the amount (issue #80), so the browser words the step the moment it arrives. The triage agent writes everything the user reads (the note, the status reason, the summary) to the user in the second person; "they" is ruled out for the user only, and the chat agent is told that "you" in a note stored on the job means the user (issue #80).

## Testing strategy

- Unit: credential encryption round trip and key rotation; tool scoping (a tool called for user A can never read user B's rows, even with B's ids in the arguments); proposal application; run state machine; limits.
- Integration: the runner against a **fake model backend** (a stub that replays recorded SDK message streams), so CI needs no credential and costs nothing; SSE stream with reconnect; cancellation mid-run; worker restart marks orphaned runs failed.
- Live (manual, opt-in, small budget): one real triage run with Harald's subscription on the Jetson, one with a test API key if Harald provides one; recorded as evidence with tokens and cost.
- End to end (Playwright): credential card, start a run on a job, watch it stream (fake backend in CI, real on the Jetson), accept a proposal, chat round trip.

## Boundaries

- **Always:** user scoping inside every tool; proposals instead of direct writes; limits on every run; secrets only decrypted in memory.
- **Ask first:** giving any agent web access, shell or filesystem tools; raising concurrency or limits; any agent that sends something outside the app (email, form submission).
- **Never:** log a credential or a full prompt containing personal data; let a model choose the user id; share one user's credential with another user's run.

## Success criteria

1. Harald's subscription token and a friend's API key can each be saved, verified and used; neither is ever readable back.
2. A triage run on a real job streams live, finishes within its limits, records tokens, cost and duration, and produces a proposal that changes nothing until accepted.
3. A chat thread on a job survives a reload and continues the same conversation.
4. CI runs the whole module against the fake backend with zero model calls.
5. No cross-user access through tools, runs, threads or proposals (automated tests).

Owner, 2026-11-04: "in admin, i want a tab on all the agent. I want you to take an agent as a person, I want the system prompt, the tools, the skills ect.. all what made an agent and be able to vew, and modify it. For example the Agent job search, I want to see the parameters he can take, the prompt, the tools, the model ect.. absolutly everything si it will be easier to me to understand how claude cli is used in the app. so when i save something from the interface, it must be used at the next use of the agent. maybe store these infos in the db"

- **Who:** admins only (`require_admin`: a member gets 404 like every admin route, a visitor 401). Routes: GET /api/admin/agents (every registered agent; test ones only outside production), GET /api/admin/agents/{name} (the page), POST /api/admin/agents/{name}/versions `{changes, note?, base_version}` (201 the page with the new version; 404 no such agent, 409 another version was saved since the page was read, 422 a change the agent cannot take). Answers are `no-store`.
- **The page, read from the running code plus the saved version:** identity (module that registered it, who starts it, its flags in plain words), its input model as a table and its JSON schema, the system prompt in full, what its first message is built from with the dynamic parts named and no person's data (`catalog.FIRST_MESSAGES`), its tools as the model sees them (description, input schema, module: written by the worker to `agent_tools`, the api having no SDK), its model per credential kind, effort, max turns (and whether its input may lower them), wall time and what ends a run, the Claude Agent SDK options of a run (`sdk_options.fixed()` plus the definition, the function `runner.build_options` uses), the environment by variable names only, the PreToolUse gate, its skills (none: `setting_sources` is empty and the Skill tool is denied), its last 10 runs in numbers only (status, model, version, turns, tokens, "Started" from `started_at` or "Not started" for a queued run; the link to a run's page only for the admin's own runs) and, since A7, the person each run is for: the name and the e-mail as the Users page of Admin shows them (the e-mail in place of an empty name), nothing else of the account, a private agent's runs included (their content stays numbers only) and the history of its versions.
- **Editable, stored as versions (`agent_overrides`, migration 0031):** description, system prompt, default message (only for an agent whose first message can be it, `AgentDefinition.uses_default_message`: the base `prompt` and not a chat; the others answer 422 and the page hides the field), model and model per credential kind (from `definitions.MODELS`: `claude-opus-5-5`, `claude-sonnet-5-5`), effort, max turns (1 to 10,000), wall time (10 seconds up to the agent's own ceiling, lowered or raised above the code's own, A7: the ceiling is `catalog.ceiling_of`, the bound of the job that actually runs the agent. For an agent run as its own run_agent job it is the agents queue's, the longest wall time any agent has in code, `catalog.longest_wall_time_s`, today 86,400 s, the website search's of B20. For an agent that runs inside another module's job it is that job's bound, from the constants that set it: `apply_check` inside the decision of a Full auto item (`apply_decide`, the agents queue's job timeout less 120 s, 3,600 s today), `apply_form` inside a fill (its form deadline, the code's wall time), `apply_answer` inside a fill (its browser lease, 900 s), the finder's two agents inside a sweep (86,400 s), `profile_extract` and `document_transcribe` inside a profile import (its 60 minute deadline). A save above it answers 422 naming it and where the agent runs, the page shows it by the field with one sentence saying where the agent runs, and a version saved under an older, higher ceiling runs at the ceiling of now. The worker's bounds are per run, the orchestrator's choice: arq 0.28 takes no timeout per job, so `worker.run_agent` ends each job at its own bound, the queue's job timeout of before (3,720 s today) or, for a run whose wall time was raised past it, that wall time plus 120 s, and hands the runner that wall time as its most; arq's own timeout of run_agent is only the outer bound, `RUN_AGENT_MAX_S`, the agents queue's ceiling plus 120 s, and a job's own bound is never below the queue's job timeout; arq keeps every in progress key of the agents queue that long, so the agents Worker deletes the in progress keys of the jobs left in its queue before its first poll (`worker.clear_in_progress`, the queue's one consumer), and a try a hard kill left is dropped at the next start, never held a day; the reaper fails a running run past the queue's stale bound, or past its raised wall time plus 300 s when its recorded version raised it, whichever is later), and the code's tools switched on or off (never one the code did not give). A save stores only the fields that differ from the code; "Revert to the code's version" saves a version with no change, so the history is kept. A saved prompt is checked for its size only (not empty, at most 100,000 characters), never for what it says. Each version also keeps the hash of the code's value of every field it changes (`code_hashes`), and the code's prompt itself when it changes the prompt (`code_prompt`): when the code changes such a field later, the page says "The code's prompt changed since you saved this version" (or the field's name) with the diff of the code's old and new prompt, or the code's value now, and a revert button; the list marks the agent. Runs keep the saved version until a new one is saved.
- **Never editable, whatever a saved prompt says:** the input model, the flags (internal, private_io, bind, bind_job, chat, needs_job, test_only, live_text), the tools' code and schemas, FORBIDDEN_TOOLS, the permission mode `dontAsk` and the empty setting sources; and the guards enforced in code: browserd's line (B20), the apply gate and the person's approval (hard rule 4), no mail sent by itself (hard rule 3), the person's own never apply rules (apply's guardrails), the privacy of private runs.
