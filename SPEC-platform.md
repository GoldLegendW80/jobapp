# Spec: platform

Module of [CAPABILITY-MAP.md](CAPABILITY-MAP.md). Depends on nothing; every other module runs on it.

## Objective

A repeatable way to build, run and deploy the app on the Jetson. After this module, a single command on the Mac ships the code to the Jetson and brings up a stack that answers `https://jobapp.taild83d16.ts.net/api/health` from the internet through Tailscale Funnel (a Cloudflare quick tunnel until 2026-10-10, see Public access), with an empty React page at `/`. No product features yet: this is the skeleton every later module plugs into.

Who uses it: Harald, as operator. Friends never see this layer.

## Target host

| | |
|---|---|
| Host | `ssh jetson` (yessai@192.168.1.47, Wi-Fi) |
| Board | Jetson Orin Nano Developer Kit Super, 6 cores, 7.4G RAM, 49G free disk |
| OS | Ubuntu 22.04, L4T R36.4.7 (JetPack 6), aarch64 |
| Docker | 29.8.0, Compose v5.5.1, `nvidia` runtime registered (not used by this app) |

RAM budget for the whole stack, all modules included: 5G, leaving the rest to the OS. Each service declares `mem_limit`. With the parser's 640m the limits of compose.yml add up to 3968m; the 1536m reserved for the browser module would take the sum to 5504m, over the budget by about 380m, which that module settles when it is built (the parser's limit is a starting figure, set from measurements by ingestion G2b and G8).

## Tech stack

| Service | Image or build | Role |
|---|---|---|
| `caddy` | `caddy:2-alpine` | Reverse proxy: `/` to `web`, `/api` to `api`, `/vnc` to `browser` (later) |

| `redis` | `redis:7-alpine` | Queue between `api` and `worker` (used from the `agents` module on) |
| `tailscale` | `tailscale/tailscale` (pinned by version and arm64 digest) | Tailscale Funnel to Caddy (`tailscale/serve.json`: HTTPS 443 proxied to `http://caddy:8080`, Caddy's unpublished tunnel listener that trusts only Funnel's `X-Forwarded-For`): free, stable URL `https://jobapp.taild83d16.ts.net`, userspace networking, state in the `tsstate` volume (see Public access) |

| `parser` | the worker's image (`jobapp-worker`), no build of its own | Parses uploaded documents for the worker, one sandboxed child per document (ingestion; see The parser service) |

`worker` and `browser` are added by their own modules; the Compose file reserves their names.

Python dependencies are managed with `uv`; JavaScript with `pnpm`.

## Commands

```bash
# local development on the Mac
docker compose -f compose.yml -f compose.dev.yml up --build    # hot reload for api and web
docker compose exec api alembic upgrade head                   # apply migrations
docker compose exec api pytest                                 # backend tests
pnpm --dir web test                                            # frontend tests
pnpm --dir web lint && uv run --directory api ruff check .     # lint

# deploy to the Jetson
./deploy.sh                    # rsync app/ to jetson:~/jobapp, then on the Jetson: build, ops/migrate.sh
                               # (alembic upgrade head in a one off container of the new image), compose up --wait
./deploy.sh logs api           # tail logs of one service
./deploy.sh url                # print the stable Funnel URL, from tailscale status in the tailscale container
./deploy.sh backup             # pg_dump -Fc to jetson:~/jobapp-backups/jobapp-YYYY-MM-DDTHHMMSS.dump, verified, then the
                               # retention: BACKUP_KEEP=7, the newest 7 dumps stay and a dump 7 days old or more is
                               # deleted, so that a document a user deletes leaves the server's backups within 7 days;
                               # the cost: after 7 days no restore point predates a bad change (Backup retention, below)
./deploy.sh restore <file>     # into a scratch database; --into-live replaces the live one
```

Images are built on the Jetson itself (native arm64), so no cross-build is needed.

## Code style

Backend: type hints everywhere, routers thin, logic in `service.py`, one module per capability.

```python
# api/app/health.py
from fastapi import APIRouter, Depends
from sqlalchemy import text
from sqlalchemy.orm import Session

from app.db import get_session

router = APIRouter()


@router.get("/api/health")
def health(session: Session = Depends(get_session)) -> dict[str, str]:
    session.execute(text("select 1"))
    return {"status": "ok"}
```

Frontend: function components, shadcn primitives, data through TanStack Query, no global state library until one is needed. Ruff and Prettier with default settings. Names in English.

## Testing strategy

- Backend: pytest with a throwaway Postgres (the dev `db` service, one database per test session). `/api/health` has a test from day one.
- Frontend: Vitest and Testing Library for components; Playwright end-to-end tests arrive with the `identity` module.
- Platform itself is verified by a smoke script, `deploy.sh smoke`: health through Caddy on the Jetson, then through the public Funnel URL.

## Boundaries

- **Always:** pin image tags and dependency versions; arm64 images only; `mem_limit` on every service; secrets only in `.env`; run tests before deploying.
- **Ask first:** adding a service to Compose, exposing a port on the Jetson's network interface, changing the public access setup (Tailscale Funnel), anything run with `sudo` on the Jetson.
- **Never:** commit `.env` or any token; open a port on the home router; touch the Jetson's existing Ollama or system services; run `docker system prune` or delete volumes without asking.

## Success criteria

1. `./deploy.sh` from a clean clone brings the stack up on the Jetson with no manual step beyond writing `.env`.
2. `curl $(./deploy.sh url)/api/health` from outside the home network returns `{"status":"ok"}`, with a database round trip.
3. The public URL serves the React shell with Tailwind and one shadcn component rendered.
4. A reboot of the Jetson brings everything back (`restart: unless-stopped`) within 2 minutes.
5. The idle stack uses under 1G of RAM (`docker stats`).
6. `./deploy.sh backup` produces a restorable dump; a restore into a fresh database is tested once.

## Migrations on deploy (issue #81, 2026-10-10)

New code never serves on a schema that lacks its columns: the schema moves first.

- Order, the same in `.github/workflows/deploy.yml` and in `./deploy.sh`: build the images, take the predeploy backup (workflow only, as before; a manual `./deploy.sh` takes none, run `./deploy.sh backup` first when the release carries a migration), run `ops/migrate.sh`, then `compose up --wait`, then health and smoke.
- `ops/migrate.sh` runs `alembic upgrade head` with `docker compose run --rm --no-deps -T --name jobapp-migrate api`: a one off container of the api service as the new `compose.yml` defines it, so the image just built, the api's `env_file` and network, no published port, no restart policy, removed when it ends. The api and worker containers of the previous release are not touched and keep serving. A db that is not running is started alone first (a first install creates the empty database there and applies every migration); a running one is left as it is.
- The rule this needs: the previous release must run on the migrated schema, expand first and contract in a later release ([CONTRIBUTING.md](CONTRIBUTING.md), Migrations). `api/tests/test_migration_rules.py` flags the obvious breaches in CI.
- A migration fails: alembic runs the whole upgrade in one transaction, Postgres rolls it back, the script exits non zero and the deploy stops before anything restarts. The previous release keeps serving. The workflow puts the previous files and `:latest` tags back; `./deploy.sh` says that the Jetson's tree and `:latest` images already hold the new release.
- A migration hangs: it is stopped after `MIGRATE_TIMEOUT_S` (default 300), the container removed, and the Postgres sessions of this database that hold or wait for the migration's advisory lock are terminated (`pg_locks` is cluster wide, so the statement names the current database), because Postgres would otherwise keep a vanished client's locks until its statement ends. Same stop as a failure. A container killed before the limit (exit 137, for instance out of the api's `mem_limit`) is reported as killed, not as a timeout, and its session is ended the same way. Removing a leftover container by hand does not end its session: the README's recovery block gives the statement.
- The migration succeeds and the new stack does not become healthy: the workflow's rollback starts the previous files and images again, on the migrated schema. Nothing downgrades the schema automatically, ever: `downgrade()` may drop data, and the expand rule makes it unnecessary. Going back in schema is a human decision: `alembic downgrade` by hand, or the predeploy dump with `ops/db.sh restore-live`.
- At head it is a no-op: one container start, a couple of seconds, "already at head, nothing to apply" in the log.
- Two deploys never migrate at once: the Jetson's deploy lock (`flock`, shared by the workflow and `./deploy.sh`) and the workflow's concurrency group serialize deploys, `ops/migrate.sh` refuses to start while a `jobapp-migrate` container runs, and `alembic/env.py` takes `pg_advisory_xact_lock` so two upgrades that still meet queue instead of racing.
- The log holds alembic's own lines and the revision reached, never a value of `.env`: the settings keep the database URL as a secret, and the script masks the credentials of anything shaped like a URL on the way out.
- Tests: `tests/deploy_test.sh` (CI, fakes) runs `ops/migrate.sh`, `cmd_deploy` and the deploy step cut out of `deploy.yml`, and asserts the order, the stop on a failing or hanging migration with the stack untouched, the no-op, the first install, and a rollback that neither reruns alembic nor downgrades. `tests/migrate_test.sh` (by hand on the Mac, real Docker, never a CI step: it builds the api image four times and the runners' disk and CPU budget is tight; CI only shellchecks it) plays the same paths on a scratch stack with real Postgres and alembic, a killed container and the README's recovery statement included.

## Backup retention (T10, issue #49, decided 2026-10-10)

The owner decided that a document a user deletes is gone from the server's backups within 7 days (SPEC-ingestion.md, Retention). The retention of every dump on the Jetson follows from that. The README (Backups and restores, Retention) is the operator's reference; this is the rule.

- One number, `BACKUP_KEEP`, 7 by default, read by `ops/db.sh` at each run: the environment of the run, then the `BACKUP_KEEP` line of the Jetson's `.env`, then the default. The cron line of `./deploy.sh backup-schedule install` and the deploy workflow name no number of their own, so a change of the default takes a deploy and a change of the value an edit of that `.env`, never a reinstall. An explicit value wins for both rules (14 keeps 14 dumps and 14 days) and, above 7, breaks the promise knowingly: every backup prints a warning.
- Two rules, applied by `ops/db.sh backup` once the dump of the run is written and verified: the newest `BACKUP_KEEP` dumps of the run's folder stay (count); a dump `BACKUP_KEEP` days old or more is deleted (age) in `~/jobapp-backups`, in `deploys/` (predeploy dumps) and in `incoming/` (dumps uploaded for a restore). The deploy's backup, whose folder is `deploys/`, rotates that folder alone; the nightly run applies the age rule in all three. This replaces the newest 10 predeploy dumps kept whatever their age.
- Age is counted in UTC calendar days between the date in the dump's name and the date in the name of the dump just written, never from a modification time. Whole days, because nightly runs a few seconds apart must agree about the dump of 7 nights ago and because a folder can then be checked by reading names. The residue: a dump written between midnight UTC and the end of the nightly run lives 7 days plus those hours; every other dump lives less than 7 days. With the schedule at 03:17 and on the assumption that the Jetson's time zone is Europe/Paris (not checked by this change), that is at most 1 hour 17 minutes in summer and 2 hours 17 minutes in winter; 3 hours 17 minutes if its clock is on UTC. `BACKUP_KEEP=6` removes it.
- Safety: nothing is deleted before the new dump is written, verified and flushed to the disk, data then folder (`sync`), and a failing backup deletes nothing and exits non zero; the dump the run wrote, the newest verified dump of the whole tree, is never deleted, and no folder has an exception of its own (the last predeploy dump goes at 7 days); a restore never deletes; `deploys/` is skipped while a backup or a restore holds its lock, and a lock file that cannot be opened is said as that and ends the run non zero; only a regular file named exactly `jobapp-YYYY-MM-DDTHHMMSS[-tag].dump` with a date that exists, directly in one of the three folders, is deleted, one full path at a time, never through a symbolic link, and a backup folder that is itself a link gets its dump and no deletion, whether or not its name is written with a slash or a `/.` after it (the name is trimmed once, in `ops/db.sh` and in `deploy.sh`, and `/` and the home folder are refused); everything else there is left alone and reported at every run, as is the scratch database of `restore --keep`.
- Two guards decided on 2026-10-11, since a verified dump is one that reads to its end, not one whose database still held its data. A run never leaves the server with its own dump alone: when every other dump would go (a week without a backup, a clock ahead), the newest of them that is not an empty file stays for one more run, one run past the limit in that case only. And a dump less than half the size of the last one accepted in its folder deletes nothing, in any folder: the run keeps it, warns with both sizes, and every run of that folder, `prune` included, is then measured against that last accepted dump until one is at least half its size or one run is made with `BACKUP_ACCEPT_SHRINK=1`. A run is never measured against a pre-restore dump, an empty file or a dump named after it. That hold also delays the 7 days and has no bound but the disk, and a user who deletes more than half of what the database holds causes it, so it must be seen: the mark `.size-hold` counts the runs held, the line is an ERROR from the seventh, `ops/db.sh retention` ends with status 3 and `./deploy.sh backup-schedule status` with 1 while a hold stands (with both sizes and the command that lifts it), and the deploy workflow turns the line of its backup into an annotation of the run. The mark is read only as a regular file and written whole; anything else under its name stops every deletion until it is removed. Lifting a hold is the owner's act.
- What the 7 days need on the server: the schedule installed and `./deploy.sh backup-schedule status` showing 7; no `BACKUP_KEEP` above 7 in the Jetson's `.env` or in the cron line; the nightly backup succeeding; no hold on the rotation; no file outside the name pattern in the backup folders and no scratch database left. Outside the rotation by nature: dumps pulled to the Mac, copies of the database volume, and a restore, which brings back what was deleted after its dump.
- The cost: after 7 days no restore point on the Jetson predates a bad change, predeploy dumps included.
- Tests: `tests/deploy_test.sh` (CI, fakes, a clock the test sets) covers the default, an explicit value, the age rule in the three folders, each safety rule, the report and the schedule against a fake Jetson; `tests/backup_test.sh` (by hand, on the Jetson) plays the age rule with copies of a real dump under old names.

## The parser service (ingestion G2a, decided by Harald on 2026-10-10)

Parsers of hostile files are where exploits live, and the worker holds decrypted model credentials during agent runs. So every parser and every image decode runs in a service of its own, which holds no secret and reaches nothing. Nothing is parsed in the api or in the worker.

- **Service `parser` in compose.yml:** the image `jobapp-worker:latest` (no second image and no build section: Compose does not pull an image another service of the file builds, and the parser follows the worker's tag forward and on a rollback), `pull_policy: never`, started on `python -I /app/app/ingestion/sandbox/server.py`, `user: "10002:10002"` (the api and the worker are 10001), `cap_drop: [ALL]`, `no-new-privileges`, `read_only`, no volume, no tmpfs, `ipc: none` (Docker leaves `/dev/shm` writable in a read only container: this takes it away), `pids_limit: 32`, `mem_limit: 640m`, restart unless-stopped. No `env_file`: its environment is `PARSER_PORT` and what the image sets, so no `CREDENTIALS_KEY`, no `SECRET_KEY`, no database or Redis address, no model credential. Its own PID namespace. The files that run the worker from another tag give the parser the same one (`compose.dev.yml`, with the code mounted read only; `tests/compose.a2-e2e.yml`; `tests/compose.j5-e2e.yml`).
- **Network:** `parsing`, `internal: true`. The parser is on it and on nothing else; the worker is on `default` and on `parsing`; every other service is on `default` alone. The parser cannot resolve or reach db, redis, the api or an outside name or address, and nothing but the worker can reach it. It publishes no port and serves nothing to a browser.
- **Protocol** (`api/app/ingestion/sandbox/server.py`), one TCP connection per job to `parser:7070`: a JSON header line of at most 4096 bytes (`{kind, size, options}`), the bytes, then a JSON header line (`{ok, failure, code, length}`) and a UTF-8 JSON body of exactly `length` bytes. A size over 20 MiB, an unknown kind and a line that is no header are refused before a byte of the document is read. A connection silent for 10 s is given up, a request has 60 s to arrive. One job at a time; a second one waits at most 75 s, then `busy`, and so does a job that finds two already waiting. A `ping` without bytes is answered at once by a child of its own, even during a job. A client that closes its connection cancels its job. The server parses nothing: it passes on what the child wrote, and its log holds a kind, sizes, a code and durations, never content (the child's standard error goes nowhere).
- **The child** (`api/app/ingestion/sandbox/main.py`), one process per job, started with an empty environment as `python -I -B main.py <kind> <options>`. Both files are standalone: the standard library only, never `app`. Before it imports a handler the child sets, on itself: `cryptography` unimportable; `RLIMIT_AS` 512 MiB, `RLIMIT_CPU` 45 s soft and 46 s hard, `RLIMIT_FSIZE` 0, `RLIMIT_NOFILE` 16, `RLIMIT_NPROC` 0, `RLIMIT_CORE` 0, `RLIMIT_MSGQUEUE` 0; `PR_SET_DUMPABLE` 0; `PR_SET_NO_NEW_PRIVS`; a seccomp filter (classic BPF built by hand, installed through `ctypes`) that ends the process on another architecture and answers `EPERM` to `socket`, `socketpair`, `bind`, `connect`, `ptrace`, `process_vm_readv`, `process_vm_writev`, `kill`, `tkill`, `tgkill`, `rt_sigqueueinfo`, `rt_tgsigqueueinfo`, `pidfd_open`, `pidfd_send_signal`, `execve`, `execveat`, `io_uring_setup`, `io_uring_enter`, `io_uring_register`, `shmget`, `msgget`, `semget`, `mq_open`, `unshare`, `setns`, and on x86_64 to every number at or above `0x40000000`. Then it reads the state back and tries two denied calls. **It fails closed:** when any step fails it exits with status 70, having imported no handler and read no byte. The server kills a child after 60 s of wall time and when it has written more than 4 MiB.
- **Kinds:** `pdf_text`, `docx`, `linkedin_zip`, `image`, `pdf_render`, each one file of `sandbox/` added by its task (G2b, G7, G8) and answering `not_supported` until then, and `ping`, built in, which reports the lockdown as measured in the child and the size and SHA-256 of the bytes it received.
- **Health:** `server.py --check` sends a ping through the loopback and requires the child's report: every denied call answering `EPERM`, every limit at its value, non dumpable, no capability, an empty environment, three descriptors and no socket, no directory it can create a file in, the server's `/proc` entry closed. `PR_GET_SECCOMP == 2` alone would prove nothing where Docker already installs a filter of its own, which is why each call is tried. The worker stays healthy without the parser: a call that cannot connect fails at once as a failure of the server.
- **The worker's client** (`api/app/ingestion/parser_client.py`): 75 s per call, at most 4 MiB of answer, and every byte of it read as hostile data: strict JSON (`ValueError` and `RecursionError` caught, no duplicate key, no float), known keys only, the caps of the columns that store the result (migration 0011), no U+0000 and no lone surrogate in a text, form feeds equal to the pages minus one, the JPEG magic on every image, reasons and notes as codes from closed lists with integers. Errors: `ParserDownError`, `ParserBusyError`, `ParserTimeoutError`, `ParserRefusedError` (`failure` "file" or "server"), `ParserMalformedError`. It logs one line per call (kind, size, outcome, duration), never content.
- **Residual risks:** what a parser taken over by a file can still do is written in the README (The parser service). The seccomp filter on the Jetson's kernel (Tegra 5.15) is an assumption until `tests/ingestion_parser_jetson.sh` has run there: without it the service is unhealthy and the deploy rolls back.
- **Tests:** `api/tests/ingestion/parser/`. On any system: the filter program run instruction by instruction, the lockdown against fakes that refuse each step, the server against hostile clients, the client against hostile servers. Marked `docker` (CI, the api job): the service started by Compose from this file's definition with a handler that tries to get out, each limit and each denied call for real on Linux, the network isolation, the filter that cannot be installed. `tests/compose_smoke.sh` and `tests/jetson_smoke.sh` check the running service through `tests/parser_check.py`.

## Public access: Tailscale Funnel (decided 2026-10-10)

- Decided by Harald on 2026-10-10, replacing the Cloudflare quick tunnel: the Gmail module needs Google OAuth redirect URIs, and those need a URL that does not change on every restart.
- Tailscale Funnel on Harald's tailnet `taild83d16.ts.net` (free plan, MagicDNS on, HTTPS certificates enabled, the `funnel` node attribute granted to `autogroup:member`). Free, and the URL is stable: `https://jobapp.taild83d16.ts.net`, the node name `TS_HOSTNAME` plus the tailnet. It survives restarts, redeploys and reboots.
- Service `tailscale` in compose.yml, in the `tunnel` profile (Jetson only, never on the Mac): the official image pinned by version and arm64 digest, userspace networking (`TS_USERSPACE=true`, no `/dev/net/tun`, no `NET_ADMIN`, every capability dropped, no sudo on the Jetson), 128m, restart unless-stopped, healthy when `tailscale status` says `Running`. Outbound connections only; no port published.
- Login: a one-time, user-owned auth key in `TS_AUTHKEY` of the Jetson's `.env`, used on the first start only (`TS_AUTH_ONCE`); the login then lives in the `tsstate` volume and the key is removed from `.env`. Without either the service never turns healthy and the deploy fails.
- `tailscale/serve.json` (`TS_SERVE_CONFIG`) terminates TLS on 443 with the node's Let's Encrypt certificate and proxies to `http://caddy:8080`, with Funnel allowed on that port only.
- Client address: Funnel sets `X-Forwarded-For` to the address the visitor connected from, replacing any value sent (checked in the tailscale v1.102.5 source, `ipn/ipnlocal/serve.go`). Caddy's `:8080` trusts private peers and reads `X-Forwarded-For` only, strictly; `Cf-Connecting-Ip` and similar headers pass through Funnel untouched and are never trusted. `./deploy.sh smoke` proves from outside that a visitor cannot spoof its address.
- `./deploy.sh url` reads `Self.DNSName` of `tailscale status --json`; it fails with the reason when the container is down or not logged in.

## Request limits by layer (issue #100, 2026-10-13)

Why: FastAPI reads a JSON body before a route's dependencies run, so a caller with no session could make the api hold a body on any JSON route, the ones that answer 401 included. Measured on `main` through Caddy: thirty connections each holding 9 MiB of a stalled sign in took the api from 115 to 375 MiB of its 512 MiB. Numbers below marked measured come from one run each on a scratch stack on the Mac (`tasks/evidence/platform-100/`).

- **Caddy** (`caddy/Caddyfile`): three body classes matched by expressions that exclude each other: `/api/auth/` 64 KiB, `POST /api/ingestion/documents` 20 MiB (method and whole decoded path, as ingestion G1 wrote it), everything else 10 MiB. A declared length over the limit is Caddy's own 413 with nothing proxied; a streamed body is cut at the limit. `read_header` 10s and `idle` 60s (defaults 1m and 5m), set in both `servers` blocks because a block with an address replaces the global one. `read_body_idle` and the write timeouts stay at Caddy's defaults, so that the upload and the paste, which answer a stalled body themselves at 30s and 60s, speak first; a minimum rate was tried and withdrawn, because with a rate Caddy counts a budget from the start of the body in place of the idle window. That default minute does not cover small bodies: measured in the review of pull request #106, Caddy answered a silent body 504 at 60s when 9,000,000 or 300,000 bytes were declared, and did nothing for 130s and 240s when 60,000 or 1,000 were.
- **api** (`api/app/body_limit.py`), which does not depend on the proxy: an ASGI middleware, innermost, so before any body is parsed and with its refusals logged. First, no session, no body: under `/api`, a request that announces a body (a Content-Length other than 0, or a Transfer-Encoding) on a route that is not in `PUBLIC_ROUTES` is answered 401 before its body is read; the session is the routes' own lookup, kept on the request. Then a size: `/api/auth/` 64 KiB, other routes 1 MiB, and a route whose schema allows more gets a size from that schema at four bytes per character (`POST /api/jobs`, a posting of 1,000,000 characters: 4,065,536 bytes); 413 above, for a declared length before a byte is read. The body is gathered in the middleware, into one buffer of at most the limit, before the app runs: the app never acts on a body that is refused, and a body sent in tiny pieces takes no more than the limit. The routes that read their own raw body are not capped and not read here: profile photo and import, jobs import, document upload and paste. A body the api caps must bring a chunk every 20s and be whole within 60s, on `/api/auth/` every 5s and within 10s (a sign in is one packet, and this is how long a caller with no session holds one of uvicorn's connections), else 408 with `Connection: close`.
- **uvicorn** (`api/Dockerfile`): `--limit-concurrency 256` (503 once that many connections are open, a connection counting as soon as it is open) and `--timeout-keep-alive 5`. Request headers are bounded by Caddy in front: about 20 KiB (its default `max_header_size` of 16 KiB plus the 4,096 bytes Go adds; measured in the review, 20,300 bytes pass and 20,600 are 431); uvicorn parses with httptools here and no header limit of its own was established.

Tests: `api/tests/test_body_limit.py` (the middleware alone), `api/tests/identity/test_body_limit_api.py` (the whole app and a real socket: every route that is not public answers 401 to a body it has not read; sizes and times; no schema allows more than the class of its route takes, walked over every route with a JSON body; a posting at the schema's maximum in four byte characters; the photo route's own limit; what the uvicorn limit does; the answer `./deploy.sh smoke` expects for its 5 MB request, read from `deploy.sh`), and in CI through the real proxy `web/e2e/ingestion-g1.spec.ts` (the 64 KiB class declared and chunked, and the 401 for a body with no session). `tests/compose_smoke.sh` holds the same checks and is run by no CI step. No CI test holds a connection against Caddy's timeouts.

What remains possible (measured once each, by the author in `tasks/evidence/platform-100/` or by the reviewer of pull request #106):

1. **Sign ins at once, issue #108, to be done next.** Each password check takes 64 MiB by design and nothing bounds how many run together: four at once took the api from 116 to a peak of 378 MiB, and the sign in limit admits 20 per address in 15 minutes. It is now the cheapest way for a caller with no session to exhaust the api's memory. Outside request bodies, not changed by this work.
2. **256 slow connections stop the app answering while they last**, which is what the uvicorn limit trades for bounded memory: 260 connections each holding a sign in body just under 64 KiB cost about 42 MiB at the api and 35 MiB at Caddy, and every other request was answered 503 until they were released. A silent sign in holds its place 5s, a trickling one 10s. The container's health check shares the limit: during such a flood it reads unhealthy and a deploy started then would fail and roll back. 256 is kept (the reviewer measured the same behaviour at a scaled limit and recommends keeping it); what would change the caller's cost is a bound per client address on public bodies in flight, not done here.
3. **A small silent or trickling body keeps its connection to Caddy for as long as the client likes** (240s with no answer for 1,000 declared bytes). The api lets go at its own times; Caddy has 128 MiB, no limit on connections and, without a third party module, none per client address, and through Funnel all visitors reach it from one peer. 2,000 connections with unfinished headers took Caddy from 22 to 63 MiB for their 10s. This was so before this work and is not bounded by it; a hard `read_body` ceiling above the upload's ten minutes may be the bound and needs its own test with an event stream and a slow upload.
